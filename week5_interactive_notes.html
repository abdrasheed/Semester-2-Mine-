🖥️ Persistent Storage Primer

Motherboard Connections (Bus)

Storage devices connect to the CPU via buses. The closer to the CPU → the faster the connection.

  • Main Memory / PCIe — closest connections, highest bandwidth
  • SATA, USB, Ethernet — more distant, lower bandwidth

🔌 Host Interfaces

The host interface is the storage connection standard. Even if the storage medium is fast, it can be bottlenecked by the interface. This is why M.2 SSDs use PCIe.

💾 HDD vs SSD

  • Mechanism: Rigid platters coated with magnetic material, rotating at ~7,200 RPM
  • Lifespan: ~4–6 years
  • Uses small DRAM cache (battery-backed) to reduce latency
  • Connects via SATA

Hybrid Drives (SSHD)

Combine HDD + SSD in one device (or as separate dual drives). Writes cached in SSD then spooled to HDD. Popular read data held in SSD portion. Not generally good for intensive Big Data tasks — the SSD cache gets saturated.

🔒 RAID — Redundant Array of Independent Disks

Individual drives fail. RAID groups multiple co-located disks so they appear as one, providing redundancy and/or speed. Options:

  • Hardware RAID: On-chip RAID controller
  • Software RAID: ZFS, XFS, or built-in OS RAID

Three Core Concepts

  • Data Striping — Segmenting sequential data across multiple physical devices → large reads spread over multiple drives
  • Disk Mirroring — Replication of logical disk volumes onto separate physical disks in real time → continuous availability
  • Parity Data — Redundancy using XOR: if one drive fails, parity + remaining data reconstructs missing data
XOR Parity Example

3 drives: A=1010, B=0110, P=A⊕B=1100. If B fails: B = A⊕P = 1010⊕1100 = 0110 ✓

Exam Key Point

Most storage systems use RAID 5 or RAID 6 so that a single disk failure does not cause data loss. RAID 0 offers no protection — it increases failure risk.

🌐 What is Distributed Storage?

Distributed storage exists for the same reason as distributed compute — single machines have limits.

  • Can saturate host interfaces within a single machine
  • Distribute storage media across physical machines
  • Higher parallelism → more data storage capacity needed
  • Most Big Data uses a Distributed File System (DFS)

🎯 Motivations for Distributed Storage

🛡️ Resiliency

Data is replicated so a single failure doesn't cause data loss or wider system failure.

⚡ Speed

More physical devices → more parallel reads/writes → higher max read/write capacity.

📈 Scalability

Horizontally scale storage infinitely — just add more machines.

📍 Data Locality

Replicated data = schedule compute close to data → reduces network transfer cost.

⚠️ Challenges: No Best Solution

No single best solution — every DFS makes trade-offs between:

PropertyChallenge
ReliabilityIf we update a file on multiple copies, how do we ensure all copies are up-to-date and how long do we wait?
AvailabilityDrives sometimes return bad data. If a read fails, most apps stall. Need to always return correct data.
PerformanceDistributing data requires network transfers. Performance varies greatly for small vs. large files.
CapacityMore replicas and error checking = more space used = higher cost.

OneDrive Example — What Can Go Wrong

Simple DFS: file written locally → copied to remote mirror. Issues:

  1. Detection delay — Client may not immediately detect file change; remote copy stays stale
  2. Corrupted upload — Disk read error uploads corrupt file, replacing last good version
  3. Timestamp confusion — "Is this file newer?" decided by timestamps; wrong system clock = wrong decision
  4. File in use — Should server overwrite client file if its version is newer but the user has it open?
  5. Out-of-order detection — Files detected out of temporal order; how to resolve?

🔗 Network File System (NFS)

NFS: basic DFS developed in 1984, still common today. Client–server architecture.

  • Servers host files
  • Clients read and write those files
  • Stateless — if server control process crashes, no data is lost (state not held in memory)
  • Locking — only one client can edit a file at once

NFS Architecture

OSes have a Virtual File System (VFS) layer — allows devices of different formats to expose files via a standard API (in Linux).

  • Read: Copy of file transferred over network to client
  • Write: Locking request first → writes to file → unlock when done

✓ NFS Advantages

  • Simple — files exist in only one place
  • Widely compatible
  • Low overhead
  • (Relatively) fast
  • Reliable under normal conditions

✗ NFS Disadvantages

  • No native replication — server is single point of failure
  • Often combined with RAID to mitigate failures
  • Inherently insecure — assumes trusted network
  • Sensitive to network congestion and server load

🐘 HDFS — Hadoop Distributed File System

Design Goals

  • Designed for commodity clusters — off-the-shelf, inexpensive but unreliable machines
  • Write-once-read-many access model (not arbitrary edits)
  • High throughput batch storage
  • High availability / fault tolerance
  • Horizontal scalability
  • All communication over TCP/IP

Architectural Principles

  • Unix-like API: open, close, read, write operations
  • Unix-like inodes: metadata (ownership, permissions, file type)
  • Unix-like paths: e.g. /my_directory/cool_file.txt
  • Separates metadata from content data: NameNode (global metadata) vs DataNodes (actual file blocks)

🗂️ NameNode (Master Node)

Responsibilities

  • Tracks all files in the HDFS
  • Stores number of blocks, locations of DataNodes, replica locations
  • Holds the namespace: directory tree, file IDs, hierarchical organization
  • Access permissions and modification times

Filesystem Image (Metadata)

All metadata = filesystem image, loaded into RAM while NameNode runs (low-latency access). Two recovery mechanisms:

  • Checkpoint file — snapshot stored locally; enables NameNode restart recovery
  • Journal/WAL — Write-Ahead Log of all mutations since last checkpoint; recovers to point of failure
⚠️ Single Point of Failure

The NameNode is a single point of failure in Hadoop versions 1 and 2. Hadoop v3 introduced High Availability NameNode with an active/standby pair.

💽 DataNode (Slave Nodes)

Responsibilities

  • Stores each block assigned to it
  • Handles associated read and write operations
  • Holds per-block metadata (checksum, size)

Physical Implementation

Each HDFS block = two files on the native filesystem of the DataNode:

  • File 1: Block contents
  • File 2: Per-block metadata (checksum + size)
Block Size = 128MB (default)

This is not like a normal file system (typically 4KB blocks). Large blocks reduce NameNode memory usage and are well-suited to Big Data's large sequential reads. Note: the host FS impacts DataNode performance.

3

Client contacts DataNodes directly (bypassing NameNode). Selects the closest DataNode for each block using Rack Awareness.

Design Decisions

  • Minimise NameNode contact — only one request per file read (NameNode is a bottleneck in early HDFS)
  • Rack Awareness — select closest DataNode by network topology. Rack structure manually configured in HDFS config file

Alternative Approaches Considered:

  • Contact all replicas, return when first responds → fast but wasteful
  • Random replica → load balanced but ignores locality
  • Least-loaded replica → requires nodes to continuously report load

✍️ HDFS Write Process

1

Client → NameNode: Register Block (addBlock)

Client asks NameNode to choose DataNodes to host replicas of the first block. NameNode returns a pipeline of DataNodes (e.g., DN1→DN2→DN3).

2

Client → DN Pipeline: Send Data as Packets

Client organizes pipeline from node-to-node. Data buffered at client side, flushed as 64KB packets into the pipeline.

3

Pipeline Forwarding (Parallel)

Writes occur in parallel — each DataNode forwards received data to the next. Next packet pushed before ACK received (sliding window). Periodic hFlush writes to journal for crash recovery.

4

DataNode → NameNode: Block Reports

Each DataNode reports blocks it receives directly to the NameNode, so NameNode knows when a block is fully written.

File Locks vs. Leases

NFS: File Locks

  • Files locked when user wants to write
  • Lock lasts until user explicitly releases it
  • Risk: user crashes → file locked forever

HDFS: Leases

  • NameNode's Lease Manager tracks write leases
  • Lease expires when: file closed OR time limit exceeded
  • If lease expires (client dies): NameNode triggers Lease Recovery
  • No write in progress → simply close file
  • Write in progress → trigger Block Recovery

Block Recovery

When a lease expires during a write:

  1. Some DataNodes have partial data (pipeline still intact if no DataNode failures)
  2. Client is unavailable — cannot Finalize the block
  3. NameNode appoints a Block Recovery Primary DataNode
  4. Primary generates new file-length data and syncs with a new generation stamp across DataNodes
  5. Block is Finalized

Pipeline Recovery (DataNode Failure During Write)

ScenarioRecovery Action
Setup FailureClient abandons write and retries from scratch
Failure During WriteFailed DataNode cuts TCP/IP. Client stops sending, reconstructs pipeline using remaining nodes, continues write.
Close FailureClient reconstructs pipeline and retries close operation

🔄 Replication, Heartbeats & Storage Policies

NameNode–DataNode Communication

DataNodes communicate with NameNode, not the other way around.

  • Startup handshake: Verifies namespace is correct, registers with unique StorageID
  • Block Reports: Sent after DataNode finishes receiving a block: list of (block_id, timestamp, length)
  • Heartbeats: Every 3 seconds — provides storage use/capacity info + Block Reports. Missing heartbeat → DataNode marked dead

Re-Replication

NameNode has two services:

  • Replication Monitor — too few or too many replicas?
  • Cluster Balancer — blocks well-distributed across cluster?
Default: 3 Replicas Policy
  • Replica 1 — Random DataNode in same rack as NameNode (or same machine as writer if available)
  • Replica 2 — Random DataNode in a different (remote) rack
  • Replica 3 — Different node in the same remote rack as Replica 2

This balances: write speed (local replica), rack-level fault tolerance (cross-rack), read speed (two nodes in remote rack).

Storage Types and Storage Policies

Hadoop 3 introduced intelligent block placement based on storage type:

Storage TypeDescription
ARCHIVECheap, high-density, cold storage

SSDSolid state
RAM_DISKIn-memory (volatile)

Storage Policies defined on directories/files. Example policies: Hot, Cold, Warm, All_SSD. Each policy specifies primary block placement + fallback for creation + fallback for replication.

🎓 Past Exam Questions

2025 Exam — Q1: HDFS Read Process (8 marks)

▼
Question: Describe the HDFS file read process step-by-step. For each step, explain what design decision was made and why.
Model Answer:

Step 1 — Client requests file from NameNode (1 mark): Client sends filename to NameNode. Design decision: only one request to NameNode because the NameNode is a singleton and a bottleneck — minimise contact.

Step 2 — NameNode returns BlockIDs + DataNode list (2 marks): NameNode responds with all BlockIDs and which DataNodes hold each replica. Again, NameNode returns all info in one response, not one per block.

Step 3 — Client reads blocks directly from DataNodes (3 marks): Client contacts DataNodes directly, bypassing NameNode for data transfer. Selects the closest DataNode per block using Rack Awareness (network topology). Reads incrementally block-by-block. Design decision: avoid overloading NameNode with data traffic; exploit data locality for lower latency.

Rack Awareness (2 marks): Rack structure is manually configured in HDFS. Client picks the DataNode in the same rack/nearest switch. Alternative options discussed: contact all replicas (fastest but wasteful), random (load balanced), least-loaded (requires tracking load).

2025 Exam — Q2: HDFS Write Pipeline (6 marks)

▼
Question: Explain how the HDFS write pipeline works and what design decisions went into its design.
Model Answer:

Step 1 — Register block with NameNode (1 mark): Client calls addBlock(src) on NameNode, which returns a pipeline of DataNodes (e.g. DN1→DN2→DN3) to hold replicas.

Step 2 — Pipeline write with packet buffering (2 marks): Client buffers data, sends 64KB packets into pipeline. DN1 writes locally and forwards packet to DN2, which writes and forwards to DN3 (pipelining). Multiple packets can be in-flight simultaneously (sliding window).

Step 3 — Block reports to NameNode (1 mark): Each DataNode reports received blocks directly to NameNode when complete.

Design decisions (2 marks): (1) Client sends data only once — avoids saturating client network. (2) Pipelining — maximise throughput. (3) DataNodes report to NameNode directly — reduces NameNode load. Alternatives: broadcast to all DNs simultaneously (fast but saturates client), serial writes (slow).

2023 Exam — Q3: NFS vs HDFS (10 marks)

▼
Question: Compare and contrast NFS and HDFS as distributed file systems for Big Data applications. Include architecture, fault tolerance, scalability, and suitability.
Model Answer (key points):

Architecture (3 marks): NFS uses client-server with one server; clients mount a directory. HDFS uses NameNode (metadata master) + multiple DataNodes (data storage). HDFS separates metadata from data — NameNode in RAM, DataNodes store 128MB blocks.

Fault Tolerance (3 marks): NFS has no native replication — server is SPOF; relies on RAID. HDFS provides 3× replication by default, across racks. Block recovery and pipeline recovery mechanisms handle DataNode failures automatically. NameNode has checkpoint + WAL for recovery.

Scalability (2 marks): NFS doesn't scale well — all data through one server. HDFS scales horizontally — add DataNodes for both storage and throughput. Data locality: schedule Hadoop tasks close to blocks.

Suitability (2 marks): NFS: good for small files, general-purpose shared storage. HDFS: designed for large files (100s MB–TB), write-once-read-many batch workloads, Big Data analytics. HDFS's large block size (128MB) unsuitable for many small files.

2023 Exam — Q4: RAID Levels (6 marks)

▼
Question: Explain RAID 0, RAID 1, RAID 5, and RAID 6. Which would you recommend for a production database server and why?
Model Answer:

RAID 0 (1 mark): Striping only. Best performance (reads spread across drives) but zero redundancy — any single drive failure loses all data. Not suitable for production.

RAID 1 (1 mark): Mirroring. Full duplicate of each drive. Good redundancy, fast reads. 50% capacity overhead.

RAID 5 (2 marks): Block-level striping with distributed parity (using XOR). Survives 1 disk failure. Parity distributed across all drives — no single bottleneck. Efficient (only 1/n overhead). Most popular for storage.

RAID 6 (2 marks): Like RAID 5 but double parity. Survives 2 simultaneous disk failures. Better suited for large arrays (higher chance of concurrent failures during rebuild). Recommended for production: RAID 6 (high fault tolerance) or RAID 10 (RAID 1+0: mirroring + striping — best performance + redundancy if cost allows).

2022 Exam — Q2: Block Recovery (5 marks)

▼
Question: What is a lease in HDFS? What happens when a lease expires during a write operation? Describe Block Recovery.
Model Answer:

Lease (1 mark): A lease is a time-limited write permission granted by the NameNode's Lease Manager. Unlike NFS locks (indefinite), HDFS leases expire after a timeout or when the file is closed, preventing indefinitely blocked files if a client crashes.

Lease expiry (2 marks): If no renewal by deadline → NameNode marks it expired → triggers Lease Recovery. If no write was in progress: simply closes the file. If write was in progress → triggers Block Recovery.

Block Recovery (2 marks): (1) Client unavailable → can't finalize block. (2) NameNode appoints a Block Recovery Primary DataNode from the pipeline. (3) Primary queries all DataNodes in pipeline for their block status (RBW/RWR). (4) Primary generates a new file length and syncs with a new generation stamp. (5) Block finalized → NameNode notified.

📝 Practice Questions

Q1: Why does HDFS use 128MB blocks instead of typical 4KB OS blocks?▼

Large blocks reduce NameNode memory pressure: Each block requires metadata in the NameNode. With 128MB blocks, a 1TB file = only ~8,000 blocks. With 4KB blocks = ~250 million blocks → NameNode RAM exhausted.

Optimised for sequential reads: Big Data workloads read entire files sequentially, not random small reads. Large blocks reduce the number of disk seeks.

Reduces NameNode load: Fewer blocks = fewer metadata lookups per file read.

Trade-off: Poor for small files — a 1KB file still occupies a full 128MB block (or at least one block entry). Many small files = "small files problem" in Hadoop.

Q2: A 500MB file is stored in HDFS with block size 128MB and replication factor 3. How many blocks are created? How many DataNode block copies exist?▼

Number of blocks: \(\lceil 500/128 \rceil = 4\) blocks (Block 1–3: 128MB each, Block 4: 500 - 3×128 = 116MB)

Total block copies: 4 blocks × 3 replicas = 12 DataNode copies total

Total storage consumed: 3 × 500MB = 1.5GB (3× replication overhead)

NameNode metadata: Stores info for 4 blocks, their locations across DataNodes, checksums, generation stamps.

Q3: Why does HDFS use a "write pipeline" rather than the client broadcasting to all DataNodes simultaneously?▼

Avoid saturating client's network connection: If client broadcasted 128MB to 3 DataNodes simultaneously, it needs 3× the upload bandwidth. In a cluster, the client (Hadoop job tracker) would become a bottleneck.

Pipeline distributes the load: Client sends data once to DN1 (uses client's outgoing bandwidth once). DN1 forwards to DN2 (uses DN1's bandwidth). DN2 forwards to DN3. Each node only uses its own bandwidth in one direction.

Pipelining allows parallelism: While DN1 is writing packet N, it forwards packet N-1 to DN2, which forwards N-2 to DN3 — all happening simultaneously.

Alternative: lazy replication (send to 1 then idle forward) is too slow — delay before all replicas are available affects read availability.

Q4: Explain the difference between Block Recovery and Pipeline Recovery in HDFS.▼

Block Recovery — triggered when the client fails (lease expires):

  • Client is dead; can't finalize the block being written
  • NameNode appoints a Block Recovery Primary DataNode
  • Primary queries pipeline DataNodes for their partial block states
  • Generates new file-length + generation stamp; all DataNodes sync and finalize
  • Goal: produce a consistent, finalized block despite client failure

Pipeline Recovery — triggered when a DataNode in the pipeline fails:

  • Client is alive; DataNode in pipeline dies
  • Failed DataNode cuts TCP/IP connection (self-detects failure)
  • Client detects missing DataNode, stops sending data
  • Client reconstructs pipeline using remaining DataNodes and continues write
  • Goal: continue the write with fewer replicas (NameNode re-replicates later)
