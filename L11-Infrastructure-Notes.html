Caching Statistics (Baeza-Yates, SIGIR 2007)

~50%
of query result requests can be served from a query result cache ("head queries")
~88%

Source: Baeza-Yates et al. SIGIR 2007. These statistics show that caching is extremely effective because query distributions are highly skewed (Zipf's law) — a small number of "head" queries account for the majority of traffic.

Query Result Cache

Store top-k search results for frequent queries. Hit = return cached results instantly, avoiding all index traversal.

Cache Hit Rate
\[ \text{Hit Rate} = \frac{\text{# requests served from cache}}{\text{total requests}} \]
🔶 Practice

A cache with 10k entries handles 1M queries/day. 300k queries are served from cache. What is the hit rate?

✅ Solved

Hit Rate = 300,000 / 1,000,000 = 30%. Interpretation: 30% of queries avoid full index traversal, reducing average latency and CPU load significantly.

Posting List Cache

Cache frequently accessed posting lists (e.g., "london", "price", "the") in RAM to avoid disk I/O. Term-level caching complements query-level caching. ~88% of posting list reads can be served from cache (Baeza-Yates 2007).

Paired Posting Lists — Phrase Caching

For common multi-word phrases, cache the merged posting list. Example: "white house rose garden"

Worked Example: Phrase Query Cache Entry

Cached posting list for "white house rose garden" (positional format):

id=0, pf=2  → Document 0 contains the phrase at position 2
id=3, pf=0  → Document 3 contains the phrase at position 0
id=5, pf=0  → Document 5 contains the phrase at position 0
id=6, pf=1  → Document 6 contains the phrase at position 1

Benefit: instead of intersecting 4 separate posting lists and checking positions (expensive), the merged cache entry gives direct document matches for repeated phrase queries.

3. Query Processing: TAAT vs DAAT

Multi-Term Query Processing Strategies

A multi-term query like "fast food restaurant" has a posting list per term. How do you combine them to score documents?

TAAT — Term At A Time

Process one term completely before moving to the next. Maintain a global accumulator array (partial scores for all documents seen so far).

Algorithm

  1. Initialise accumulator A[d] = 0 for all d
  2. For each query term t:
      For each (docid, score) in posting(t):
        A[docid] += score(t, docid)
  3. Return top-K documents by A[d]

⚠️ TAAT Disadvantage

Must maintain partial scores for ALL documents encountered across any term. Memory proportional to number of unique documents in all posting lists. For common terms, this can be enormous.

DAAT — Document At A Time

Process all posting lists simultaneously, advancing a pointer to the same document across all lists. Score documents one at a time.

Algorithm

  1. Open a cursor on each term's posting list
  2. Find the minimum current docid across all cursors
  3. Score that document using contributions from all matching terms
  4. Advance all cursors pointing to that docid
  5. Maintain a top-K heap; update if score qualifies
  6. Repeat until all cursors exhausted

DAAT Advantage

Only maintain top-K scores — constant memory regardless of corpus size. Naturally supports dynamic pruning (WAND/MaxScore) by skipping documents that can't enter top-K.

TAAT Full Worked Example

Query: "cat dog". Posting lists (docid: score):
"cat": [(1:3), (2:5), (4:2), (7:1)]
"dog": [(2:4), (3:2), (4:3), (7:2)]

✅ TAAT Processing

After processing "cat":
A[1]=3, A[2]=5, A[4]=2, A[7]=1

After processing "dog":
A[2] += 4 → A[2]=9
A[3] += 2 → A[3]=2
A[4] += 3 → A[4]=5
A[7] += 2 → A[7]=3

Final accumulators: A[1]=3, A[2]=9, A[3]=2, A[4]=5, A[7]=3
Top-2: doc2 (9), doc4 (5)

Note: accumulator A[1] and A[3] must be stored even though only one term matched them — this is the memory cost.

DAAT Full Worked Example

Same query. Cursors start at beginning of each list.

✅ DAAT Processing

Current: cat→(1:3), dog→(2:4). Min docid = 1 (only cat). Score(1) = 3. Advance cat.
Current: cat→(2:5), dog→(2:4). Min docid = 2 (both). Score(2) = 5+4 = 9. Advance both.
Current: cat→(4:2), dog→(3:2). Min docid = 3 (only dog). Score(3) = 2. Advance dog.
Current: cat→(4:2), dog→(4:3). Min docid = 4 (both). Score(4) = 2+3 = 5. Advance both.
Current: cat→(7:1), dog→(7:2). Min docid = 7 (both). Score(7) = 1+2 = 3. Advance both.
All cursors exhausted. Top-2: doc2 (9), doc4 (5). ✓ Same result as TAAT.

Key difference: only ever needed current top-2 heap in memory — no full accumulator array.

4. Index Pruning: WAND, MaxScore, BMW

4.1 Static Pruning

Remove postings at index build time. Reduces index size and speeds up traversal.

  • Term-level: Keep only top-N docs per term (by TF or BM25 score)
  • Document-level: Remove postings from very long documents

4.2 Dynamic Pruning — MaxScore

MaxScore pre-computes an upper bound UB for each term's contribution to any document score. It splits query terms into essential and non-essential sets:

Essential Terms

A term t is essential if: without it (i.e., removing its UB from the total), the remaining terms' UBs still exceed the current threshold θ. Essential terms must be processed. Non-essential terms can be skipped unless they appear with essential terms.

MaxScore Pruning Condition
\[ \text{If} \sum_{t \in \text{remaining terms}} UB_t < \theta \Rightarrow \text{PRUNE (skip document)} \]

θ = current K-th best score. UB_t = maximum possible contribution of term t to any document.

🔶 MaxScore Full Worked Example

Query: "cat dog fish". Upper bounds: UB(cat)=4, UB(dog)=1. Current threshold θ=4.5.
Processing in DAAT order, current candidates: docid=21, docid=25.

✅ Solution

For docid=21: Only "cat" matches. Max possible score = UB(cat) + UB(dog) = 4 + 1 = 5. But wait — docid 21 is NOT in dog's posting list, so actual max = UB(cat) = 4 < θ=4.5. → PRUNE docid 21

For docid=25: Only "dog" matches. Max possible = UB(cat) + UB(dog) = 4 + 1 = 5. Docid 25 not in cat's list, so actual max = UB(dog) = 1 < θ=4.5. → PRUNE docid 25

Both documents pruned without computing exact scores — they cannot possibly beat the current top-K. This is the MaxScore "essential term" optimisation.

4.3 WAND (Weak AND) — Essential Term Skip Logic

WAND uses a pivot-based approach to skip documents. The key "essential term" concept:

WAND Skip Logic

  1. Sort posting list cursors by current docid
  2. Try to find the leftmost "pivot" term p such that sum of UBs from p to last term ≥ θ
  3. If all cursors for terms left of pivot point to a docid < pivot's current docid → skip ahead
  4. Otherwise evaluate the document
WAND Upper Bound Condition
\[ \text{Score}_{UB}(d) = \sum_{t \in q,\, t \in d} UB_t \geq \theta \Rightarrow \text{Evaluate document d} \]
🔶 Practice

Query: terms A, B, C with UB_A=5, UB_B=3, UB_C=2. θ=8. Document has terms A and C. Skip or evaluate?

✅ Solved

UB score = UB_A + UB_C = 5 + 2 = 7 < θ=8 → SKIP. Cannot possibly enter top-K.

Tonellotto et al. SIGIR 2011 — Pruning Performance

Empirical comparison on a large web index:

AlgorithmAvg. Query Time% Postings Evaluated
Exhaustive (full DAAT)1.36s100%
MaxScore1.24s43%
WAND0.96s10.8%

Key finding: WAND evaluates only 10.8% of all postings but returns exactly the same top-K results. This ~10× reduction in work explains the significant speedup over exhaustive evaluation.

4.4 BMW (Block-Max WAND)

Extends WAND: each posting list is divided into blocks with per-block maximum scores stored. Allows skipping entire blocks (not just documents) → typically 3–5× faster than standard WAND.

5. Index Compression

An inverted index stores (docID, tf) pairs for each term. Efficient compression reduces storage and I/O bandwidth — critical for in-memory and disk-based indexes.

5.1 D-Gap (Delta) Encoding

Store differences between consecutive sorted docIDs instead of absolute values. Small gaps → better compression with variable-length codes.

D-Gap Encoding
\[ \delta_i = d_i - d_{i-1} \quad (d_0 = 0) \]
🔶 Practice

DocID sequence: [5, 12, 15, 30, 31]. Compute d-gaps.

✅ Solved

δ = [5, 7, 3, 15, 1]. Original max = 31 (5 bits each); d-gap max = 15 (4 bits). Small values compress better with variable-length codes.

5.2 Elias Unary Code

The simplest variable-length code. Encodes integer x as: x−1 zeros followed by a 1.

Unary coding uses x bits for value x. Optimal only for very small integers (x ≤ 2–3). Used as a component in Elias Gamma coding.

5.3 Elias Gamma (γ) Code

Encodes an integer x using two parts:
1. Unary component: N = ⌊log₂ x⌋ zeros followed by a 1 (N+1 bits total)
2. Binary remainder: x − 2N in binary using N bits

Elias γ Encoding
\[ N = \lfloor \log_2 x \rfloor \quad \text{Bits} = 2N + 1 \]

Unary part: (N zeros + 1) = N+1 bits. Binary remainder: (x − 2^N) in N bits.

🔶 Full Encoding Worked Example

Given d-gaps [1, 5, 3, 9, 2, 4], encode each with Elias γ and count total bits. Compare with original 24 bytes (8 gaps × 3 bytes).

✅ Solution

1 → 1 bit (code: 1)
5 → 5 bits (N=2: code: 00101)
3 → 3 bits (N=1: code: 011)
9 → 7 bits (N=3: code: 0001001)
2 → 3 bits (N=1: code: 010)
4 → 5 bits (N=2: code: 00100)

Total = 1+5+3+7+3+5 = 24 bits vs original 24 bytes = 192 bits → 8× compression

🔶 Practice: Encode term4

Posting list for term4 has d-gaps: [6, 3, 1, 15, 2]. Encode each with Elias γ. How many total bits?

✅ Solution

6: N=⌊log₂6⌋=2, code=00110, 5 bits
3: N=1, code=011, 3 bits
1: N=0, code=1, 1 bit
15: N=⌊log₂15⌋=3, code=0001111, 7 bits
2: N=1, code=010, 3 bits
Total = 5+3+1+7+3 = 19 bits

5.4 Variable Byte (VByte) Encoding

Use 7 bits per byte for data, 1 bit as continuation flag. Values ≤127 need 1 byte; ≤16383 need 2 bytes.

VByte: bytes needed
\[ \text{bytes}(n) = \lceil \log_{128}(n+1) \rceil \]
🔶 Practice

Encode d-gaps [5, 7, 3, 15, 1] in VByte. Total bytes?

✅ Solved

All ≤ 127 → each takes 1 byte. Total: 5 bytes. Original 32-bit ints: 20 bytes → 4× compression.

5.5 Frame of Reference (FOR) Compression

FOR compresses blocks of integers by storing only the reference frame (minimum value m) and each value as its offset from m. All offsets use a fixed b bits where b = ⌈log₂(M − m + 1)⌉.

FOR Bit Width
\[ b = \lceil \log_2(M - m + 1) \rceil \]

M = maximum value in block, m = minimum value. Store: m (full int) + all offsets as b-bit values.

🔶 FOR Example

Block of docIDs: {2000, 2003, 2010, 2015, 2020, 2025, 2050, 2063}. Compute b and total bits for 8 values.

✅ Solution

m = 2000, M = 2063. Range = 2063 − 2000 + 1 = 64. b = ⌈log₂ 64⌉ = 6 bits.
Offsets: {0, 3, 10, 15, 20, 25, 50, 63} — each stored in 6 bits.
Total bits: 32 (store m=2000) + 8×6 = 32 + 48 = 80 bits for 8 values (vs 256 bits raw).
Compression ratio: 256/80 = 3.2×

⚠️ FOR vs PForDelta

FOR requires ALL values to fit in b bits — one outlier inflates b for the whole block. PForDelta (Patched FOR) handles exceptions separately, using a small exception list for ~10% of values that don't fit b bits. This gives better compression for blocks with occasional large gaps.

Key Catena Finding

Compression is not just about ratio — decompression speed is equally critical. At query time, millions of postings must be decoded per second. SIMD-capable methods (PForDelta, FOR) dominate because they decode 4–32 values per CPU instruction.

6. Distributed Retrieval

Vertical vs Horizontal Scaling

Vertical Scaling (Scale Up)

Add more resources to a single machine: more RAM, faster CPU, more cores, larger SSD. Simple — no distributed coordination overhead. Limited by physical hardware ceiling. Used first because it's easier.

Horizontal Scaling (Scale Out)

Add more machines to the cluster. Distribute the index across N machines (sharding). Supports arbitrary scale but requires coordination: distributed IDF, result aggregation, network overhead. Required for web-scale (billions of docs).

Term Partitioning vs Document Partitioning

⚠️ Term Partitioning

Each machine handles a subset of terms. Machine 1: terms A–M. Machine 2: terms N–Z.

Problem: A multi-term query must contact ALL machines (a query for "cat dog" needs both machines). Results must be collected like TAAT — every machine processes every document for its terms. Rarely used in practice for this reason.

Document Partitioning (Preferred)

Each machine holds a complete inverted index for a subset of documents. Machine 1: docs 1–N/k. Machine 2: docs N/k+1 to 2N/k.

Each machine processes the full query independently and returns its top-K. A broker aggregates results into the global top-K. This is the dominant approach in production systems.

Document Partitioning Strategies

StrategyHowProsCons
RandomAssign docs by docID mod NUniform load, simple IDF estimationNo semantic locality
SemanticGroup similar topic documentsEnables selective search — route query to relevant shardsLoad imbalance, complex assignment
LanguageGroup by document languageNatural for multilingual searchCross-language queries harder
Query-log-basedPlace docs near queries that retrieve themCan reduce cross-shard communicationRequires historical query data

⚠️ Term Partitioning: Rarely Used in Practice

Every query must collect partial scores from ALL machines (one per term in the query). This is equivalent to TAAT distributed — requires aggregating partial accumulators across the network. Network overhead and synchronisation costs make this impractical at scale.

6.1 Document Sharding & Distributed IDF

Distributed IDF Estimation
\[ \text{IDF}(t) = \log \frac{N_{\text{global}}}{\sum_{i=1}^{k} \text{df}_i(t)} \]
🔶 Practice

3 shards, each 1M docs. "retrieval": df=500 (shard 1), 300 (shard 2), 200 (shard 3). Global IDF?

✅ Solved

N=3M, df=1000. IDF = log(3,000,000/1000) = log(3000) ≈ 8.006 (natural log)

6.2 Resource Selection: CORI and ReDDE

Resource selection decides which shards to query for a given query, rather than broadcasting to all. Reduces cost and latency for selective search.

CORI

Collection Retrieval and Inference. Models each shard as a document and scores shards using TF-IDF of query terms. High CORI score = shard likely contains relevant results. Select top-k shards by CORI score.

ReDDE

Relevant Document Distribution Estimation. Estimates the number of relevant documents each shard would contribute to the global top-K. Uses a sampled "central sample index" to estimate shard relevance without querying each shard.

6.3 Selective Search

Route each query to only the most relevant shards (selected by CORI or ReDDE) rather than all shards. Typically query 2–3 shards out of 10–20.

Trade-off

  • Benefit: Proportional reduction in latency and cost — 3 shards out of 10 = ~70% cost reduction
  • Risk: May miss relevant documents in unqueried shards → potential recall loss
  • Best for: Head queries where relevant documents are concentrated in a few shards
  • Worst for: Rare queries where relevant documents are scattered

7. Tiered Indexes & Further Optimisations

Tiered Index Architecture

Split index into tiers based on document quality/importance:

  1. Tier 1: High-quality documents (high PageRank, frequently clicked). Very small — try here first.
  2. Tier 2: Medium quality. Query if Tier 1 has insufficient results.
  3. Tier 3: Long tail. Rarely queried — only for specific/rare queries.

Impact-Ordered Index

Sort postings within each posting list by decreasing impact (TF-IDF or BM25 contribution), not by docID. Early termination achieves high precision by scoring only top-impact entries — process first P% of postings and stop.

Index Freshness

  • Batch re-indexing: Periodic full rebuild — simple but stale index
  • Incremental indexing: Merge small "delta" indexes into main index continuously
  • Real-time indexing: Documents immediately searchable — complex but fresh (used by Elasticsearch)

8. Query Efficiency Prediction (QEP)

Query Efficiency Prediction (QEP)

Predict — at query time, before executing the query — how much computational cost (CPU time, memory, evaluated postings) this query will require. Used to adaptively allocate resources per query rather than using fixed settings.

What QEP Depends On

Macdonald, Tonellotto & Ounis (SIGIR 2012) showed QEP models depend on four key factors:

Query-level factors

  • Query length: More terms = more posting lists = more work
  • Posting list length: Total number of postings across all query terms — longer lists = more candidates to process

Execution-level factors

  • Pruning rate: What fraction of postings will be skipped by WAND/MaxScore — hard to know without executing (hence "prediction")
  • K: Number of results requested — larger K = stricter threshold needed, more postings evaluated

QEP Applications

Query Scheduling

Predicted-expensive queries are queued during peak load; cheap queries execute immediately. Prevents a single hard query from blocking the queue. Similar to CPU job scheduling.

Adjusting K

Reduce K for predicted-expensive queries. E.g., retrieve top-10 instead of top-100 to reduce threshold computation. Quality impact is minimal for most queries.

Selective Parallelisation

Allocate more parallel threads/shards to expensive queries; process cheap queries on a single thread. Avoids over-provisioning for simple queries.

QEP Impact at Bing Scale

1/3
of production servers saved by QEP at Bing
("saves one-third of production servers" across "a few hundred thousand query servers")

Source: Macdonald, Tonellotto & Ounis, SIGIR 2012. This is one of the most dramatic examples of an academic IR technique having direct production impact.

Interpretation

At Bing's scale of hundreds of thousands of servers, saving 1/3 of servers through smarter query resource allocation means enormous cost savings. QEP enables the system to handle the same query load with 33% fewer machines by intelligently routing query costs.

QEP Model Design

A QEP model is a regression model predicting query cost:

QEP Regression
\[ \hat{C}(q) = f(\text{query length}, \sum_t |\text{posting}(t)|, \hat{P}_{\text{prune}}, K) \]

Features extracted at query time without executing. Model trained on historical (query, observed cost) pairs.

⚠️ Chicken-and-Egg Problem

The best feature for predicting cost is the pruning rate — but you only know the pruning rate after executing the query. QEP uses proxy features (posting list lengths, upper bound distributions) to estimate it before execution.

9. Green IR

Green IR

The study and practice of reducing the energy consumption and environmental impact of information retrieval systems while maintaining acceptable quality. Motivated by the enormous energy footprint of large-scale search engines.

Energy Context

~8.5B

⚠️ Neural IR's Energy Problem

Neural ranking models (BERT-based cross-encoders, large LMs) are dramatically more expensive than BM25. A single BERT inference may use 100–1000× more energy than a BM25 score. At web scale, deploying these models naively is environmentally unsustainable. This motivates cascade architectures (cheap BM25 first, expensive neural re-ranking on small set) and efficient models (ColBERT, SPLADE).

Green IR Principles

  • Cascade retrieval: Use cheap model (BM25) to generate candidates, apply expensive model (BERT) only to top-N
  • Early termination: WAND/MaxScore/BMW reduce postings evaluated → less CPU → less energy
  • QEP-based allocation: Don't over-provision — use resources proportional to query difficulty
  • Model compression: Smaller, quantised neural models (TinyBERT, DistilBERT) sacrifice small quality for large energy savings
  • Caching: Cached results require zero computation energy

10. Summary

Business Impact & Motivation

0.5s delay → Yahoo −20% traffic, Bing −12% revenue/user, Google −20% searches. 1% latency = ~1,000 extra Bing servers. Every millisecond matters at scale.

Caching

50% of query results cacheable (head queries); 88% of posting list accesses cacheable (Baeza-Yates SIGIR 2007). Zipf distribution of query frequency makes caching highly effective. Policies: LRU/LFU/Static.

TAAT vs DAAT

TAAT: one full term at a time, needs O(N) accumulator memory. DAAT: all terms simultaneously, O(K) heap memory, supports dynamic pruning. DAAT is industry standard.

Dynamic Pruning

MaxScore: essential/non-essential term split, prune if remaining UBs < θ. WAND: pivot-based, evaluates only 10.8% of postings (Tonellotto SIGIR 2011, vs 100% exhaustive). BMW: per-block maxima for block-level skipping.

Compression

D-gaps + coding: Elias Unary (x bits for value x), Elias γ (2⌊log₂x⌋+1 bits), VByte (7 data + 1 flag bits per byte), FOR (b=⌈log₂(M−m+1)⌉ bits per block), PForDelta (SIMD, industry standard). Catena ECIR 2014: decompression speed equally important as compression ratio.

Distributed Retrieval

Document partitioning preferred (term partitioning requires TAAT-like full collection traversal). Strategies: random/semantic/language/query-log. Resource selection (CORI, ReDDE) enables selective search. Vertical then horizontal scaling.

Query Efficiency Prediction

QEP predicts query cost from: query length, posting list lengths, estimated pruning rate, K. Applications: scheduling, adjusting K, selective parallelisation. Impact: saves 1/3 of Bing production servers (Macdonald/Tonellotto/Ounis SIGIR 2012) across hundreds of thousands of servers.

Green IR

1 KJ per search, 1.1–1.5% global electricity. Neural models are 100–1000× more expensive than BM25. Mitigations: cascade architectures, dynamic pruning, QEP, model compression, caching.

Exam-Style Questions
H/M[10 marks]
Q1. (a) Explain the difference between TAAT and DAAT query processing. Include the memory requirements of each. [4] (b) Explain MaxScore dynamic pruning: define essential/non-essential terms, the pruning condition, and show a worked numerical example with 3 query terms. [6]
(a) TAAT (Term At A Time): process one posting list fully before moving to next. Maintains accumulator A[d] for all documents encountered — memory O(N) proportional to documents in all posting lists. DAAT (Document At A Time): advance cursors across all posting lists simultaneously. Maintains only top-K heap — memory O(K). DAAT supports dynamic pruning (WAND, MaxScore) naturally because all information about a document is collected before scoring it. TAAT is awkward to prune because partial scores are accumulated across terms. [4]

(b) MaxScore: pre-compute upper bound UB_t for each query term t = maximum BM25/score contribution to any document. Partition terms into essential (must process) and non-essential (can skip unless co-occurring with essential terms). Essential term t: if you remove t's UB from the sum, remaining UBs < θ (meaning t is needed for any document to potentially enter top-K). Pruning condition: for candidate document d, if sum of UBs of terms occurring in d < θ → PRUNE. Example: terms A(UB=4), B(UB=1), θ=4.5. Document docid=21 contains only A: max possible score = UB(A) = 4 < θ=4.5 → PRUNE. Document contains only B: UB(B)=1 < 4.5 → PRUNE. Only documents with UBs summing ≥ 4.5 need full evaluation. [6]
H/M[10 marks]
Q2. (a) Describe Elias Gamma (γ) coding. Write the encoding formula and show how to encode x=5 and x=12. [4] (b) Describe Frame of Reference (FOR) compression: the bit width formula, a full example, and compare to PForDelta. [4] (c) Why is decompression speed equally important as compression ratio for inverted indexes? [2]
(a) Elias γ: N=⌊log₂x⌋. Code = N zeros + 1 (unary, N+1 bits) + (x−2^N) in binary (N bits). Total bits = 2N+1.
x=5: N=⌊log₂5⌋=2, code = 001 (unary, 3 bits) + 01 (binary: 5−4=1, 2 bits) = 00101 (5 bits).
x=12: N=⌊log₂12⌋=3, code = 0001 (unary, 4 bits) + 100 (binary: 12−8=4, 3 bits) = 0001100 (7 bits). [4]

(b) FOR: given a block of integers, m=min, M=max. b=⌈log₂(M−m+1)⌉ bits per value. Store m as full 32-bit int, then each value as (value−m) in b bits. Example: block {2000,2010,2015,2063}: m=2000, M=2063, range=64, b=⌈log₂64⌉=6. Offsets: {0,10,15,63} each in 6 bits. PForDelta: extends FOR by handling outliers (≥90% of values use b bits; exceptions stored in separate list). Better for blocks with irregular large gaps. [4]

(c) At query time, millions of postings per second must be decoded. If decompression is slow, it becomes the bottleneck even if compression achieves great ratios. PForDelta uses SIMD CPU instructions to decode 32+ values per instruction — this matters more than saving a few bits when you're decoding billions of postings per second. [2]
H/M[8 marks]
Q3. (a) Define Query Efficiency Prediction (QEP) and list the four key factors it depends on. [3] (b) Describe three applications of QEP in a production search engine. [3] (c) State the key finding of Macdonald, Tonellotto and Ounis (SIGIR 2012) regarding QEP's impact at Bing. Why is this significant? [2]
(a) QEP predicts query computational cost before executing the query, allowing adaptive resource allocation. Four factors: (1) Query length — more terms = more work; (2) Posting list length — sum of DF across query terms; (3) Pruning rate — estimated fraction of postings that will be skipped by WAND/MaxScore (hard to know pre-execution, need proxy estimates); (4) K — number of requested results, affects threshold and thus pruning. [3]

(b) Three applications: (1) Query scheduling — route expensive queries to off-peak slots or lower-priority queues; cheap queries execute immediately, preventing head-of-line blocking. (2) Adjusting K — reduce top-K for predicted-expensive queries (e.g., top-10 instead of top-100) to raise the threshold and allow more pruning. (3) Selective parallelisation — allocate extra CPU threads/shards to expensive queries; run cheap queries on a single thread to avoid overhead. [3]

(c) Finding: QEP "saves one-third of production servers" across "a few hundred thousand query servers" at Bing. Significant because: at Bing's scale, saving 33% of hundreds of thousands of servers means enormous hardware and energy cost reduction — potentially hundreds of millions of dollars. This is a direct translation of an academic IR technique into real-world infrastructure savings. [2]
H[8 marks]
Q4. A search engine has a 5-billion document corpus distributed across 10 machines. (a) Compare term partitioning and document partitioning for this setup, including why term partitioning is rarely used. [4] (b) Describe selective search: how it works, the resource selection models used, and the quality/cost trade-off. [4]
(a) Term partitioning: machine 1 handles terms A-M, machine 2 handles N-Z. Problem: every multi-term query must contact ALL machines to collect contributions from each term. Result aggregation is like TAAT across machines — requires collecting partial accumulators from all shards, merging over network. Network latency and synchronisation overhead make this very slow. Every query is a fan-out to all machines regardless of content. Rarely used. Document partitioning (preferred): each machine holds complete index for 500M documents. Each machine executes the full query independently and returns local top-K. Broker aggregates N local top-K lists into global top-K. Only K results per machine sent over network — efficient. [4]

(b) Selective search: rather than broadcasting every query to all 10 shards, route each query to the K most relevant shards (K < 10). Resource selection models: CORI — models each shard as a document, scores shards with TF-IDF of query terms, selects top-k shards. ReDDE — estimates expected number of relevant documents per shard using a central sample index, selects shards expected to contribute most to global top-K. Trade-off: querying 3/10 shards reduces cost/latency by ~70%, but risks missing relevant docs in unqueried shards. Head queries (concentrated relevant documents) benefit most; rare/diverse queries may suffer recall loss. [4]

Evaluates only 10.8% of postings. Same top-K as exhaustive (1.36s → 0.96s). Safe: UB check before evaluation.

Doc: each shard has full index for subset of docs. Preferred. Term: each shard has all docs for subset of terms — must contact all shards per query. Rarely used.
