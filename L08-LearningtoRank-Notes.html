Generative vs Discriminative Models

Generative Models (BM25, LM, DFR)

  • Assume documents were "generated" from an underlying statistical model
  • Estimate P(document|class) using Bayes' Rule
  • Work well with small training data
  • Strong theoretical foundations
  • Examples: BIM, BM25, Query Likelihood, DFR/PL2
  • Interpretable: each component has a clear meaning

Discriminative Models (LTR)

  • Directly estimate P(relevance|features) from training data
  • Can incorporate many diverse features
  • Usually outperform generative models with enough data
  • Require large training datasets (e.g., click logs, LETOR)
  • Examples: RankSVM, LambdaMART, Neural Rankers
  • Less interpretable but more flexible

Why LTR? Motivation

Generative models like BM25 use only a handful of carefully designed features (TF, IDF, length). In practice, hundreds of signals exist: PageRank, anchor text, query-click history, proximity scores for different fields, etc. LTR can combine all these signals optimally from training data — this is fundamentally beyond what a hand-crafted formula can do.

Features for Learning to Rank

Feature Categories

Query-Dependent (QD)

Depend on both query AND document: BM25 score (body, title, anchor, URL), TF-IDF, PL2, BM25F, cosine similarity, proximity scores, deep learned semantic matching (e.g., BERT score)

Query-Independent (QI)

Depend only on document: PageRank, number of inlinks, spamminess score, document age, URL depth, page length, readability score

Query Features (Q)

Depend only on query: query length (number of terms), presence of named entities, query type classification (navigational, informational, transactional)

Typical Feature Set (Web LTR — hundreds of features)

BM25-based features (per field):

  • BM25 on body text
  • BM25 on title field
  • BM25 on anchor text
  • BM25 on URL
  • BM25F (combined field BM25)

Other retrieval features:

  • PL2 on body/title
  • TF-IDF variants
  • Language model scores (Dirichlet, JM)
  • Proximity / MRF scores
  • Semantic similarity (embedding-based)

Graph/structural features:

  • PageRank
  • In-degree (number of inlinks)
  • HITS hub/authority scores
  • URL depth, number of slashes

Click/behavioural features:

  • CTR (click-through rate) for (query, doc) pair
  • Dwell time on page after click
  • Skip rate (user skipped without clicking)
  • Query reformulation rate after viewing

Ranking Cascade (Web-Scale Search)

Training Data for LTR NEW

Types of Training Data

Explicit Relevance Judgments

Human assessors rate (query, document) pairs on a relevance scale. Examples: TREC ad-hoc tracks, LETOR benchmark datasets. High quality but expensive — limited scale.

Implicit Signals (Click-Through)

User clicks, dwell time, skip rates collected from search logs. Very large scale (billions of interactions at Google/Bing) but noisy — clicks ≠ relevance. Subject to position bias (top results clicked more regardless of relevance).

Key LTR Benchmark Datasets

LETOR (Learning to Rank)

Classic benchmark from Microsoft Research. Multiple datasets (LETOR 3.0, 4.0). ~46 features per (query,doc) pair. OHSUMED, MQ2007, MQ2008 subsets. Up to ~100K query-document pairs.

MS MARCO

Microsoft Machine Reading Comprehension dataset — repurposed for passage and document retrieval. ~1M queries, real Bing queries. Sparse relevance judgments (from click data). Standard benchmark since 2016.

TREC Deep Learning

TREC 2019–2023 Deep Learning tracks. Built on MS MARCO but with dense relevance judgments (NIST assessors). Standard for evaluating both classical and neural LTR models.

Position Bias in Click Data

Users are more likely to click on highly-ranked results simply because they appear near the top — independent of true relevance. This creates a feedback loop: biased training data → biased model → documents ranked at top → more clicks → more bias. Solutions:

  • Inverse Propensity Scoring (IPS): down-weight clicks on top positions, up-weight clicks on lower positions
  • Randomisation: occasionally randomise result order to collect unbiased data (costly)
  • Unbiased LTR: jointly learn relevance model and propensity (position bias) model

Pointwise Learning to Rank EXPANDED

Pointwise LTR

Treat ranking as a regression or classification problem on individual (query, document) pairs. Each pair is treated independently — predict a relevance score s = f(x) where x is the feature vector. The model is a function from features to a scalar relevance estimate.

Pointwise: Regression Tree Approach

Most common pointwise approach: train a regression tree (or ensemble) to predict the relevance label y ∈ {0, 1, 2, 3} from features. At test time, score each (query, doc) pair and sort by predicted score.

Mean Squared Error (MSE) Loss — Pointwise
\[ \mathcal{L}_{MSE} = \frac{1}{n} \sum_{i=1}^n (y_i - \hat{y}_i)^2 = \frac{1}{n} \sum_{i=1}^n (y_i - f(\mathbf{x}_i))^2 \]

yᵢ = true relevance label, ŷᵢ = predicted score. Minimised via gradient descent or regression tree fitting.

Pointwise Advantages

  • Simple to implement — standard ML regression
  • Works with any ML method (trees, SVMs, linear models)
  • Efficient — O(n) training pairs
  • Easy to add new features

Pointwise Disadvantages

  • Ignores rank order — treats position 1 and position 10 equally
  • Predicting absolute relevance is harder than predicting relative order
  • MSE is not directly correlated with ranking metrics (NDCG, MAP)
  • Does not model interaction between documents in the list

Pairwise LTR: RankNet EXPANDED

Pairwise LTR

Instead of predicting absolute relevance, learn which of two documents (dᵢ, dⱼ) is more relevant to a query. Formulates ranking as a binary classification of document pairs. Proposed by Burges et al. (Microsoft Research, 2005).

RankNet: The Core Idea

A scoring function f(x) assigns a score sᵢ = f(xᵢ) to each document. The probability that dᵢ should be ranked above dⱼ is modelled as a sigmoid of the score difference:

RankNet: Pairwise Preference Probability
\[ P_{ij} = P(d_i \succ d_j) = \frac{1}{1 + e^{-\sigma(s_i - s_j)}} = \sigma(\sigma_{\text{param}} \cdot (s_i - s_j)) \]

• sᵢ = f(xᵢ) = score for document i (from the model)
• σ(·) = sigmoid function
• σ_param (often just written σ) controls steepness of the sigmoid
• When sᵢ > sⱼ: Pᵢⱼ > 0.5 (dᵢ more likely to be ranked above dⱼ)
• When sᵢ = sⱼ: Pᵢⱼ = 0.5 (equal preference)

RankNet: Cross-Entropy Loss
\[ \mathcal{L}_{RankNet} = -\bar{P}_{ij} \log P_{ij} - (1 - \bar{P}_{ij}) \log(1 - P_{ij}) \]

• P̄ᵢⱼ = ground truth preference: 1 if dᵢ is truly more relevant than dⱼ, 0.5 if tied, 0 if dⱼ is more relevant
• This is the standard binary cross-entropy loss applied to pairwise preferences
• Summed over all pairs (dᵢ, dⱼ) in the training set

Practice Example

Two documents: sᵢ=3.0, sⱼ=1.0. σ=1. dᵢ is truly more relevant (P̄=1). Compute P_ij and the RankNet loss.

Solved Example

P_ij = 1/(1+e^(−1×(3−1))) = 1/(1+e^(−2)) = 1/(1+0.135) ≈ 0.880
Loss = −1×log(0.880) − 0×log(0.120) = −log(0.880) ≈ 0.128
Low loss because the model correctly ranks dᵢ above dⱼ with high confidence.

RankNet: Gradient Derivation

When P̄ᵢⱼ ∈ {0, 1} (hard labels), the gradient of the loss with respect to the score sᵢ simplifies nicely:

\[ \frac{\partial \mathcal{L}}{\partial s_i} = \sigma \cdot (\bar{P}_{ij} - P_{ij}) \cdot (-1) = -\sigma \cdot (1 - P_{ij}) \quad \text{(when } \bar{P}_{ij}=1\text{)} \]

This gradient is used to update the scoring function f (neural network weights or tree parameters) via backpropagation. The gradient is large when Pᵢⱼ is small (model gets the order wrong) and small when Pᵢⱼ is large (model is correct).

Pairwise Advantages

  • Closer to the IR goal than pointwise (pairwise order is what ranking needs)
  • Loss directly penalises wrong pairwise orderings
  • Well-studied, principled gradient derivation

Pairwise Disadvantages

  • O(n²) pairs per query — expensive for large candidate sets
  • Does not optimise full list-level metrics (NDCG, MAP)
  • Treats all pairs equally — swapping rank 1 and rank 2 vs rank 100 and 101 gets same loss

Listwise LTR: LambdaMART

Listwise LTR

Optimise the entire ranked list directly using a list-level metric (e.g., NDCG, MAP). Does not decompose into independent pairs or individual documents — considers the whole permutation. State-of-the-art for web search.

Pointwise

Learn to predict relevance of individual (query, doc) pairs. Treats each pair independently. Simple regression/classification. Easy but ignores rank position.

E.g., regression tree predicting relevance label [0,1,2,3]

Pairwise

Learn which of two documents is more relevant. Pairwise preference loss. Closer to IR goal but doesn't account for full list structure.

E.g., RankNet: minimise P(wrong ordering)

Listwise

Optimise the full ranked list directly. Uses list-level metrics (NDCG). Most effective but more complex. State-of-the-art.

E.g., LambdaMART: gradient boosted trees with NDCG-weighted gradients

RankNet Loss (Pairwise — repeated for context)
\[ P_{ij} = P(d_i \succ d_j) = \frac{1}{1 + e^{-\sigma(s_i - s_j)}} \]
\[ \mathcal{L} = -\bar{P}_{ij} \log P_{ij} - (1 - \bar{P}_{ij}) \log(1 - P_{ij}) \]

P̄_ij = 1 if dᵢ more relevant than dⱼ, 0.5 if equal, 0 otherwise. σ controls steepness.

LambdaRank: NDCG-Weighted Gradients NEW — EXAM CRITICAL

The Problem with Optimising NDCG Directly

NDCG (and MAP, ERR) are non-differentiable functions of the ranked list — they depend on rank positions, which are discrete. We cannot compute ∂NDCG/∂s directly. LambdaRank bypasses this by defining surrogate gradients that approximate the direction NDCG would improve.

LambdaRank: Lambda Gradient
\[ \lambda_{ij} = \frac{\partial \mathcal{L}_{RankNet}}{\partial s_i} \cdot |\Delta \text{NDCG}_{ij}| \]

Expanded form:

\[ \lambda_{ij} = -\sigma \cdot |\Delta \text{NDCG}_{ij}| \cdot \left(1 - P_{ij}\right) \]

Where:
• |ΔNDCG_ij| = the absolute change in NDCG if documents dᵢ and dⱼ were swapped in the ranked list
• (1 − Pᵢⱼ) = the RankNet gradient (how wrong the current ordering is)
• σ = sigmoid steepness parameter

Key insight: pairs where swapping would cause a large NDCG gain get a large gradient — learning focuses on the most impactful ordering corrections.

LambdaRank: Computing |ΔNDCG_ij|

Recall NDCG@k:

\[ \text{NDCG}@k = \frac{1}{\text{IDCG}@k} \sum_{i=1}^k \frac{2^{r_i} - 1}{\log_2(i+1)} \]

When documents at positions i and j are swapped, ΔNDCG changes by:

\[ |\Delta\text{NDCG}_{ij}| = \left| \frac{2^{r_i}-1}{\log_2(i+1)} + \frac{2^{r_j}-1}{\log_2(j+1)} - \frac{2^{r_j}-1}{\log_2(i+1)} - \frac{2^{r_i}-1}{\log_2(j+1)} \right| \cdot \frac{1}{\text{IDCG}} \]

Swapping two documents at positions close to the top (small i, j) causes larger |ΔNDCG| and thus larger gradients — the model learns more from top-position errors.

LambdaRank Worked Example

Suppose sᵢ=2.0 (rel=3, at rank 5) and sⱼ=3.0 (rel=0, at rank 2). The model currently ranks dⱼ above dᵢ (wrong — dᵢ is more relevant). σ=1.

P_ij = σ(sᵢ−sⱼ) = σ(2−3) = σ(−1) = 1/(1+e) ≈ 0.269
(1−Pᵢⱼ) = 0.731 — large because model order is wrong

|ΔNDCG| is large because: rank-2 doc has rel=0 (should be low) and rank-5 doc has rel=3 (should be high). Swapping them would dramatically improve NDCG.

Therefore λᵢⱼ is large → large gradient → model strongly updates to push dᵢ above dⱼ.

MART / Gradient Boosted Regression Trees NEW

MART (Multiple Additive Regression Trees) / GBRT

Gradient Boosted Regression Trees (GBRT), also called MART or GBM (Gradient Boosted Machines). An ensemble method that sequentially adds regression trees, each fitting the residual error (or gradient) of the previous ensemble. The final score is the sum of all tree outputs.

LambdaMART = LambdaRank + MART

Training algorithm (simplified):

  1. Initialise all document scores to 0
  2. For each boosting round t = 1 to T:
    1. Compute λ_ij for all document pairs using LambdaRank formula
    2. Sum lambdas per document: Λᵢ = Σⱼ λᵢⱼ
    3. Fit a regression tree hₜ(x) to the pseudo-residuals Λᵢ
    4. Update scores: sᵢ ← sᵢ + η × hₜ(xᵢ)
  3. Final score: F(x) = Σₜ η × hₜ(x)

Key properties:

  • η = learning rate (step size)
  • T = number of trees (typically 100–1000)
  • Each tree has limited depth (typically 2–8 leaves)
  • Trained on NDCG-weighted gradients → optimises NDCG indirectly
  • Implemented in: LightGBM, XGBoost, Microsoft MART library
  • Used by Bing, Baidu, Yandex in production

Gradient Boosted Trees: Visual Intuition

Why Trees (not Neural Nets) for LTR?

For tabular/structured feature data (BM25 scores, PageRank, etc.), gradient boosted trees typically outperform neural networks. Trees: (1) handle missing features naturally, (2) require no feature normalisation, (3) are interpretable (feature importance), (4) train faster on CPU. Neural LTR (e.g., DSSM, BERT-based) is used when raw text is available (deep semantic features), but classical LTR with GBRT still dominates for structured features.

Risk in Learning to Rank NEW

LTR Risk

A LTR model may improve average-case performance across the test set but perform worse than a strong baseline (e.g., BM25) on individual queries. This is the risk of LTR — trading off reliability for average gain.

Sources of LTR Risk

  • Training data mismatch: test queries not well represented in training data → model generalises poorly
  • Feature bias: model learns spurious correlations from noisy click data
  • Overfitting: with too many trees/features, model memorises training queries
  • Query type mismatch: navigational queries behave differently from informational — a model trained on one type may fail on the other

Risk-Sensitive LTR

One approach: penalise the LTR model when it performs worse than a safe baseline (BM25). The risk-sensitive objective adds a penalty term:

\[ \text{Objective} = \text{E}[\text{NDCG}_{LTR}] - \alpha \cdot \text{E}[\max(0, \text{NDCG}_{baseline} - \text{NDCG}_{LTR})] \]

α controls the trade-off between average gain and safety. Higher α → more conservative (closer to baseline on bad queries).

Summary

LTR Motivation

Generative models (BM25) can't easily combine hundreds of heterogeneous features. LTR learns optimal feature weights from click data and relevance judgments. Consistently outperforms BM25 on average with sufficient training data.

Features

Query-dependent (BM25, TF-IDF per field, proximity), query-independent (PageRank, spam, age), query features (length, type). 100s of features typical in web LTR systems.

Training Data

LETOR (benchmark, ~46 features), MS MARCO (1M queries from Bing), TREC Deep Learning (dense NIST judgments). Click data: large-scale but noisy; position bias must be corrected.

Approaches

Pointwise (MSE, simple) → Pairwise (RankNet cross-entropy, O(n²) pairs) → Listwise (LambdaMART, best). Listwise approaches are state-of-the-art for web search.

RankNet

Pairwise LTR. Pᵢⱼ = σ(σ_param×(sᵢ−sⱼ)). Loss = cross-entropy. Gradient penalises wrong pairwise orderings. Foundation for LambdaRank/LambdaMART.

LambdaRank / LambdaMART

λᵢⱼ = |ΔNDCG_ij| × RankNet gradient. Focuses learning on document swaps that maximise NDCG improvement. LambdaMART = LambdaRank + Gradient Boosted Trees. Used by Bing, Baidu, Yandex.

Risk

LTR improves average but may degrade performance for individual queries. Risk-sensitive LTR adds penalty for underperforming the BM25 baseline. Important for deployment in production search systems.

Short Answer Questions
Q1. Describe three types of features used in Learning to Rank, giving two examples of each.
(1) Query-Dependent (QD): change per (query,doc) pair. E.g. BM25 score on body, cosine similarity between query and document. (2) Query-Independent (QI): fixed per document. E.g. PageRank, spam score (document-level). (3) Query Features (Q): fixed per query. E.g. query length (number of terms), query type classification (navigational vs informational).
Q2. Why might a learning-to-rank model introduce risk (worse performance for some queries)?
LTR learns an average-case model from training data. For queries poorly represented in training (e.g., rare query types, languages), the model may activate wrong sub-trees or features. Click-through training data has position bias (top results clicked more regardless of relevance). Risk-sensitive LTR adds a penalty for underperforming vs BM25 baseline (with α parameter) to reduce the chance of catastrophic failure on individual queries.
Q3. Why can't we directly optimise NDCG in gradient-based LTR, and how does LambdaRank address this?
NDCG (and MAP, ERR) are functions of rank positions, which depend on the sorted order of scores. Sorting is a non-differentiable operation — ∂NDCG/∂score does not exist in the usual sense. LambdaRank addresses this by defining surrogate gradients (λᵢⱼ) that combine the RankNet gradient (how wrong the pairwise ordering is) with |ΔNDCG_ij| (how much NDCG would improve if the pair were swapped). This provides a useful gradient direction even though the true gradient is undefined.
Exam-Style Questions
H/M[10 marks]
Q1. Compare and contrast pointwise, pairwise, and listwise approaches to Learning to Rank. For each approach: (a) describe how it formulates the learning problem, (b) give a named example algorithm, (c) state one advantage and one disadvantage. [10]
Pointwise [3]: Formulation: predict relevance of individual (q,d) pairs independently using regression/classification. Example: regression tree. Advantage: simple to implement and understand; standard ML tooling applies. Disadvantage: ignores rank order structure — treating position 1 and position 10 equally; MSE not correlated with NDCG.

Pairwise [3]: Formulation: learn preference between pairs of documents (dᵢ ≻ dⱼ). Example: RankNet (minimise cross-entropy on pairwise preference probabilities). Advantage: closer to IR goal than pointwise; directly penalises wrong orderings. Disadvantage: O(n²) pairs per query — expensive; treats all pair swaps equally regardless of rank position impact on NDCG.

Listwise [4]: Formulation: optimise the entire ranked list using a list-level metric. Example: LambdaMART (NDCG-weighted gradients with gradient boosted trees). Advantage: directly targets NDCG; state-of-the-art effectiveness; large-impact swaps get large gradients. Disadvantage: more complex; non-differentiable metrics require surrogate gradients; requires more training data.
H/M[10 marks]
Q2. Explain the RankNet algorithm in detail. (a) Write the pairwise preference probability formula and explain each component [3]. (b) Write the cross-entropy loss for a pair (dᵢ, dⱼ) and explain when it is minimised [3]. (c) How does LambdaRank extend RankNet to optimise NDCG? [4]
(a) Preference probability [3]: Pᵢⱼ = P(dᵢ≻dⱼ) = 1/(1+exp(−σ(sᵢ−sⱼ))). sᵢ = model score for dᵢ; σ = sigmoid function; σ_param controls steepness. When sᵢ > sⱼ, Pᵢⱼ > 0.5 (model predicts dᵢ ranked above dⱼ). When sᵢ = sⱼ, Pᵢⱼ = 0.5 (no preference).

(b) Cross-entropy loss [3]: L = −P̄ᵢⱼ log Pᵢⱼ − (1−P̄ᵢⱼ) log(1−Pᵢⱼ). P̄ᵢⱼ = ground truth: 1 if dᵢ truly more relevant, 0.5 if tied, 0 if dⱼ more relevant. Loss is minimised when the model's probability Pᵢⱼ matches the ground truth P̄ᵢⱼ: if dᵢ is truly more relevant (P̄=1), loss minimised when Pᵢⱼ → 1 (model assigns much higher score to dᵢ).

(c) LambdaRank extension [4]: RankNet treats all pairs equally regardless of their position in the ranking. LambdaRank multiplies the RankNet gradient by |ΔNDCG_ij| — the change in NDCG if dᵢ and dⱼ were swapped: λᵢⱼ = −σ × |ΔNDCG_ij| × (1−Pᵢⱼ). This means: pairs at top positions whose swap causes large NDCG gain get larger gradients → learning focuses on the most impactful rank corrections. NDCG is not directly differentiable, so |ΔNDCG_ij| acts as a surrogate weight that guides gradient descent toward better NDCG.
H/M[8 marks]
Q3. (a) What is LambdaMART, and how does it differ from LambdaRank? [3] (b) Describe the MART (gradient boosted trees) training procedure for LTR in pseudocode or clearly numbered steps. [5]
(a) LambdaRank vs LambdaMART [3]: LambdaRank is the gradient signal — it defines the λᵢⱼ = |ΔNDCG_ij| × (1−Pᵢⱼ) gradient for pairwise document comparisons. LambdaMART combines these gradients with MART (Multiple Additive Regression Trees / Gradient Boosted Trees) as the learning algorithm. Instead of using a neural network to generate scores, LambdaMART fits shallow regression trees sequentially to the lambda pseudo-residuals.

(b) MART training procedure for LTR [5]:
1. Initialise all document scores F₀(x) = 0
2. For t = 1 to T (number of trees):
  a. Compute λᵢⱼ for all document pairs using LambdaRank formula
  b. Aggregate per-document gradient: Λᵢ = Σⱼ λᵢⱼ (sum over all paired documents)
  c. Fit a regression tree hₜ(x) to predict Λᵢ from features xᵢ (leaf values via Newton step)
  d. Update the ensemble: Fₜ(x) = Fₜ₋₁(x) + η × hₜ(x) (η = learning rate)
3. Final model: F(x) = Σₜ η × hₜ(x). At test time, score document x using F(x) and rank by descending score.
H/M[8 marks]
Q4. (a) Describe the sources and limitations of training data used for Learning to Rank, contrasting explicit relevance judgments with click-through data. [4] (b) What is position bias in click data and how can it be corrected? [4]
(a) Training data [4]: Explicit judgments (e.g., LETOR, TREC assessors): human annotators label (query,doc) pairs on relevance scale. High quality, reliable. Limitation: expensive and slow to collect — typically thousands to tens of thousands of pairs. Not scalable to billions of queries. Click-through data (e.g., from Bing/Google search logs): user clicks, dwell time, CTR collected automatically at massive scale (billions of interactions). Limitation: noisy — clicks ≠ relevance (user may click on irrelevant result). Subject to position bias. MS MARCO combines both: click-derived relevance labels from Bing at scale.

(b) Position bias [4]: Users tend to click on results ranked higher in the list regardless of their actual relevance (presentation bias). This is because higher-ranked results receive more attention (eye-tracking studies confirm this). Effect: training data overestimates the relevance of top-ranked documents. Corrections: (1) Inverse Propensity Scoring (IPS): down-weight clicks from top positions by a propensity factor p(rank), give more weight to clicks at lower positions; (2) Interleaving experiments: interleave results from two systems, measure clicks as unbiased comparison; (3) Unbiased LTR: jointly learn propensity model and relevance model from click data; (4) Randomisation: occasionally shuffle results to collect random click data (costly to serve).
H/M[8 marks]
Q5. A retrieval system uses a multi-stage ranking pipeline. (a) Describe the three stages of a typical web-scale ranking cascade and justify why multiple stages are used. [4] (b) At what stage would LambdaMART typically be applied, and what features would it use? [4]
(a) Three-stage cascade [4]: Stage 1 (Candidate Generation): Fast lexical matching (Boolean retrieval, BM25) over the entire collection (billions of documents) to retrieve ~1000 candidates per query. Millisecond latency. Coarse but high-recall. Stage 2 (Learning to Rank): LambdaMART or similar LTR model with 100s of features (BM25 per field, PageRank, proximity) applied to the ~1000 candidates. Reduces to top ~20. Hundreds of milliseconds. Stage 3 (Re-ranking): Slow, accurate neural model (BERT cross-encoder, ColBERT) applied to the top 20. Produces final ranking. Seconds of latency. Reason for multiple stages: balances cost vs accuracy — running a BERT re-ranker over billions of documents is computationally infeasible; each stage filters candidates for the next more expensive model.

(b) LambdaMART at Stage 2 [4]: LambdaMART is applied to the ~1000 BM25 candidates from Stage 1. Features used include: (QD) BM25 scores for body, title, anchor, URL separately and BM25F combined; PL2 scores; proximity/MRF scores; deep semantic similarity scores from fast dense retrieval. (QI) PageRank, spam score, URL depth, document age, number of inlinks. (Q) Query length, query type (navigational vs informational). LambdaMART then learns the optimal combination of these 100s of features to maximise NDCG on training data, producing a reranked top-20 for Stage 3.
Flashcards
Learning to Rank
ML technique to learn optimal ranking from training data with relevance labels. Uses 100s of features. Deployed by Bing, Baidu, Yandex.
LambdaMART
State-of-the-art listwise LTR. LambdaRank gradients (|ΔNDCG|×(1−Pᵢⱼ)) + Gradient Boosted Trees. Focuses on impactful document swaps.
RankNet
Pairwise LTR. Pᵢⱼ=σ(σ·(sᵢ−sⱼ)). Minimise cross-entropy loss of pairwise preference probabilities. Foundation for LambdaRank.
LambdaRank Gradient
λᵢⱼ = −σ·|ΔNDCG_ij|·(1−Pᵢⱼ). Multiplies RankNet gradient by NDCG gain from swapping. Large gradient for high-impact wrong orderings.
Ranking Cascade
Multi-stage retrieval: cheap BM25 (1B→1K) → LambdaMART with 100s features (1K→20) → BERT re-ranker (20→10). Each stage trades cost for accuracy.
Click-through Data
User clicks in search logs. Used as implicit relevance signal. High quantity but noisy — position bias: top results clicked more. Enables large-scale LTR training.
Position Bias
Users click on high-ranked results regardless of relevance. Biases training data. Corrected by IPS (inverse propensity scoring) or interleaving experiments.
MART / GBRT
Multiple Additive Regression Trees. Sequentially fit regression trees to gradient residuals. LambdaMART uses NDCG-weighted pseudo-residuals (lambda values).
MS MARCO
Microsoft dataset: ~1M queries from real Bing search logs. Standard LTR/neural IR benchmark. TREC Deep Learning adds dense NIST judgments on top.
QD / QI / Q Features
QD: vary per (query,doc) — BM25, TF-IDF. QI: vary per doc only — PageRank, spam. Q: vary per query only — query length, type.
