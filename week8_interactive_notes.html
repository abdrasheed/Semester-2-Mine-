🔮 Apache Cassandra

Cassandra is a distributed key-value data store inheriting BigTable's data model AND Amazon Dynamo's replication techniques. It is peer-to-peer — no master service — solving the SPOF problem of HBase. Focused on Availability + Partition Tolerance (BASE, AP system).

No SPOF

Each node is a possible "master". No HMaster equivalent. Failure of any single node does not bring down the system.

Peer-to-Peer (Dynamo-inspired)

Uses DHT ring architecture from Amazon's Dynamo for distributed index and replication without central coordination.

BigTable Data Model

Sparse, distributed, persistent, multidimensional map. Inherits HBase's column family structure. No explicit timestamps by default.

Tunable Consistency

Unique feature: users can dynamically trade Availability for Consistency per operation using consistency levels.

Cassandra Data Model

Key Differences from HBase

  • Base reference: <partition_key, column> (not <rowkey, column, timestamp>)
  • No default timestamps
  • Column families can be multi-tiered (column families of column families)
  • Data lookup by partition key (hashed to determine node)
// Cassandra API (from DHT design)
insert(table, key, rowMutation)         // Insert/update data
get(table, key, columnName)             // Retrieve data
delete(table, key, columnName)           // Delete data

// Important: all operations on a given row are ATOMIC per replica

Cassandra Ring & Arc Architecture

Ring Mechanics

  • Nodes arranged in a ring with numeric IDs in hash space
  • Each partition key is hashed to a position in ring
  • Data assigned to node with next highest ID
  • With 3 replicas: next 3 clockwise nodes

Example Assignments (3 replicas, ring: N1,N12,N18,N25,N40)

Partition Key HashPrimaryReplicas
hash("Elite Dangerous") = 5N12N18, N25
hash("Star Citizen") = 19N25N40, N1
hash("Destiny 2") = 30N40N1, N12
Arc: The arc of the ring that a node owns = the partition keys it is responsible for. Nodes within an arc monitor each other to detect failures and trigger re-replication.
Node Failure: When a node drops from the cluster, its arc extends to the next node (longer arc). Re-replication automatically triggered by the remaining nodes in the arc.

Hash Partitioning Strategies

RandomPartitioner (default)

How: Uses hash function with random output in given range (e.g., MD5 hash → ring position).
Pro Simple to calculate. Spreads load evenly.
Con Does not enable range queries (similar keys not near each other).

OrderPreservingPartitioner

How: Order preserving hash: if x ≤ y then hash(x) ≤ hash(y).
Pro Great for range queries (similar keys collocated).
Con Can cause hot-spots: data with similar keys clusters on few nodes.

Replication Strategy

Multi-Datacenter Replication

Cassandra can replicate across multiple datacentres using snitches — configuration objects that tell nodes which datacenter and rack each other node belongs to. This enables:

  • LOCAL_QUORUM: quorum within local datacenter only
  • EACH_QUORUM: quorum satisfied in every datacenter
  • Geographic fault tolerance — entire DC can fail without data loss

📡 Cassandra — Gossip, Virtual Nodes & Consistency

Why No Finger Tables? → Gossiping Protocol

Classic DHTs use finger tables for O(log N) routing without global knowledge — designed for highly dynamic public P2P networks. Cassandra operates in controlled datacentres, allowing a different approach: gossiping — every node eventually knows every other node. No routing needed.

Token Generation

Every second, each node generates a token containing: its ID and ring position, and info about nodes it has communicated with.

Message Spreading

Each token is sent to 3 other nodes. Information floods through the network ("epidemic propagation"). Eventually all nodes become aware of all other nodes.

Bootstrap

New nodes read a seed file to get initial contact nodes. Seed nodes contain bootstrapping information. New node announces itself to seeds, gossip spreads it everywhere.

Result: Global Knowledge

Eventually all nodes know: all other nodes, the arc each node owns, and routing is a simple O(1) lookup (not O(log N) like finger tables).

Virtual Nodes

Problem: Basic ring structure doesn't account for hardware heterogeneity. A powerful server (8 cores) shouldn't have the same arc responsibility as a weak one (4 cores). Hashing doesn't naturally balance based on capacity.
Solution: Represent each physical node as multiple virtual nodes (vnodes). Spread vnodes across the ring. A powerful node gets more vnodes → handles more arcs → greater load.

Physical nodes and their virtual node assignments in the ring:

Physical → Virtual Node mapping:

N12 (8 cores) has 4 virtual nodes vs N1 and N18 (4 cores) with 2 each → proportional load.

Consistency Models

The Core Trade-off: Reading from ONE replica is fast but may return stale data. Reading from ALL replicas is slow but guaranteed consistent. How do we tune this?

Option 1: Eventual Consistency

Write: Write to primary node → propagates to replicas asynchronously.
Fast writes + reads
Stale reads possible
Data propagation in progress — no way to know if replica is current.

Option 2: Majority Consensus

Write: Two-phase: ensure majority available → write to majority → commit.
Guaranteed current reads
Slower writes + higher latency
Only commits if majority of nodes have data.

Option 3: Quorum — Generalised Consensus

Parameters: N = number of replicas, R = read quorum, W = write quorum
Condition 1: R + W > N
Condition 2: 2 × W > N
Both conditions must hold. This guarantees every read sees the latest write (by set intersection).
Intuition: If R+W > N, then any read set and any write set must share at least one common node. That shared node holds the latest write. Reading its timestamp lets the coordinator return the most recent value.

Tuning:
• Read-intensive: Decrease R (smaller read quorum → faster reads), increase W
• Write-intensive: Decrease W (smaller write quorum → faster writes), increase R

🖥️ Cluster Management

Practical Reality: Big Data platforms need to be deployed on physical hardware. This is harder than it sounds — especially on heterogeneous, shared, multi-user clusters.

Example Cluster Setup

Rack 1 (Year 1)

  • 2 Storage Servers
  • 2 Compute Servers
  • Single network switch
  • Data stored here (HDFS)

Rack 2 (Year 2)

  • 3 Compute Servers v2 (2× faster)
  • Separate network switch
  • New hardware generation

Problems with Manual Deployment

Scale

Log on to each machine, install dependencies, start services from command line. Larger cluster = exponentially more work.

Networking

Must manually configure workers to find master. Multiple network switches add complexity. Cross-rack communication latency.

Data Locality

Data in Rack 1. Computing in Rack 2 requires cross-switch transfer. Defeats purpose of data locality.

Hardware Heterogeneity

Spark detects core count but NOT CPU speed differences. Rack 2 is 2× faster but gets same load → suboptimal utilization.

Software Multiplicity

Multiple applications share the cluster. Competing for resources. Incompatible library versions. Need isolation and fair sharing.

Shared Cluster Challenges

Reality: Clusters are expensive. Many teams and projects share the same cluster simultaneously. Two primary problems arise:

1. Software Incompatibilities

Different applications need different library versions, executables, drivers. They conflict on shared OS.

Solution: Software Sandboxes (JVM, VMs, Containers)

2. Resource Distribution

How to share CPU/memory/storage fairly? How to prevent one job from monopolising the cluster?

Solution: Resource Management Systems (YARN, Kubernetes)

📋 Past Exam Questions & Model Answers

[2025 Exam Q] Explain Cassandra's ring architecture and how it avoids single points of failure. How does it differ from HBase? (10 marks)

Model Answer

Ring Architecture:

  • Nodes assigned numeric IDs in a shared hash space and arranged in a ring
  • Partition keys are hashed to ring positions
  • Node with next highest ID from the hash value is primary for that partition key
  • With N replicas: next N clockwise nodes also hold copies
  • Each group of nodes responsible for a partition key forms an "arc"
  • Nodes within an arc monitor each other; if one fails, arc extends to next node and re-replication triggers

No SPOF:

  • Unlike HBase (with HMaster), Cassandra has no central master
  • Every node is a potential coordinator (can accept any request)
  • Node failure is handled by arc extension + re-replication
  • Multi-datacenter replication provides geographic resilience

Differences from HBase: HBase uses HMaster + ZooKeeper for coordination (SPOF exists), region-based partitioning, and is CP-oriented. Cassandra uses DHT ring, peer-to-peer gossip, and tunable consistency (AP-oriented by default). Cassandra is generally faster and easier for multi-DC deployments.

[2024 Exam Q] Explain the Quorum consistency model in Cassandra. Given N=5, what values of R and W satisfy quorum conditions? What trade-off does this enable? (10 marks)

Model Answer

Quorum model: A generalisation of majority consensus. Parameterised by N (replicas), R (read quorum), W (write quorum). Two conditions must hold: R+W > N and 2×W > N.

Intuition: If R+W > N, every read set and write set must intersect (pigeonhole principle). The shared node holds the latest write, and comparing timestamps guarantees the coordinator returns the most recent value.

For N=5, valid configurations (both conditions):

  • W=3, R=3: R+W=6>5 ✓, 2W=6>5 ✓ — balanced
  • W=4, R=2: R+W=6>5 ✓, 2W=8>5 ✓ — read-optimised
  • W=3, R=4: R+W=7>5 ✓, 2W=6>5 ✓ — write-optimised

Trade-off: Decrease R (fewer nodes for reads) → faster reads, but W must increase → slower writes. Read-intensive workloads: small R, large W. Write-intensive: small W, large R.

[2023 Exam Q] What is Cassandra's gossiping protocol? Why does Cassandra use gossip instead of finger tables? (8 marks)

Model Answer

Gossip protocol:

  • Every second, each node generates a token containing its ID, ring position, and info about recently contacted nodes
  • Token sent to 3 random other nodes
  • Information propagates ("epidemically") through network
  • Eventually all nodes know all other nodes — global knowledge achieved
  • New nodes bootstrap via seed file (list of initial nodes)

Why gossip instead of finger tables:

  • Finger tables designed for public P2P networks with constantly joining/leaving nodes — need O(log N) routing with minimal per-node state
  • Cassandra operates in controlled datacentres — membership changes are rare and predictable
  • With gossip, every node eventually has complete cluster knowledge → lookups become O(1) (simple table lookup), not O(log N)
  • Trade-off: gossip consumes slight bandwidth; acceptable in DC with reliable, fast networks
[2023 Exam Q] Compare containers, virtual machines, and JVM sandboxes. Which is preferred for Big Data and why? (10 marks)

Model Answer

JVM: Creates sandbox per Java process using Runnable JARs. Solves app/library incompatibilities only. Java-only. Minimal overhead but limited scope.

Virtual Machines: Hypervisor runs complete Guest OS per VM. Solves ALL incompatibility levels including drivers. But: instruction translation overhead, GB-sized images, slow startup. Not suitable for Big Data where performance is critical.

Containers: Lightweight; share host OS kernel. Docker images contain app + libraries + executables. Solves app/library/executable incompatibilities. Uses host drivers (doesn't solve driver-level). Fast startup, MB-sized images, minimal overhead vs native.

Preferred for Big Data: Containers.

  • Near-native performance (direct hardware access via host OS)
  • Fast deployment (docker pull from DockerHub)
  • All major Big Data platforms (Spark, Hadoop, Cassandra, Kafka) available as Docker images
  • Integrates with resource managers (YARN, Kubernetes)
  • Lightweight enough to run many per node
  • VMs rejected due to performance overhead; JVM too limited in scope
[2022 Exam Q] What are virtual nodes in Cassandra and why are they needed? (6 marks)

Model Answer

Problem: In a basic Cassandra ring, each physical node owns one arc of the ring. But nodes may have different capacities (e.g., 4 cores vs 8 cores). Simple ring assignment doesn't account for this — a powerful node gets the same data load as a weak one.

Virtual Nodes (vnodes): Each physical node is represented as multiple virtual nodes spread around the ring. A node with greater capacity gets more vnodes → owns more arcs → handles proportionally more data and requests.

Benefits:

  • Proportional load balancing based on hardware capacity
  • When a node is added/removed, load redistributes more smoothly
  • Greater granularity of ring position assignment
  • Example: N12 (8 cores) gets 4 vnodes; N1 (4 cores) gets 2 vnodes

✏️ Practice Questions

Q1. A Cassandra cluster has 5 nodes with IDs: N5, N15, N30, N50, N70. With replication factor 3, which nodes store data with hash key = 25? What happens if N30 fails?

Primary assignment: Hash key 25 → next highest node = N30 (next after 25).

3 replicas (clockwise from N30): N30 (primary), N50 (replica 1), N70 (replica 2).

If N30 fails:
  • N30's arc-mates (N50 and N70) detect the failure
  • The arc extends: N15 now becomes the new lower boundary for key 25's arc
  • Re-replication triggers: the data is copied to the next node that would extend the arc (N5)
  • Clients can still read from N50 or N70 (2 replicas still alive)
  • With consistency level ONE, reads continue uninterrupted immediately

Q2. For a Cassandra cluster with N=6 replicas, find all valid (R, W) quorum pairs where both R and W ≥ 1. Which pair gives the best write performance? Which gives the best read performance?

Conditions: R + W > 6 (→ R+W ≥ 7) AND 2W > 6 (→ W ≥ 4)

Valid pairs (W ≥ 4, R+W ≥ 7):
WMinimum R neededValid R values
4R ≥ 3R = 3, 4, 5, 6
5R ≥ 2R = 2, 3, 4, 5, 6
6R ≥ 1R = 1, 2, 3, 4, 5, 6

Best write performance: W=4, R=3 (minimum W that satisfies 2W>6)
Best read performance: W=6, R=1 (write to all replicas, read from just one)

Q3. A company runs Python ML jobs (needing CUDA drivers v12) and Java Spark jobs (needing specific log4j 1.x) on the same cluster. What sandbox approach should they use and why?

Recommendation: Containers (Docker)

Analysis:
  • JVM only: Insufficient — doesn't solve Python runtime incompatibility or conflicting log4j versions across JVM instances (same executable version)
  • Virtual Machines: Would work (full isolation including drivers) but too heavy — GB-sized images, slow startup, high overhead unacceptable for ML training jobs
  • Containers: Best choice — each job runs in its own container image with specific Python/CUDA versions, specific JAR dependencies, own log4j version
Caveat — CUDA drivers: If CUDA driver versions differ between jobs (driver-level incompatibility), containers CANNOT fully solve this (they share host OS drivers). In that case: request specific GPU nodes with correct driver version, OR use separate VM-based isolation for GPU jobs.

Practical solution: Containers + resource manager (Kubernetes) for scheduling containers to appropriate nodes with compatible GPU drivers.

Q4. Explain the difference between Cassandra's gossiping protocol and BitTorrent's original tracker-based approach. What SPOF does each have (if any)?

BitTorrent original (tracker-based):
  • Centralised tracker servers maintain list of peers with each file piece
  • Downloaders register with and query tracker servers periodically
  • SPOF: Tracker servers — if tracker goes down, new peers can't find the swarm
Cassandra gossiping:
  • Every node periodically sends token (state info) to 3 random nodes
  • Information floods through network ("epidemic propagation")
  • Eventually all nodes know all other nodes (global knowledge)
  • No SPOF — information spreads through all nodes; no central tracker
Why Cassandra can use gossip but BitTorrent couldn't (initially): Cassandra operates in controlled datacentres with stable, fast networks — eventual global knowledge is achievable and reliable. BitTorrent operates on the public internet with millions of unreliable peers constantly joining/leaving — gossip would flood the internet with tokens.
