🔺 CAP Theorem

Definition (Eric Brewer, ~2000): A distributed data storage system can only guarantee two of the three desirable properties: Consistency, Availability, and Partition Tolerance.

C — Consistency

Every node has the same knowledge of data at any instant in time. A read always returns the most recent write or an error.

A — Availability

A guarantee that every request receives a response, which may be processed or failed. The system is always operational.

P — Partition Tolerance

The system continues to operate even if a message is lost or part of the system fails (network partition).

CA Systems

Oracle, MySQL

Consistent + Available. Fail when nodes become unavailable (no partition tolerance).

CP Systems

MongoDB, HBase

Consistent + Partition Tolerant. Data may become temporarily unavailable during partitions.

AP Systems

Cassandra, CouchDB

Available + Partition Tolerant. Clients may get inconsistent (stale) data temporarily.

NFS & HDFS Under CAP

PropertyNFSHDFS
Consistency Yes One copy only → always consistent Mediocre Best-effort replica sync takes time
Availability Decent Returns data if server alive Decent? Returns data if ≥1 replica exists; NameNode is SPOF
Partition Tolerance No Single copy = single point of failure Decent Resilient to failures based on replication factor
Classification CA (no partition tolerance) Towards CP (sacrifices some consistency)
Big Data Insight: As we scale towards Big Data, availability and fault tolerance become easier (more replicas = more resilience), but consistency becomes harder. More replicas = more costly to keep all up-to-date + more edge cases (e.g., HDFS recovery procedures).

⚗️ BASE Properties

BASE is an acronym for the consistency model used by modern Big Data systems (Cassandra, CouchDB). It trades strict consistency for high availability and partition tolerance.

B — Basically Available

System guarantees it will respond to every request. The response may be old (stale) data, or simply a notification that the desired data is unavailable. The system is never "down".

A — Soft State

The system's internal storage state will constantly change, even when no new input is received. This happens due to eventual consistency propagation and background synchronisation processes.

S — Eventually Consistent

The system will become consistent if new input stops being provided — but consistency is NOT guaranteed per-transaction. Different clients may see different versions of the same data.

ACID vs BASE Comparison

PropertyACID (Traditional DB)BASE (Big Data)
ConsistencyStrong Per transactionEventual Over time
AvailabilityModerate May refuse if inconsistentHigh Always responds
Partition ToleranceLow Usually fails on partitionHigh Continues operating
Data StateHard state (deterministic)Soft state (fluid)
Use CaseBanking, financial transactionsSocial media, Big Data analytics
ExamplesOracle, PostgreSQL, MySQLCassandra, CouchDB, DynamoDB
Why BASE for Big Data? At planet-scale (billions of records, thousands of nodes), enforcing ACID consistency requires distributed locking and two-phase commit — both are expensive and slow. BASE allows systems to accept temporary inconsistency in exchange for massive throughput and availability gains.

🌲 Log-Structured-Merge (LSM) Trees

The Index Problem

Challenge: Any distributed storage system must keep an index specifying physical locations of all storage units. The index must always be available and fast to search.

Write Ahead Log (WAL)

Persistently stores write records between spill file writes. Append-only (fast sequential writes). Acts as crash recovery mechanism.

MemTable

In-memory store of the most recent batch of write records. Records keyed to their files. Read requests check here first — acts as a recent cache.

SSTable (Sorted String Table)

Series of immutable sorted spill files on disk. Once MemTable fills, it is sorted and written as a new spill file added to the SSTable.

Index

Maps file keys to the SSTables containing information about that key. Maintained in both memory and persistent storage for speed.

Compactor

Background process that merges SSTables to reduce fragmentation. Removes old data from updates/deletes. Can be scheduled during quiet periods.

Tombstone Files

Deletes are written as "tombstones" rather than removing data in-place. The Compactor reads tombstones during merges to avoid persisting deleted data forever.

LSM Tree Write Process

1

Write to WAL (Write Ahead Log)

Append the record to the WAL. This ensures the write is persistently stored before any other action. If the system crashes before the MemTable is flushed, the WAL allows recovery.

2

Add to MemTable

Add the record to the in-memory MemTable. This is fast (RAM write). The MemTable holds recent writes and serves reads quickly (acts as cache).

3

MemTable Full? → Flush to SSTable

When the MemTable reaches capacity: (a) Sort the MemTable by key, (b) Write it to a new sorted Spill File on disk, (c) Update the Index with keys for that SSTable, (d) Clear the WAL.

4

Background: Compact SSTables

The Compactor periodically merges multiple SSTables, removes outdated records (old versions of updated keys) and tombstoned records (deleted keys). Reduces fragmentation and storage bloat.

LSM Tree Read Process

1

Check MemTable

Check if the MemTable has the desired record. Assuming recent data is most likely needed, this gives fast returns — the MemTable acts as a recent-write cache.

2

Query the Index (via Bloom Filter)

If not in MemTable, ask the Index for a list of SSTables that might contain the record. Uses a Bloom Filter for fast O(k) probabilistic lookup.

3

Scan Identified SSTables

Load identified SSTables into memory and scan them. This uses sequential block reads (fast disk I/O), then scans in memory. Bloom Filters reduce the number of SSTables to scan.

Design Decision Summary

Why Writes Are Fast

  • WAL is append-only (sequential write)
  • MemTable is an in-memory write (no disk)
  • Spill file writes are batched + sorted (sequential)
  • No in-place modifications to existing files

Why Updates/Deletes Are Costly

  • Updates written as new records (old version lingers)
  • Deletes written as tombstones (not immediate removal)
  • Requires Compactor to clean up (expensive merge)
  • Schedule compaction during quiet periods

🎯 Bloom Filters

Definition (Burton Howard Bloom, 1970): A space-efficient probabilistic data structure used to test whether an element belongs to a set. A query returns either "possibly in set" or "definitely not in set" — never a false negative.

No False Negatives

If a Bloom filter says "not in set", the item is definitely not in the set. This guarantee is absolute.

False Positives Possible

If a Bloom filter says "possibly in set", the item might not actually be there (hash collision). False positive rate is controllable via parameters.

Space Efficient

Example: 1,000 items at 5% false positive rate requires only ~778 bytes. Compare to storing all 1,000 keys explicitly.

How Bloom Filters Work

Step 1 — Initialise the Bit Array

Define a hash space: a binary array of m bits, all initialised to 0. Define k hash functions, each mapping any key to a position in [0, m-1].

Step 2 — Writing Records (Adding to Set)

W1

Hash the key using all k functions

For key K1, apply h₁(K1), h₂(K1), ..., hₖ(K1) → get k position values

W2

Set those positions to 1

Example: K1 hashes to positions 3 and 5. Set bits[3]=1, bits[5]=1.

W3

Repeat for each record

K2 hashes to positions 5 and 9. Set bits[9]=1 (bit 5 already 1 — hash collision with K1 at position 5).

Step 3 — Reading Records (Membership Query)

R1

Hash the query key using all k functions

Re-hash your query key to get the same k positions.

R2

Check all positions

Any 0? Item is definitely NOT in the set.
All 1? Item is possibly in the set (but could be false positive).

Hash Collision: Two different keys (e.g., K1 and K2) can map to the same bit position. This causes false positives. Probability decreases as m (hash space size) increases and as k (number of hash functions) is optimised.

Bloom Filter Mathematics

Probability a bit stays 0 after adding 1 element with 1 hash function:
p₁ = 1 − (1/m)
Probability a bit stays 0 after adding 1 element with k hash functions:
p₂ = (1 − 1/m)ᵏ
Probability a bit stays 0 after n elements with k hash functions:
p₃ = (1 − 1/m)^(kn)
False Positive Probability (approximation using e):
pfp ≈ (1 − e−kn/m)ᵏ
Note: Not strictly correct but a good approximation

Optimal Parameters

Optimal number of hash functions k, given m and n:
kopt = (m/n) × ln(2)
Or equivalently, given target pfp:
kopt = −log₂(pfp)
Optimal bit array size m, given n elements and target pfp:
mopt = −1.44 × log₂(pfp) × n

Worked Example

Given: n = 1,000 elements, pfp = 5% = 0.05

kopt = −log₂(0.05) = −(−4.32) ≈ 5 hash functions
mopt = −1.44 × log₂(0.05) × 1000 = 1.44 × 4.32 × 1000 ≈ 6,224 bits
6,224 bits = 778 bytes ≈ <1 KB for 1,000 items at 5% FPR!

This shows the extreme space efficiency of Bloom filters. Storing 1,000 keys directly would require ~thousands of bytes per key.

Bloom Filters in LSM Trees

Application: During LSM Tree reads, a Bloom Filter is maintained per SSTable. Before loading an SSTable from disk, the index checks the Bloom Filter to determine if the requested key might be in that SSTable. This avoids expensive disk reads for SSTables that definitely don't contain the key. False positives mean occasionally loading the wrong SSTable — acceptable overhead. False negatives would mean missing data — not possible with Bloom Filters.

📋 Past Exam Questions & Model Answers

[2025 Exam Q] Explain the CAP theorem. Describe where NFS and HDFS sit within the CAP triangle and justify your answers. (10 marks)

Model Answer

CAP Theorem: Proposed by Eric Brewer (~2000). States that a distributed data storage system can only guarantee two of three properties simultaneously:

  • Consistency (C): Every node returns the same data at any instant
  • Availability (A): Every request receives a response (even if stale)
  • Partition Tolerance (P): System continues operating despite node/message failures

NFS under CAP:

  • C: Yes — single copy, so always consistent
  • A: Decent — returns data as long as server is alive
  • P: No — single copy = single point of failure; partition = data loss
  • Classification: CA system (relies on RAID for some fault tolerance but no native distributed replication)

HDFS under CAP:

  • C: Mediocre — replication is eventual; replicas may briefly differ during write/recovery
  • A: Decent (with caveat) — returns data if ≥1 replica exists; however, NameNode is a SPOF
  • P: Decent — replication factor (default 3) provides resilience against DataNode failures
  • Classification: Trending CP — prioritises consistency and partition tolerance over guaranteed availability
[2024 Exam Q] Compare ACID and BASE consistency models. Why do Big Data systems prefer BASE? (8 marks)

Model Answer

ACID (Atomicity, Consistency, Isolation, Durability): Traditional database guarantee. Every transaction leaves the database in a valid state. Requires distributed locking and coordination for distributed systems — expensive at scale.

BASE (Basically Available, Soft State, Eventually Consistent): Modern Big Data model.

  • Basically Available: System always responds (may return stale data or unavailability notice)
  • Soft State: System state continuously changes even without new input (propagation of updates)
  • Eventually Consistent: If input stops, system will eventually reach consistent state

Why Big Data prefers BASE:

  • At massive scale (billions of records, thousands of nodes), ACID consistency requires expensive distributed locking
  • Two-phase commit (ACID) introduces latency — unacceptable for high-throughput Big Data
  • More replicas = higher availability and fault tolerance (which is desired)
  • But more replicas = harder to keep consistent (trade-off forces BASE)
  • Many Big Data use cases (social media, analytics) tolerate stale reads but require high availability
[2023 Exam Q] Describe the LSM tree write and read processes. What design decisions make writes fast? (12 marks)

Model Answer

Write Process:

  1. Append record to WAL (Write Ahead Log) — ensures persistence before further processing
  2. Add record to in-memory MemTable
  3. When MemTable is full: sort it, write to new Spill File (SSTable), update Index, clear WAL
  4. Background Compactor periodically merges SSTables, removes tombstoned/updated records

Read Process:

  1. Check MemTable first (recent-write cache, fast)
  2. If not found, query Index using Bloom Filter to identify candidate SSTables
  3. Load identified SSTables and scan them (sequential block reads)

Design decisions making writes fast:

  • WAL is append-only → sequential disk write (fast)
  • MemTable is in-memory → no disk I/O during normal write
  • Spill files written as batched sequential writes (sorted, immutable)
  • No in-place modifications → avoids slow random writes
  • Disk I/O is 3 orders of magnitude faster for sequential vs random access
[2023 Exam Q] Explain how Bloom Filters work. Derive the formula for false positive probability and explain how to choose optimal parameters. (10 marks)

Model Answer

How Bloom Filters work:

  • Initialise a bit array of m bits (all 0s)
  • Define k hash functions, each mapping a key to a position in [0, m−1]
  • Add element: hash it with all k functions; set those bit positions to 1
  • Query: hash query key; if any bit is 0 → definitely not in set; if all bits 1 → possibly in set (false positive possible)

False Positive Probability Derivation:

  • P(single bit stays 0 after 1 element, 1 function) = 1 − 1/m
  • P(single bit stays 0 after 1 element, k functions) = (1 − 1/m)ᵏ
  • P(single bit stays 0 after n elements, k functions) = (1 − 1/m)^(kn)
  • P(false positive) ≈ (1 − e^(−kn/m))ᵏ

Optimal Parameters:

  • k_opt = (m/n) × ln(2) = −log₂(p_fp)
  • m_opt = −1.44 × log₂(p_fp) × n
  • Example: n=1000, p_fp=5% → k=5, m=6224 bits (778 bytes)
[2022 Exam Q] Why is a log-based approach preferred for index storage in Big Data systems? What are the trade-offs of LSM trees? (8 marks)

Model Answer

Why log-based indexing:

  • Disk sequential I/O is up to 1000× faster than random I/O
  • Traditional index structures (B-trees) require random writes — slow for Big Data scale
  • A log is append-only → always sequential writes → maximum throughput
  • Logs are simple and can be partitioned across nodes by key hash

LSM Tree advantages:

  • Very fast writes (in-memory MemTable + sequential batch flushes)
  • Efficient reads via MemTable cache + Bloom Filter index
  • WAL provides crash recovery with low overhead

LSM Tree disadvantages:

  • Updates require compaction to remove old versions (expensive)
  • Deletes use tombstones; actual deletion deferred to compaction
  • Read amplification: may need to check multiple SSTables
  • Write amplification: same data written multiple times (MemTable → spill file → compacted file)
  • Compaction is CPU/IO intensive — must be scheduled carefully

✏️ Practice Questions

Q1. A distributed storage system always returns data immediately but may return stale data. Which CAP properties does it prioritise? What CAP property does it sacrifice?

Prioritises: Availability (A) — always returns a response. Partition Tolerance (P) — continues operating through failures.

Sacrifices: Consistency (C) — stale data means different nodes may return different values at the same instant.

Classification: AP system — classic BASE approach (e.g., Cassandra, CouchDB).

Q2. In an LSM Tree, why is the MemTable checked before SSTables during a read? What happens if the MemTable doesn't contain the record?

Why MemTable first: The MemTable holds the most recently written records. Assuming temporal locality (recent data most likely to be needed), checking it first gives fast O(1) returns without any disk I/O. It acts as a write-through cache.

If not in MemTable:
  1. Query the Index (using Bloom Filters) to identify which SSTables might contain the key
  2. Load the candidate SSTables from disk (sequential block reads)
  3. Scan the SSTables in memory for the record

Q3. Calculate the optimal Bloom filter parameters for n=500 elements at a 1% false positive rate. Show your working.

Given: n = 500, p_fp = 0.01

Step 1 — Optimal k:
k_opt = −log₂(p_fp) = −log₂(0.01) = −(−6.644) ≈ 7 hash functions

Step 2 — Optimal m:
m_opt = −1.44 × log₂(0.01) × 500
= −1.44 × (−6.644) × 500
= 1.44 × 6.644 × 500
= 4,784 bits ≈ 4,784 bits = 598 bytes

Interpretation: We need 7 hash functions and ~598 bytes to represent 500 items with only 1% false positive rate. Extremely space efficient!

Q4. Explain the role of the Write Ahead Log (WAL) in LSM trees. What would happen if the WAL didn't exist?

WAL's role: The WAL is an append-only persistent log that records each write before it is added to the MemTable. It bridges the gap between receiving a write request and flushing the MemTable to an immutable SSTable on disk.

Without WAL: If the system crashes while the MemTable holds in-memory writes that haven't yet been flushed to disk, those writes are permanently lost. The WAL provides crash recovery — on restart, the system replays the WAL to reconstruct the MemTable state before the crash.

Key property: The WAL is sequential (append-only), so it has minimal write overhead while providing full durability guarantees.

Q5. Why can Bloom Filters produce false positives but NOT false negatives? Relate this to how they are used in LSM trees.

No false negatives: When a key K is added to the filter, specific bits are set to 1. When querying K later, we check those exact same bits. Hash functions are deterministic — K always maps to the same positions. If any of those bits were 0, K was never added (impossible if it was). So "definitely not in set" is always correct.

False positives occur: Due to hash collisions — multiple different keys may map to the same bit positions. A query key might find all its positions set to 1, but those bits were set by different keys. The filter says "possibly in set" but the key isn't actually there.

LSM Tree implication: False negatives are catastrophic (missing data), false positives are acceptable (just causes loading one extra SSTable unnecessarily). Bloom Filters' guarantee of "no false negatives" makes them perfect for this use case.
