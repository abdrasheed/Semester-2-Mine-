📊 Google BigTable

Key Shift: BigTable moves from file-based storage (NFS, GFS, HDFS) to table-based storage. This shift continues today — think Spark RDDs and Python DataFrames. Google needed faster writes than GFS provided.

4 Core Design Motivations

1. Contiguous Record Sets

Most Big Data processes read/write a contiguous set of records — similar to rows in a table. This maps naturally to a table abstraction.

2. Structured Fields (Columns)

Records usually have standard fields that could be columns in a table. Not all records will have all fields (sparse rows are fine).

3. No Explicit Relationships

Unlike SQL databases, there are no explicit relationships between fields — no need for an RDBMS or complex joins.

4. Multi-Version Records

May need to store multiple versions of a record representing it at different points in time, indexed by timestamp.

6 Key Properties of BigTable

1. Sparse

Rows can be incomplete — containing only a subset of fields. Empty cells don't waste storage.

2. Distributed

Sets of records stored as blocks, distributed amongst multiple machines for scalability.

3. Persistent

Records always stored to persistent storage — survives failures.

4. Multidimensional

Indexed through combination of RowKey + Column Name + Timestamp — 3D addressing.

5. Sorted

Records ordered lexicographically by RowKey for efficient range scans.

6. Map

Fundamentally a map from RowKeys to Records — a key-value store at its core.

Key observation: Row 000004 has no Email, Row 000005 has no Degree or Email — this is sparse storage in action. No wasted space for missing values. RowKeys are sorted lexicographically (000001 → 000006).
3D Addressing: Every cell in BigTable is addressed by: Table[RowKey, ColumnFamily:ColumnQualifier, Timestamp] → Value
This is why BigTable is called "multidimensional".

🗄️ HBase

HBase is the open-source implementation of Google's BigTable, written in Java (released by PowerSet, 2008). It runs on top of HDFS for persistent storage. Aims: maintain HDFS read speeds while providing better write/append throughput.
What HBase is NOT: No transactions, no normalization, no relational API, no proper schema. It is NOT an RDBMS. Think of it as a fast key-value table store.

HBase Architecture

👑

HMaster

Assigns regions to Region Servers. Creates/deletes tables. Routes data requests. Handles failures.

🖥️

Region Server

Handles data requests from users. Stores multiple regions. Writes to HDFS via DataNodes.

🐘

ZooKeeper

Communication bridge. Tracks state of HMaster and Region Servers. Triggers recovery on failure.

HDFS Integration

When HBase needs to write to disk: Region Servers act as HDFS clients → communicate with NameNode → write data to DataNodes. HBase is layered on top of HDFS, not a replacement.

HBase Data Model

RowKey

Unique identifier for each row. Rows ordered lexicographically. Sort happens just before write to disk.

Column Family

Columns grouped into families. Each family has its own HDFS directory: /table/region/CF/. All data for a row within a CF stored together on disk.

Cell

Combination of RowKey + Column Qualifier. Intersection of a row and column. Contains the value.

Timestamp

Recorded when data is stored. Updates write new data with new timestamp — multiple versions coexist. Latest returned by default.

Region

Contiguous sets of rows stored together. Assigned by HMaster. Managed by Region Servers. Held in memory until flushed to disk as HFile.

Version Control

Configure max versions to keep, or max age (e.g., 1 week). Acts as automatic garbage collection of old versions.

Data Ordering in HBase

Sorting is applied at 3 levels:

  1. Rows within a region: Sorted lexicographically by RowKey when written to disk
  2. Cells within a row: Sorted lexicographically by column qualifier
  3. Cells with same column qualifier: Sorted numerically by timestamp (newest first)

HBase as Key-Value Store

Two views of HBase:
  • Table abstraction (conceptually useful): Multi-dimensional table
  • Key-Value store (implementation reality): Key = <RowKey, ColumnQualifier, Timestamp> → Value = <data>
A "row" is simply all cells sharing the same RowKey — there is no true row concept internally.

HBase API

// Write operations
Put(rowkey, column_key, timestamp, value)   // Write a cell

// Read operations
Get(rowkey)                                    // Returns ALL cells of row
Get(rowkey, column_key, timestamp)           // Returns a specific cell
Get([get1, get2, get3])                       // Batch multi-get (one result per Get)

// Range scan
Scan(start_rowkey, end_rowkey)                // Returns all rows in [start, end)

// Delete operations
Delete(rowkey)                                 // Delete entire row
Delete(rowkey, timestamp)                      // Delete row at specific timestamp
Delete(rowkey, column_family)                  // Delete column family
Delete(rowkey, column_key [, timestamp])     // Delete specific column

Region Server Storage (LSM Tree)

Write-Ahead Log (WAL)

Append-only persistent log. Ensures durability between spill file writes. Used for crash recovery.

MemStore

In-memory store of most recent write records (HBase's MemTable). Checked first on reads. Flushed to HFile when full.

BlockCache

Stores recently read data in memory. Unique to HBase (not in generic LSM). Improves access time for repeated reads.

HFile

Compressed sorted spill file on HDFS. HBase's SSTable equivalent. MemStore converted to HFile when full.

🦁 ZooKeeper

ZooKeeper is a distributed key-value data store designed to be lightweight and highly reliable. Used everywhere: HBase, Spark, Flink, Reddit, Twitter, Facebook/Meta, eBay. Based on Google's Chubby service.
Core philosophy: A distributed application should NOT be responsible for tracking its own state. Use an independent service (ZooKeeper) for this — avoids 'master' services failing and bringing down the whole system.

ZooKeeper Data Model

ZNode Hierarchy

Keys structured into a hierarchical namespace. Each node in the hierarchy is a ZNode. ZNodes hold a readable/writable value. Access controlled by Access Control Lists (ACLs).

Reliability via Replication

ZooKeeper runs on ≥5 servers. One tagged as Leader, one as Follower (next if leader fails). Leader synchronises state with all servers.

ZooKeeper Use Cases (All Used by HBase)

File Locking

Hold 'Lock' message for a file while it's being written. Prevents concurrent write conflicts in distributed systems.

Global Configuration

Store configuration variables, table schemas accessible by all nodes. Single source of truth for cluster config.

File Access Controls

Store access permissions for files/tables. Enforced by reading ZooKeeper before processing requests.

Bootstrap Configuration

Store key start-up data (e.g., where master services are located). Nodes query ZooKeeper on startup to discover cluster.

Service Replica Discovery

Each service writes information about itself to ZooKeeper. Others can query to get list of active replicas.

Failure Notification

Applications register watches on ZNodes. When a node's state changes (e.g., Region Server dies), ZooKeeper notifies subscribers → triggers recovery.

🌐 DHT Overlay Networks

The Master Problem: Many Big Data systems have master services that are Single Points of Failure:
  • Hadoop Job Tracker
  • Spark Master
  • NFS Server
  • HDFS NameNode
  • HBase HMaster
DHT Solution: Build systems without a master — Peer-to-Peer (P2P) architecture.

BitTorrent Context (2001)

The most familiar P2P system. Core ideas: (1) Break file into smaller pieces, (2) Download pieces simultaneously from multiple peers, (3) Coordinate via tracker servers. Problem: tracker servers = SPOF. Solution: DHT removes even the tracker.

Consistent Hashing — Core Idea

Problem: In P2P systems, how do we distribute an index (file→location mapping) across peers without a central master?
Solution: Hash file keys to determine which peer stores the index entry for that file.

Step 1 — Hash the File Key

Apply hash function to filename (or MD5 of contents) to get a number in hash space [0, N-1]. Example: "MyFile" → hash → 36 (in space 0-99).

Step 2 — Find Responsible Peer

Peer with ID 36 stores the index entry for "MyFile". If no peer has ID 36, use peer with next highest ID.

Step 3 — Peer ID Assignment

Peers assigned IDs in the same hash space as file keys (usually same hash function applied to IP+port). On join: request all index data for your ID. On leave: pass index data to successor.

What This Creates — DHT

A Distributed Hash Table where different rows of the index are distributed among peers. No master required. Any peer can be found deterministically.

Overlay Network

The DHT gives us: file key → peer ID. But we still need: peer ID → IP address.
An Overlay Network is an additional protocol (set of rules) allowing peers to be found in the network given only their peer ID.

Simple Linear Lookup — O(n) Problem

Linear Chain Approach

Simplest design: each peer only knows the IP of the peer with the next highest ID (its successor). Requests hop around the ring until the target peer is reached.

Peer 1 → asks Peer 12
Peer 12 → asks Peer 18
Peer 18 → asks Peer 25 ← TARGET
Peer 25 → returns data to Peer 1

Problem: O(n) hops where n = number of peers. Extremely slow for large networks.

Finger Tables — O(log N) Solution

Optimization: Instead of knowing only 1 successor, store information about m = log₂N other peers. This reduces lookup from O(n) to O(log₂ N) hops.
The i-th entry in finger table of peer n points to peer responsible for ID:
finger[i] = (n + 2^(i−1)) mod 2^m
Lookup time in N-peer network:
O(log₂ N) hops
Number of entries per peer: m = log₂ N

Example Finger Table — Peer N8 (m=6, IDs 0–63)

i Formula: N8 + 2^(i-1) mod 64 → Points to
18 + 1 = 9N14
28 + 2 = 10N14
38 + 4 = 12N14
48 + 8 = 16N21
58 + 16 = 24N32
68 + 32 = 40N42
Intuition behind O(log N): With m-bit IDs, the maximum ring distance is 2^m. At each step, the finger table lets the query jump to the peer closest to but not exceeding the target — effectively halving the remaining search distance each hop. This achieves O(log N) without any global knowledge of the network.

DHT Summary — No Master Required

No SPOF

No single master to fail. Any peer failing just shifts its index to its successor.

No Global Knowledge

No node knows which nodes are in cluster, what data is stored, load of each node, or which nodes failed.

Scalable

Adding peers: new peer requests index data for its ID. O(log N) lookup regardless of cluster size.

Redundancy

Multiple hash functions select multiple peers for each key — provides replication without central coordination.

📋 Past Exam Questions & Model Answers

[2025 Exam Q] Describe the BigTable data model. What are its 6 key properties and why is the shift from file-based to table-based storage significant? (10 marks)

Model Answer

Significance of shift: Moving from file-based storage (NFS, GFS, HDFS) to table-based storage reflects how Big Data processes actually work: they read and write contiguous sets of structured records. Table abstraction also continues in Spark RDDs and Python DataFrames — a fundamental conceptual shift in Big Data thinking.

Data Model: BigTable is a sparse, distributed, persistent, multidimensional sorted map. Each cell addressed by: Table[RowKey, ColumnFamily:ColumnQualifier, Timestamp] → Value.

6 Properties:

  • Sparse: Rows can be incomplete; missing fields don't waste space
  • Distributed: Records stored as blocks across multiple machines
  • Persistent: Always stored to persistent storage
  • Multidimensional: Indexed by RowKey + ColumnName + Timestamp
  • Sorted: Records ordered lexicographically by RowKey for range scans
  • Map: Fundamentally a map from RowKeys to Records (key-value store)

Why no RDBMS needed: Big Data records often have no explicit relationships between fields — joins are expensive at scale. BigTable provides structure without relational overhead.

[2024 Exam Q] Describe HBase's architecture. How does it implement LSM Trees and how does it relate to HDFS? (12 marks)

Model Answer

Architecture components:

  • HMaster: Assigns regions to Region Servers, creates/deletes tables, routes requests, handles failures
  • Region Server: Handles data requests, stores multiple regions, writes to HDFS
  • ZooKeeper: Tracks state of all components, triggers recovery on failure, communication bridge

LSM Tree implementation:

  • WAL (Write-Ahead Log): Append-only crash recovery log — fast sequential writes
  • MemStore: In-memory buffer (HBase's MemTable) — checked first on reads, flushed to HFile when full
  • BlockCache: Recently read data cache — unique HBase addition for read optimization
  • HFile: Compressed sorted spill files on HDFS (HBase's SSTable)
  • Compactor: Background merges HFiles, removes tombstones and old versions

Relation to HDFS: HBase sits on top of HDFS. When Region Servers need to persist data, they write HFiles to HDFS (communicating with NameNode → DataNodes). HDFS provides the durable storage layer; HBase provides the table abstraction and LSM-based write acceleration.

[2023 Exam Q] Explain what ZooKeeper is and why it is important in distributed Big Data systems. Give three specific use cases. (8 marks)

Model Answer

Definition: ZooKeeper is a lightweight, highly reliable distributed key-value data store where applications can be notified when values change. Based on Google's Chubby service.

Importance: Distributed applications should NOT track their own state — this creates fragility (master failure brings down system). ZooKeeper provides an independent, replicated state tracking service. All components report state to ZooKeeper; management services subscribe to change notifications.

Three use cases:

  • File Locking: Hold lock messages for files being written, preventing concurrent write conflicts
  • Bootstrap Configuration: Stores cluster start-up data (master locations) so new nodes can discover the cluster
  • Service Replica Discovery: Each service writes its info to ZooKeeper; others query it to get list of active replicas and detect failures

Reliability: ZooKeeper runs on ≥5 servers with leader/follower replication — it is itself highly available, making it suitable as the reliability backbone of a cluster.

[2023 Exam Q] Explain how DHT Overlay Networks work. What problem do they solve and how do Finger Tables improve performance? (12 marks)

Model Answer

Problem solved: Centralized index masters (HDFS NameNode, etc.) are Single Points of Failure. DHTs distribute the index across all peers so no single node's failure brings down the system.

How DHT works:

  • Hash file key → get a number in hash space [0, 2^m - 1]
  • Peer with that ID stores the index entry for the file
  • If no peer with that exact ID, peer with next highest ID is responsible
  • Peers are also assigned IDs via same hash function (e.g., hash of IP+port)
  • The result: a Distributed Hash Table where index rows are spread across peers

Overlay Network: DHT maps file→peerID, but we need peerID→IP. An overlay network protocol provides this routing using finger tables.

Finger Tables:

  • Simple linear approach: each peer knows only its successor → O(n) hops
  • Finger table: each peer stores log₂N entries pointing to exponentially distant peers
  • Entry i points to peer responsible for: (n + 2^(i-1)) mod 2^m
  • Each lookup halves the remaining distance → O(log₂ N) hops
  • Each peer stores only log₂N entries — no global knowledge needed
[2022 Exam Q] Compare HBase and HDFS. When would you use each? (8 marks)

Model Answer

AspectHBaseHDFS
AbstractionTable (rows, columns, timestamps)File system (files, blocks)
Random writesSupported via LSM TreeNot supported (write-once)
LatencyLower (ms range)Higher (optimized for batch)
Access patternPoint reads/writes by row keyLarge sequential batch reads

Use HDFS when: Processing large files sequentially (MapReduce, log analysis, batch ETL). Throughput over latency.

Use HBase when: Need fast random read/write access to individual records (e.g., real-time lookups, serving layer for web applications). Also when data is sparse (varying columns per record).

Note: HBase runs ON TOP of HDFS — they are not mutually exclusive. HBase uses HDFS for its HFiles (SSTables), providing a table abstraction above HDFS's file storage.

✏️ Practice Questions

Q1. A BigTable row has RowKey="user_0042", with values for "Name" and "Email" but not "Phone" or "Address". What BigTable property does this demonstrate? How is this more efficient than a traditional RDBMS row?

Property demonstrated: Sparse
In BigTable, rows can be incomplete — containing only a subset of fields. An empty "Phone" or "Address" column consumes no storage space at all.

RDBMS comparison: In a traditional relational database, a row must have a value (or explicit NULL) for every column in the table. NULLs still consume storage space and must be included in schema checks and query results. At Big Data scale with millions of sparse records, RDBMS NULLs waste significant storage. BigTable's sparse model stores only actual data — missing values don't exist.

Q2. Explain the role of ZooKeeper in an HBase cluster. What would happen if ZooKeeper failed?

ZooKeeper's role in HBase:
ZooKeeper acts as the communication and coordination backbone:
  • Tracks state of HMaster and all Region Servers
  • Triggers recovery when a Region Server or HMaster fails
  • Stores bootstrap configuration (where HMaster is located)
  • Manages file locks and access controls
  • Enables service discovery (Region Server registry)
If ZooKeeper failed: The HBase cluster would lose its coordination layer. New clients couldn't discover the HMaster. Region Server failures wouldn't trigger recovery. The cluster might continue serving existing connections briefly but would quickly degrade. This is why ZooKeeper runs on ≥5 servers with leader replication — it must itself be highly available since everything depends on it.

Q4. What is the difference between MemStore and BlockCache in HBase? Why does HBase have BlockCache when the generic LSM Tree doesn't?

MemStore: Stores the most recently written records in memory. Acts as the LSM Tree's MemTable. Write requests go here first; flushed to HFile when full. Optimizes write performance.

BlockCache: Stores recently read data blocks in memory. Reduces repeated disk reads for frequently accessed data. Optimizes read performance for repeated access patterns.

Why HBase has BlockCache (generic LSM doesn't): HBase is designed as a general-purpose table store serving many concurrent clients (web applications, real-time systems). Many clients will read the same popular rows repeatedly (e.g., user profile lookups). BlockCache is a read-through cache that exploits temporal locality in access patterns. A generic LSM tree like Cassandra also has read caches, but it's an application-level addition on top of the pure LSM structure — in HBase, it's a first-class architectural component due to its use case as a serving store.

Q5. HBase performs multi-version storage. Describe how versions are used and what happens if you do three consecutive writes to the same cell (RowKey="user1", Col="age") with values 25, 26, 27.

Multi-version mechanism: When data is updated, HBase does NOT overwrite the old value in-place. Instead, it writes a new cell with the same RowKey and column qualifier but a new (higher) timestamp.

Three consecutive writes:
RowKeyColumnTimestampValue
user1ageT3 (newest)27
user1ageT226
user1ageT1 (oldest)25
Default behavior: Get("user1") returns value 27 (latest timestamp).
Time travel: Get("user1", "age", T1) returns 25.
Cleanup: If max_versions=1 is configured, the Compactor will eventually purge versions 25 and 26. If max_age=7days, versions older than 7 days are purged during compaction.
