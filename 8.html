Introduction to Information Extraction

What is Information Extraction?

Information Extraction (IE) is the task of automatically extracting structured information from unstructured or semi-structured text. It bridges the gap between human-readable text and machine-processable data.


Core Idea ("Machine Reading"): Transform raw, unstructured text into structured databases or knowledge graphs that computers can query, reason over, and use for downstream tasks.

Unstructured Input

"Boeing CEO Kelly Ortberg said the company plans to resume production of the 737 MAX. He replaced former CEO Dave Calhoun. They also intend to produce Air Force One."

Structured Output

Kelly Ortbergis_ceo_ofBoeing
Dave Calhounwas_ceo_ofBoeing
Boeingproduces737 MAX
Boeingintends_to_produceAir Force One

Named Entity Recognition (NER)

Two Sub-problems

1. Span Detection

Find the character offsets of entities in text. Where does the entity begin and end?

2. Type Classification

Assign a semantic type to each detected span: PER ORG LOC DATE etc.

Dictionary-Based Approach

Advantages ✓

  • No training data needed
  • Directly enables entity linking
  • Fast lookup with hash tables
  • Easy to update with new entities

Disadvantages ✗

  • No use of context information
  • Need exhaustive list of entities
  • Ambiguity: Paris (France vs Texas)
  • Surface form variation: NYC vs New York
Key Ambiguity Problem: "Paris" could be Paris, France (capital city) or Paris, Texas (US city) or Paris of Troy (mythology). Dictionary lookup alone cannot resolve this — context is needed!

spaCy NER — Python Code

import spacy

# Load a pre-trained English model (run: python -m spacy download en_core_web_sm)
nlp = spacy.load("en_core_web_sm")


def run_ner(text: str) -> list[dict]:
    """Run NER and return entity spans as a list of dicts."""
    doc = nlp(text)
    return [
        {
            "text":  ent.text,
            "label": ent.label_,   # PERSON, GPE, ORG, DATE, ...
            "start": ent.start_char,
            "end":   ent.end_char,
        }
        for ent in doc.ents
    ]


# Example usage
sentence = "Robert Burns was born in Alloway in 1759."
for entity in run_ner(sentence):
    print(f"{entity['text']:15s}  {entity['label']:8s}  "
          f"chars {entity['start']}-{entity['end']}")

# Robert Burns    PERSON    chars 0-12
# Alloway         GPE       chars 24-31
# 1759            DATE      chars 35-39

Span Recovery from IOB Tags

Given IOB-tagged tokens, how do we recover entity spans?

def recover_spans(tokens: list[str], iob_tags: list[str]) -> list[dict]:
    """
    Convert parallel token + IOB-tag lists into entity span dicts.
    Each span dict has keys: 'text', 'type', 'start', 'end'.
    Handles adjacent B-tags (two separate entities) and orphan I-tags.
    """
    spans = []
    active = None   # currently open span

    for idx, (token, tag) in enumerate(zip(tokens, iob_tags)):
        if tag.startswith("B-"):
            if active:                          # close previous span first
                spans.append(active)
            active = {
                "text":  token,
                "type":  tag[2:],               # strip the "B-" prefix
                "start": idx,
                "end":   idx,
            }
        elif tag.startswith("I-") and active:
            active["text"] += " " + token       # extend the current span
            active["end"]   = idx
        else:                                   # "O" tag or orphan "I-"
            if active:
                spans.append(active)
            active = None

    if active:                                  # flush any trailing span
        spans.append(active)

    return spans


# Example
tokens = ["adele", "went", "to", "paris", "berlin", "and", "new", "york", "city"]
tags   = ["B-PER", "O",    "O",  "B-LOC", "B-LOC",  "O",   "B-LOC","I-LOC","I-LOC"]

for span in recover_spans(tokens, tags):
    print(span)
# {'text': 'adele',         'type': 'PER', 'start': 0, 'end': 0}
# {'text': 'paris',         'type': 'LOC', 'start': 3, 'end': 3}
# {'text': 'berlin',        'type': 'LOC', 'start': 4, 'end': 4}

HMM for NER

Hidden Markov Model Structure

  • Hidden states = IOB tags (y₁, y₂, ..., yₙ)
  • Observed states = words in text (x₁, x₂, ..., xₙ)
  • Transition probability: P(yᵢ | yᵢ₋₁) — probability of moving from one tag to the next
  • Emission probability: P(xᵢ | yᵢ) — probability of a word given a tag

HMM Structure Diagram (SVG)

HMM Probability Equations

$$P(\mathbf{x}, \mathbf{y}) = P(y_1) \prod_{i=2}^{n} P(y_i \mid y_{i-1}) \prod_{i=1}^{n} P(x_i \mid y_i)$$
$$\mathbf{y}^* = \arg\max_{\mathbf{y}} P(\mathbf{y} \mid \mathbf{x}) = \arg\max_{\mathbf{y}} P(\mathbf{x}, \mathbf{y})$$

Solved efficiently using the Viterbi algorithm (dynamic programming, O(n·K²) where K = number of states).

Limitations of HMM for NER

Cannot use extra features! HMMs only look at the word itself (emission) and the previous tag (transition). They cannot incorporate:
  • Capitalization: "Bath" (city) vs "bath" (common noun) — same word, different case
  • Part-of-speech tags: knowing a word is a proper noun helps NER
  • Text type / document context: a sports news article vs medical journal
  • Surrounding context words: "Dr." before a name strongly suggests a person
  • Word morphology: suffixes like "-shire", "-ville" suggest locations

CRF for NER

Conditional Random Field (CRF)

CRFs are discriminative models that overcome HMM limitations by allowing arbitrary feature functions over the entire input sequence.

$$P(\mathbf{y} \mid \mathbf{x}) = \frac{1}{Z(\mathbf{x})} \exp\left(\sum_k w_k \cdot f_k(\mathbf{y}, \mathbf{x})\right)$$

where $Z(\mathbf{x})$ is the partition function (normalizer), $w_k$ are learned weights, and $f_k$ are feature functions.

CRF Feature Extraction Code

def extract_crf_features(
    tokens: list[str],
    position: int,
    prev_label: str,
) -> dict:
    """
    Build a feature dict for one token — fed directly to sklearn-crfsuite.
    CRFs support arbitrary features (unlike HMMs limited to word identity).

    Args:
        tokens:     All tokens in the sentence.
        position:   Index of the current token (0-based).
        prev_label: Predicted label for the previous token ('O' at start).
    """
    token = tokens[position]
    n     = len(tokens)

    features = {
        # Orthographic (capitalisation, digit, punctuation)
        "token":               token.lower(),
        "starts_with_capital": token[0].isupper(),
        "is_all_caps":         token.isupper(),
        "is_digit":            token.isdigit(),
        "contains_hyphen":     "-" in token,

        # Morphological (suffix / prefix signal entity types)
        "suffix_2": token[-2:] if len(token) >= 2 else token,
        "suffix_3": token[-3:] if len(token) >= 3 else token,
        "prefix_2": token[:2]  if len(token) >= 2 else token,
        "prefix_3": token[:3]  if len(token) >= 3 else token,

        # Context window (neighbouring words)
        "prev_token": tokens[position - 1].lower() if position > 0     else "BOS",
        "next_token": tokens[position + 1].lower() if position < n - 1 else "EOS",

        # Sequence position
        "is_first":   position == 0,
        "is_last":    position == n - 1,
        "prev_label": prev_label,   # Markov chain: depend on previous tag
    }
    return features


# Example
tokens = ["Glasgow", "University", "is", "old"]
feats  = extract_crf_features(tokens, position=0, prev_label="O")
print(feats["starts_with_capital"])  # True
print(feats["suffix_3"])             # "gow"
print(feats["prefix_3"])             # "Gla"

# CRF predicts one of: {B-PER, I-PER, B-LOC, I-LOC, B-ORG, I-ORG, O}

NER Evaluation

Token-Level Evaluation

Evaluate each IOB tag prediction independently.

$$\text{Precision} = \frac{TP}{TP + FP}$$ $$\text{Recall} = \frac{TP}{TP + FN}$$ $$F_1 = \frac{2 \cdot P \cdot R}{P + R}$$
Problem: Token-level F1 is tokenizer-dependent. "New York City" tokenized differently affects scores.

Span-Level Evaluation

A span prediction is correct only if both the boundaries and type match exactly.

  • TP: Predicted span matches gold span exactly
  • FP: Predicted span not in gold
  • FN: Gold span not predicted
Preferred: Span-level evaluation is more meaningful for practical NER systems.

Practice Q3 — Why is Token-Level Eval Problematic? [Exam Style]

System A uses WordPiece tokenization; System B uses whitespace tokenization. Both make the same error. Why can't you directly compare their token-level F1 scores?

Show Answer ▼

Token-level F1 counts per-token predictions. "New York City" is 3 tokens under whitespace tokenization but might be 4+ sub-word tokens under WordPiece. A wrong prediction on this span contributes different numbers of FP/FN tokens depending on the tokenizer, making cross-system comparison invalid. Span-level evaluation avoids this by operating on character offsets instead.

Entity Linking

From Strings to Things

Entity Linking (EL), also called wikification or entity disambiguation, maps entity mentions in text to unique entries in a Knowledge Base.

💊
"aspirin"
→ acetylsalicylic acid (chemical structure)
🎨
"red"
→ color #FF0000 (RGB concept)
🗺️
"Paris"
→ Paris, France (Q90 in WikiData)

The Candidate Generation Problem

The same surface form can refer to many different entities:

"Paris" could be:
  • 🇫🇷 Paris, France — capital city (most common)
  • 🤠 Paris, Texas — city in Lamar County, Texas
  • ⚔️ Paris of Troy — figure in Greek mythology
  • 🎭 Paris Hilton — celebrity (her first name)
  • 🎬 Paris (film) — multiple films named Paris
Solution: Use aliases from the KB (NYC = "New York City" = "Big Apple" = "the five boroughs") combined with context to disambiguate.

Entity Linking as Retrieval

EL is analogous to Information Retrieval (IR), but over a Knowledge Base instead of a document collection:

IR conceptEL equivalent
QueryEntity mention in text (e.g. "NYC")
Document collectionKnowledge Base (WikiData, Wikipedia)
Relevant documentCorrect KB entity (New York City)
RankingScore candidates by context similarity

Section 12

Entity Linking Methods

Method 1: Sparse Retrieval (TF-IDF)

  • Represent entity mention as character n-gram bag
  • Represent KB entities using their descriptions/aliases
  • Compute TF-IDF vectors and cosine similarity
$$\text{sim}(\mathbf{a}, \mathbf{b}) = \frac{\mathbf{a} \cdot \mathbf{b}}{|\mathbf{a}| \cdot |\mathbf{b}|}$$

Method 2: Dense Retrieval (Bi-encoder)

Encode both the entity mention and KB entities into dense vectors using transformers, then use dot-product similarity for efficient retrieval (using ANN search like FAISS).

Method 3: Cross-Encoder Reranker

After candidate generation, a cross-encoder jointly encodes the mention and each candidate entity to produce a fine-grained relevance score.

Input: [E]NYC[/E] to see the Statue of Liberty [SEP] new york city, city in USA
Output: score = 0.89 → Correct entity: New York City
Pipeline: Bi-encoder → top-k candidates → Cross-encoder reranker → best entity
(Josifoski et al., EMNLP 2020)

$$\text{Accuracy@1} = \frac{\text{# mentions correctly linked at rank 1}}{\text{total mentions}}$$ $$\text{Accuracy@k} = \frac{\text{# mentions where correct entity in top-k}}{\text{total mentions}}$$
Challenges:
  • NIL entities: mention doesn't match any KB entry (e.g. very new or obscure entities)
  • Nested entities: "University of Glasgow" ⊃ "Glasgow" — which span to link?

Entity Linking Code — Candidate Generation

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

# Knowledge base: entity_id -> description text
kb = {
    "Q90":     "Paris France capital city Europe Seine river",
    "Q44989":  "Paris Texas city United States Red River",
    "Q170217": "Paris Troy mythology Greek hero Trojan War",
}
kb_ids   = list(kb.keys())
kb_texts = list(kb.values())

# Build TF-IDF index using character n-grams (robust to spelling variants)
vectorizer = TfidfVectorizer(analyzer="char_wb", ngram_range=(3, 5))
kb_matrix  = vectorizer.fit_transform(kb_texts)   # sparse matrix


def link_entity(mention_context: str, top_k: int = 3) -> list[tuple[str, float]]:
    """
    Rank KB candidates for a mention using TF-IDF cosine similarity.

    Args:
        mention_context: Mention text + surrounding context words.
        top_k:           Number of candidates to return.

    Returns:
        List of (entity_id, score) sorted by descending similarity.
    """
    mention_vec = vectorizer.transform([mention_context])
    scores      = cosine_similarity(mention_vec, kb_matrix)[0]
    ranked      = sorted(zip(kb_ids, scores), key=lambda x: x[1], reverse=True)
    return [(entity_id, round(score, 4)) for entity_id, score in ranked[:top_k]]


# Example
results = link_entity("Paris visited trip France Eiffel Tower")
for rank, (entity_id, score) in enumerate(results, 1):
    print(f"Rank {rank}: {entity_id}  score={score:.4f}")
# Rank 1: Q90     score=0.8xxx  <- Paris, France
# Rank 2: Q44989  score=0.xxxx
# Rank 3: Q170217 score=0.xxxx

Practice Q4 — Bi-encoder vs Cross-encoder [Exam Style]

Explain why a bi-encoder is used for candidate generation but a cross-encoder is used for reranking. What is the key trade-off?

Show Answer ▼

Bi-encoder: Encodes mention and KB entity independently. This allows all KB entities to be pre-encoded and stored. At inference, only the mention needs encoding; dot-product retrieval over millions of entities is fast (ANN with FAISS). Downside: the two representations never directly interact during encoding — contextual interactions between mention and entity are missed.

Cross-encoder: Encodes mention + entity description jointly as one sequence — the transformer's self-attention can model fine-grained interactions. This gives much higher accuracy. Downside: can't pre-encode; must re-run for every candidate at query time — too slow to apply to all KB entities.

Trade-off: Bi-encoder = fast but less accurate (candidate generation). Cross-encoder = slow but more accurate (reranking only top-k candidates).

Practice Q5 — What is Accuracy@k? [Exam Style]

A system is tested on 200 entity mentions. The correct entity is in the top-1 result 130 times, and in the top-5 results 170 times. Calculate Accuracy@1 and Accuracy@5.

Show Answer ▼
$$\text{Accuracy@1} = \frac{130}{200} = 0.65 \qquad \text{Accuracy@5} = \frac{170}{200} = 0.85$$

The gap between @1 and @5 (0.20) shows there is room for a better reranker — 20% of mentions have the right answer ranked 2–5 but not at rank 1.

Why is Relation Extraction Hard?

  • Many surface forms: "born in", "is a native of", "was born on", "hails from" all express birthPlace
  • Ambiguity: "Apple acquired Beats" vs "Apple beats expectations"
  • Reasoning: "X CEO resigned. Y was named his successor" → Y is_ceo_of company of X
  • Long sentences: Subject and object can be far apart with complex syntax

Knowledge Triples

Relations are represented as (subject, relation, object) triples:

Reykjavikcapital_ofIceland
Kelly Ortbergis_ceo_ofBoeing
Florence Nightingaleborn_inFlorence
Boeingheadquartered_inArlington, VA

Entity Types as Filter

Entity types constrain which relation extraction is valid:

✓ Valid
"Michael J Fox born in Canada"
PERSON + COUNTRY → born_in is sensible
✗ Invalid
"Michael J Fox born in Star Wars"
PERSON + FILM → born_in is semantically wrong

N-ary Relations → Binary Decomposition

Complex relations like "Boeing appointed Kelly Ortberg as CEO" involve 3+ entities:

"<company> appointed <person> as <position>"
Decomposed into binary triples:
Kelly Ortberghas_positionCEO
Kelly Ortbergworks_forBoeing
BoeingappointedKelly Ortberg

Co-occurrence — Blunt Tool

Counting how often two entities appear in the same document/sentence gives a signal, but:

from collections import Counter


def count_cooccurrences(
    documents: list[str],
    entity_pairs: list[tuple[str, str]],
) -> list[tuple]:
    """
    Count how often each entity pair co-occurs in the same sentence.

    Limitations:
    - Does NOT reveal WHAT the relation is, only that entities co-appear.
    - Popular entities fire everywhere (Google, US) -> many false positives.
    - Example FP: "Google Maps on my Apple iPhone" != a real Google-Apple relation.
    """
    counts: Counter = Counter()

    for doc in documents:
        sentences = [s.strip() for s in doc.split(".") if s.strip()]
        for sent in sentences:
            lower = sent.lower()
            for e1, e2 in entity_pairs:
                if e1.lower() in lower and e2.lower() in lower:
                    # Use a sorted canonical key so (A,B) == (B,A)
                    key = tuple(sorted([e1, e2]))
                    counts[key] += 1

    return counts.most_common()


# Example
docs = [
    "Boeing CEO Kelly Ortberg announced new plans. Based in Arlington.",
    "Kelly Ortberg replaced Dave Calhoun at Boeing. Calhoun led since 2020.",
    "Boeing will produce the 737 MAX. Kelly Ortberg confirmed the timeline.",
]

Relation Extraction Methods

Hearst Patterns (Pattern Bootstrapping)

Lexico-syntactic patterns for extracting specific relations. Named after Marti Hearst (1992) who used them for hyponymy (is-a) extraction.

Bootstrap loop:
Choose relation → Gather entity pairs → Find sentences → Extract patterns → Use patterns → Repeat
PatternRelationExample
X such as Yhypernym(X,Y)"cities such as Paris"
Y and other Xhypernym(X,Y)"Paris and other cities"
X, especially Yhypernym(X,Y)"capitals, especially Paris"
X including Yhypernym(X,Y)"countries including France"
import re

# Hearst patterns: group(1)=hypernym, group(2)=hyponyms
# Exception: "and_other" pattern has groups reversed (see below)
HEARST_PATTERNS = [
    ("such_as",    re.compile(r"([\w\s]+?)\s+such as\s+([\w\s]+(?:,\s*[\w\s]+)*(?:\s+and\s+[\w\s]+)?)",    re.I)),
    ("including",  re.compile(r"([\w\s]+?)\s+including\s+([\w\s]+(?:,\s*[\w\s]+)*(?:\s+and\s+[\w\s]+)?)",  re.I)),
    ("and_other",  re.compile(r"([\w\s]+?)\s+and other\s+([\w\s]+)",                                        re.I)),
    ("especially", re.compile(r"([\w\s]+?),\s+especially\s+([\w\s]+(?:,\s*[\w\s]+)*(?:\s+and\s+[\w\s]+)?)",re.I)),
]
SPLIT = re.compile(r",\s*|\s+and\s+")  # splits "A, B, and C" into [A, B, C]


def extract_hearst_pairs(text: str) -> list[tuple[str, str]]:
    """
    Extract (hypernym, hyponym) is-a pairs using Hearst patterns (Hearst 1992).
    Returns list of (hypernym, hyponym) tuples, lowercase and stripped.

    Example:
        extract_hearst_pairs("languages such as Python, Java, and C++")
        -> [('languages', 'python'), ('languages', 'java'), ('languages', 'c++')]
    """
    pairs = []
    for name, pattern in HEARST_PATTERNS:
        for m in pattern.finditer(text):
            g1, g2 = m.group(1).strip().lower(), m.group(2).strip().lower()
            if name == "and_other":
                pairs.append((g2, g1))          # roles are swapped for this pattern
            else:
                for hypo in SPLIT.split(g2):
                    if hypo.strip():
                        pairs.append((g1, hypo.strip()))
    return pairs


# Example
text = "Programming languages such as Python, Java, and C++ are popular."
for hypernym, hyponym in extract_hearst_pairs(text):
    print(f"  {hyponym!r:20s}  is-a  {hypernym!r}")
# 'python'              is-a  'programming languages'
# 'java'                is-a  'programming languages'
# 'c++'                 is-a  'programming languages'

Supervised Relation Extraction

Binary Classification

One relation type. Predict: does this entity pair exhibit this relation? (0 or 1)

Example: Born_In(person, location) — binary yes/no for each entity pair candidate.

Multi-class Classification

Multiple relation types, each pair has exactly one relation (or none).

Example: Given entity pair (Florence Nightingale, Florence), predict one of: {born_in, lives_in, works_in, named_after, none}

Multi-label Classification

Multiple relation types, each pair can have zero or more relations simultaneously.

Example: A person can be both born_in and educated_in the same city.

BERT Relation Classifier

Special entity markers wrap the entities, then [CLS] representation is used for classification:

[CLS] [E1]Florence Nightingale[/E1] was named for her birthplace [E2]Florence[/E2] [SEP]
→ named_after: 0.73 
import torch
from transformers import AutoTokenizer, AutoModelForSequenceClassification

# Relation labels (index = class ID used by the model)
RELATION_TYPES = ["no_relation", "born_in", "works_for",
                  "located_in", "named_after", "capital_of"]

# Load BERT checkpoint fine-tuned for relation extraction
# (In practice use a TACRED-fine-tuned model, e.g. "jean-baptiste/roberta-large-ner-english")
tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
model     = AutoModelForSequenceClassification.from_pretrained(
    "bert-base-uncased", num_labels=len(RELATION_TYPES)
)
model.eval()  # disable dropout for inference


def classify_relation(sentence: str, entity1: str, entity2: str) -> tuple[str, float]:
    """
    Predict the relation between two entities in a sentence.

    Key idea: wrap entities with markers so BERT knows which pair to classify.
    The [CLS] representation is then used for softmax classification.

    Args:
        sentence: Full sentence containing both entities.
        entity1:  Subject entity string.
        entity2:  Object entity string.

    Returns:
        (relation_label, confidence_score)
    """
    # Step 1: mark entities with positional markers
    marked = sentence.replace(entity1, f"[E1]{entity1}[/E1]", 1)
    marked = marked.replace(entity2, f"[E2]{entity2}[/E2]", 1)

    # Step 2: tokenise and run BERT
    inputs  = tokenizer(marked, return_tensors="pt", truncation=True, max_length=512)
    with torch.no_grad():
        logits = model(**inputs).logits         # shape: (1, num_labels)

    # Step 3: softmax -> pick top class
    probs = torch.softmax(logits, dim=-1)[0]    # shape: (num_labels,)
    best  = int(probs.argmax())
    return RELATION_TYPES[best], round(float(probs[best]), 4)


# Example
sentence = "Florence Nightingale was named for her birthplace Florence."
relation, confidence = classify_relation(sentence, "Florence Nightingale", "Florence")
print(f"Relation : {relation}")       # named_after  (with fine-tuned model)
print(f"Confidence: {confidence:.4f}")

# Marked input fed to BERT:
# [CLS] [E1]Florence Nightingale[/E1] was named for her birthplace [E2]Florence[/E2] [SEP]

Coreference Resolution

The Challenge

Coreference resolution determines which mentions in a text refer to the same entity. This is essential for understanding full document meaning.

"The bee landed on the flower because it had pollen."
→ it = flower (it's the flower that has pollen)
"Bill was robbed by John, so officer arrested him."
→ him = John (the one who committed the crime)
"Jim was afraid of Bob because he gets scared around new people."
→ he = Jim (it's Jim who gets scared)

The Winograd Schema

Winograd schemas require world knowledge and commonsense reasoning to resolve — a well-known challenge for AI systems.

"The trophy doesn't fit into the brown suitcase because it's too large."

What does "it" refer to?

"The trophy doesn't fit into the brown suitcase because it's too small."

What does "it" refer to?

Note that just one word changed ("large" → "small"), but the answer flips! This requires size-based reasoning.

Reference Types

TypeDefinitionExample
CoreferenceTwo mentions refer to same real-world entity"Gates ate a bagel. Bill said it was great."
AnaphoraA mention (anaphor) refers BACK to a previous mention (antecedent)"Bill ate a bagel. He drank tea."
CataphoraA mention refers FORWARD to a later mention"Before he left, John checked his phone."
ExophoraReference to something outside the text entirely"They say it'll rain." (they = society/people)

Hobbs Algorithm

Hobbs (1978) — Rule-Based Pronoun Resolution

  1. Begin at the NP or S node immediately dominating the pronoun
  2. Go up the tree to the first NP or S node encountered
  3. Traverse all branches to the left of this node in a left-to-right, BFS order
  4. Propose as antecedent any NP node that is encountered which has a NP or S node between it and the previous position
  5. If no antecedent found, go to previous sentence and repeat tree traversal
  6. Accept first candidate matching gender and number agreement

Parse Tree Visualization (SVG)

Sentence: "The dog chased the cat. It was fast."

Hobbs traverses left from "It" in S₂, goes up to S₁, then BFS left-to-right finds "the dog" (NP₁) as the first matching NP with correct gender/number.

Hobbs: Strengths and Weaknesses

Strengths

  • Fast, deterministic
  • No training data needed
  • Linguistically motivated
  • Works well for clear cases

Weaknesses

  • No semantic knowledge
  • Only handles pronouns
  • Requires a parse tree
  • Fails on complex semantics (Winograd)

Clustering Approach

  1. Start: each mention in its own cluster
  2. For each mention pair, compute ML-based compatibility score
  3. Merge the two most compatible clusters
  4. Repeat until stopping criterion met

2023 Exam — Q3(e) context — BERT POS NER + BERT
Without using an ensemble approach, how might you include explicit parts-of-speech into a BERT-based NER model? How does this differ from the approach used in a CRF-based model?
Model Answer ▼

CRF approach: Each (word, POS-tag) pair becomes a separate binary feature in a sparse feature vector. The CRF sees e.g. feature token=Nations, POS=NNP as individual feature dimensions.

BERT approach: BERT models sequences of word embeddings. To incorporate POS, a new POS embedding bank (one embedding vector per POS tag) can be introduced — analogous to segment/positional embeddings — and added to the input token embeddings before the transformer layers. This way, each token's representation combines its WordPiece embedding + its POS embedding.

Key distinction: CRF uses one-hot / sparse features; BERT uses dense embedding addition at the input layer.
2022 Exam — Q3(c) — 4 marks NER: Domain Mismatch
You apply a 97%-accurate off-the-shelf POS tagger (trained on news) to patent text. It frequently makes errors on specialised domain vocabulary. Why does this problem arise and how could you fix it?
Model Answer (4 marks) ▼

Why it arises: This is a domain mismatch (train-test distribution shift). The POS tagger was trained on news text but patents contain specialised vocabulary (technical jargon, chemical names, product terms) that was never seen during training. For unseen words, the tagger cannot make informed predictions — it defaults to its priors.

Two fixes:

  1. Fine-tuning: Annotate a sample of patent text with correct POS tags and fine-tune the existing model on this in-domain data. More data → better domain coverage.
  2. Pre/post-processing with a domain dictionary: Maintain a domain-specific lexicon that maps technical terms to their most likely POS in the patent domain. Apply this as a pre- or post-processing step to override the tagger for known terms.
This principle applies equally to NER — NER systems trained on news fail on biomedical/legal text for the same domain mismatch reason.

A coreference system produces the following clusters on a test sentence:

Gold: {Annie, her, She} | {pen} | {Troy} | {his} | {bag, it}
