Work Distribution Challenges

Parallelism sounds great in theory — but in practice, distributing work across multiple machines introduces a cascade of new problems that must be solved before we can benefit from the speed-up.

⚖️

Load Balancing

Making sure all machines have work to do — no idle cores, no bottlenecks.

📦

Overheads

Extra stages, intermediate writes, and aggregation add latency on top of compute.

🎛️

Orchestration

A master service must assign tasks to machines and respond to failures.

🌐

Transfer Latency

Data crossing network links is orders of magnitude slower than local storage.

💥

Machine Failures

Any node can fail mid-job. Work must be re-allocated automatically.

👑

Master Failures

If the orchestrator itself dies, recovery is hard — unless multiple masters exist.

Additional Stages & Their Costs

Parallel computation requires an aggregation stage that adds overhead and creates a dependency barrier — Stage 3 cannot start until all Stage 2 workers finish.

1
Data Split + Read — Each pipeline reads its chunk of data from storage
2
Parallel Computation — Each pipeline computes its local result (e.g. Count=1)
3
Aggregation (Barrier) — Cannot start until Stage 2 is complete on ALL nodes. Sum all local counts.
Key insight: The slowest pipeline dictates the total time. If Pipeline 2 processes a shorter document, it finishes early and sits idle until Pipeline 1 catches up. This is the load balancing problem.

Data Splitting & Load Balancing

To enable parallelism, split data into n chunks (where n ≥ number of pipelines). For perfect efficiency, each chunk should contain equal amounts of work.

Good Splitting ✅

  • Equal-sized chunks → equal compute time
  • Pipeline 1 and Pipeline 2 finish together
  • No idle time wasted waiting for stragglers

Bad Splitting ❌

  • Unequal chunks → one finishes early
  • Fast pipeline waits idle for slow one
  • Effective speed-up reduced significantly
Pro tip: In Hadoop, you control load balancing indirectly by adjusting how HDFS block size maps to input splits. Smaller splits = better load balancing but more task overhead.

Orchestration & Communication Overheads

Communication Costs

Every communication link between tasks adds latency. Two scenarios:

Same Machine

Data transfer goes via local disk or memory — fast but still not free. Cost depends on storage hierarchy (RAM > SSD > HDD).

Different Machines

Data must cross the network. ~100μs latency minimum. For TB-scale shuffles, this becomes the dominant bottleneck.

Master Services (Orchestrators)

Complex architectures need a master service that:

  • Tracks which machines have available slots
  • Assigns tasks to available slots on appropriate machines
  • Monitors task progress via heartbeats
  • Re-allocates work when a task fails

Orchestration Example

Machine 1 has 2 slots, Machine 2 has 2 slots, Machine 3 has 2 slots. Master assigns GetWords+Count tasks to Machines 2 & 3 (Stage 1+2), then assigns Sum to Machine 2 (Stage 3), pulling intermediate results via network transfer.

Fault Tolerance

Machine Failure

Worker Dies Mid-Task

  1. Master detects missing heartbeat
  2. Gets fresh copy of data from storage
  3. Restarts tasks on a surviving machine
Handled by the master service automatically.
Master Failure

The Orchestrator Dies

  • No recovery possible (single master)
  • Multiple masters = conflict resolution needed
  • Multiple masters waste resources on management
Single point of failure — a key Hadoop V1 limitation!
Network Failure / Partition

Master can't communicate with a machine — is it dead, or just temporarily unreachable?

  • If actually dead: re-allocate work → correct
  • If temporary glitch + work re-allocated: same work done twice (duplicate output!)

This is the classic network partition problem — handled differently by Hadoop (treat as machine failure) vs modern systems.

MapReduce: Origin Story

Setting the Scene — Early 2000s, Google

A relatively small search company is trying to scale up. Between 2000 and 2004, the Google Index grew over 20×. Buying ever-bigger mainframes is impractical — so Google invents a horizontal scaling framework.

  • 2004: Google files a patent and publishes: "MapReduce: Simplified data processing on large clusters" — Dean & Ghemawat
  • Cited 22,910+ times — one of the most influential CS papers
  • Insight: If we constrain workloads to two operations, orchestration becomes trivially solvable

The Two Operations

Core insight: The majority of distributed compute workloads can be expressed as just two operations. By limiting to these two, the framework can automatically handle all the hard orchestration problems.
MAP

Map Function

Map(Key₁, Value₁) → List[<Key₂, Value₂>]
  • Takes one input key-value pair
  • Emits zero or more output key-value pairs
  • Applied independently to each input record
  • Perfectly parallelisable — no coordination needed
Use for: Extraction, Filtering, Transformation (per-record operations)
REDUCE

Reduce Function

Reduce(Key₂, List[Value₂]) → List<Value₂>
  • Takes a key and all values associated with that key
  • Emits aggregated result(s)
  • One reducer instance per unique key
  • Can run parallel (one per key) but needs Map to complete first
Use for: Aggregation, Counting, Grouping (cross-record operations)

When to Use Each

Task TypeOperationExample
Extraction/Filtering MAP Extract tweets containing "crypto" from a 1TB dataset
Transformation MAP Apply sentiment analysis to each news article
Aggregation REDUCE Sum all word counts per word across all documents
Grouping REDUCE Collect all URLs per domain for link analysis

Word Count Example (Canonical)

Count how many times each word appears across a corpus of documents.

Map Phase Code

// Input: (docID, document_text)
// Output: list of (word, 1) pairs

class WordCountMapper {
  map(String docID, String document):
    for word in document.split(" "):
      emit(word, 1)   // emit one (word, 1) per word
}

// E.g. "Coinbase has reached crypto" →
//   (coinbase, 1), (has, 1), (reached, 1), (crypto, 1)

Reduce Phase Code

// Input: (word, [1, 1, 1, ...])  ← all 1s for that word
// Output: (word, total_count)

class WordCountReducer {
  reduce(String word, List<Integer> counts):
    total = sum(counts)
    emit(word, total)  // (crypto, 2)
}
Framework magic: Between Map and Reduce, the framework automatically groups all values by key — all (crypto, 1) pairs from all mappers are collected and sent to one reducer as (crypto, [1,1]).

Full MapReduce Pipeline

MapReduce is fault-tolerant by design — intermediate results are persistently written to storage between phases. This enables task re-execution on failure.

Map Phase

  • Read split from HDFS
  • Run user Map function
  • Sort output by key
  • Write to HDFS
→

Shuffle

  • HDFS stores Map output
  • Copy by key to reducers
  • Network transfer
  • Group by key
→

Reduce Phase

  • Read from HDFS
  • Run user Reduce function
  • Write final output to HDFS

Why Intermediate Storage Matters for Fault Tolerance

If a Reduce task fails halfway through, the system can re-read the Map outputs from HDFS and re-run just that reducer. Without persistent intermediate storage, a failure mid-pipeline would require restarting everything from the beginning.

The cost: Every MapReduce job incurs 2× HDFS read + 2× HDFS write + network shuffle, even for simple computations. This is Hadoop's biggest weakness.

MapReduce Use Cases & Examples

Web Index Building (Google)

Map: (URL, page_html) → emit(word, docID) for each word
Reduce: (word, [docIDs]) → inverted index entry

Log Analysis

Map: (lineNum, logline) → if ERROR: emit(error_type, 1)
Reduce: (error_type, [1,1,...]) → count per error type

Market Data Aggregation

Map: (txID, transaction) → emit(stock, price)
Reduce: (stock, [prices]) → min, max, avg, VWAP

Social Network Graph

Map: (userID, friends_list) → emit(friend, userID)
Reduce: (user, [friends]) → mutual friends calculation

Hadoop: History & Context

Why Google Didn't Release the Code

Google published the MapReduce design in 2004 — but kept their implementation closed-source. This was deliberate: MapReduce was a competitive advantage.

  • Other companies saw the utility and built their own internal versions
  • Including Google's main competitor at the time: Yahoo!
  • Yahoo! released their Java implementation as open source in April 2006
  • Named it Hadoop (after a toy yellow elephant belonging to one of the developer's children)
Hadoop V1 = MapReduce (Java) + HDFS. The same distributed file system (HDFS) stores input data, intermediate Map outputs, and final Reduce outputs.

Popularity Trajectory

Hadoop peaked around 2014-2015, then declined as developers moved to Apache Spark (10-100× faster for iterative workloads). Still in production at many enterprises today — particularly for batch ETL on HDFS.

Hadoop Architecture

Hadoop separates concerns into Compute and Storage layers, each with their own master and worker nodes.

Compute Layer

Client

User-facing software. Submits jobs to the JobTracker. Communicates job requirements.

Job Tracker (Master)

Receives jobs from Client. Queries NameNode for data locations. Assigns tasks to TaskTrackers. Handles failures.

Task Tracker (Workers ×N)

Executes Map and Reduce tasks in available slots. Reports status back to JobTracker.

Storage Layer (HDFS)

Name Node (Master)

Tracks location of ALL data blocks across all DataNodes. Handles replication. Single point of failure in V1.

Data Nodes (Workers ×N)

Store actual data blocks locally. Serve read/write requests. Report block status to NameNode.

Typically co-located: Each physical machine runs one TaskTracker + one DataNode. This enables Data Locality.

MapReduce Execution in Hadoop

Hadoop strictly implements the MapReduce design with HDFS as persistent intermediate storage at every stage boundary.

1
HDFS Read — JobTracker queries NameNode → assigns Map tasks to TaskTrackers with local data splits
2
Map + Sort — Each TaskTracker runs Map function on its split, sorts output key-value pairs by key
3
Write to HDFS — Sorted Map output written persistently to HDFS (fault tolerance checkpoint)
4
Copy (Shuffle) — Each Reducer copies its assigned keys from all Mappers' HDFS outputs via network transfer
5
Reduce — User Reduce function aggregates values grouped by key
6
Write Final Output — Results written to HDFS for consumption

Overheads in Hadoop MapReduce

OverheadStageImpactNotes
Job Setup Before Map Medium JVM startup, configuration distribution, slot allocation
HDFS Read Map input Medium Mitigated by data locality; large sequential reads are fast
Map Output Sort Post-Map High Every Map output must be sorted by key before write — always required
HDFS Write (intermediate) Post-Map High Full Map output written to disk — necessary for fault tolerance but expensive
Network Shuffle Copy phase Very High Data crosses machine boundaries sorted by key — can dominate job time
HDFS Write (final) Post-Reduce Medium Final output persisted to HDFS — unavoidable
Always-reduce problem: Hadoop always requires a Reduce phase, even for pure Map-only workloads (like simple filtering). This forces an unnecessary Sort+Write+Shuffle+Read cycle.
HDFS latency profile: Optimised for large sequential block reads (manageable latency). Terrible for small random reads. Minimum file size ~64MB (default block size).

Data Locality

Core Hadoop philosophy: move the compute to the data, not the data to the compute.

Why Data Locality Matters

Without Locality

Transfer 64MB HDFS block over 1Gbps LAN: ~512ms. For 1TB input: ~8,192 seconds of network time just to deliver data to compute.

With Locality

Read the same 64MB block from local HDD: ~50ms. Same 1TB: ~800 seconds. 10× faster just from co-location.

How Hadoop Achieves Data Locality

  • JobTracker + NameNode coordination: Before assigning a Map task, JobTracker queries NameNode to find which machines hold replicas of the input split
  • Preferential assignment: Map tasks are preferentially assigned to TaskTrackers that have the data locally — the slot on the same machine as the data is chosen first
  • Rack awareness: If no local slot is available, JobTracker chooses a machine on the same network rack (one network hop vs. cross-rack)
  • Reduce locality: Reducers copy by key from HDFS — network transfer unavoidable here, but HDFS replication helps parallelise reads

Hadoop Versions

V1

  • Basic MapReduce + HDFS
  • Single JobTracker (SPOF)
  • Fixed Map/Reduce task slots
  • Only supports MapReduce jobs

V2 (YARN)

  • Introduces YARN resource manager
  • Better resource allocation
  • Supports multiple frameworks (Spark, Flink on same cluster)
  • Flexible container sizing

V3

  • Multiple NameNode support (fixes SPOF)
  • Erasure coding (reduces storage overhead vs. 3× replication)
  • Container support
  • GPU support for ML workloads

How Hadoop Addresses the Challenges

ChallengeHadoop's ApproachRating
Load Balancing Not native — developer controls via data split size. Smaller splits = better balance but more overhead. Partial
New Stages (Overhead) Always forces Sort + HDFS Write + Shuffle. Performs poorly for simple jobs. Cannot skip Reduce. Weak
Transfer Latency HDFS optimised for large sequential reads. Data locality minimises network transfer. Still slow for small reads. Partial

Past Exam Questions

📋 2025 Exam — Q2a: UpBank Hadoop Deployment (6 marks)

6 marks ▼
UpBank is a modern challenger bank processing millions of transactions per day. Their engineering team wants to deploy Hadoop to analyse daily transaction logs. Discuss the key decisions they need to make when deploying Hadoop for this task, including cluster sizing, data partitioning, and configuration choices.
Model Answer:

1. Cluster Sizing:
• Estimate data volume: daily log size × retention period determines total HDFS capacity
• Factor in HDFS replication (default 3×) — actual storage needed = raw data × 3
• Worker nodes: enough TaskTrackers to process a day's worth of logs within SLA window
• Master node: dedicated machine for JobTracker + NameNode (avoid co-location in production)

2. Data Partitioning:
• HDFS block size (default 128MB in V2) determines number of Map tasks per file
• Smaller blocks = more parallelism + better load balancing, but higher scheduling overhead
• Partition by date/hour for efficient time-range queries and data pruning

3. Configuration:
• Number of Map/Reduce slots per TaskTracker (balance CPU cores vs. memory per task)
• Replication factor: 3 for fault tolerance on commodity hardware
• Enable data locality: ensure data is distributed across cluster before running jobs
• In V2+: configure YARN container memory/CPU allocation per task

UpBank wants to compute the total transaction value grouped by merchant category (e.g., "Groceries", "Transport", "Entertainment"). Describe the Mapper and Reducer classes you would implement, including their input/output types and logic.
Model Answer:

Mapper Class:
• Input: (transactionID: String, transactionRecord: String)
• Parse record to extract: merchant_category, transaction_amount
• Output: emit(merchant_category: String, amount: Double)
• Example: "txn001, Tesco, Groceries, £45.20" → emit("Groceries", 45.20)

📋 2025 Exam — Q2c: Hadoop Limitations for Market Statistics (4 marks)

4 marks ▼
UpBank's data science team wants to compute real-time market statistics (e.g., running averages, live alerts) from transaction streams. Explain why Hadoop MapReduce is unsuitable for this use case and what alternative would be better.
Model Answer:

Why Hadoop is unsuitable:
1. Batch-only: Hadoop processes data in fixed batches — a job must be explicitly triggered and processes all input before producing output. Cannot process transactions as they arrive.
2. High latency: HDFS read + Map output sort + HDFS write + shuffle + reduce typically takes minutes to hours. Real-time alerts require sub-second latency.
3. No streaming support: Hadoop V1 has no streaming mechanism. Data must be collected, stored, then processed in bulk.
4. Stateless reducers: Each job starts fresh — maintaining running aggregates (like rolling averages) requires complex workarounds.

Better alternative: Apache Kafka (for ingestion) + Apache Flink or Spark Streaming (for stateful stream processing) — designed for low-latency, continuous, stateful computation over event streams.

📋 2023 Exam — Q2a: News Aggregator MapReduce Design (9 marks)

9 marks ▼
A news aggregator collects 10 million articles per day from 50,000 sources. They want to identify the top-10 most cited news sources for each topic category (e.g., "Politics", "Technology"). Design a MapReduce solution. Your answer should describe the Mapper and Reducer logic, including input/output types, and discuss how chaining multiple MapReduce jobs can produce the final result.
Model Answer:

Job 1 — Count citations per (topic, source):
• Mapper Input: (articleID, article_json)
• Parse to extract: topic_category, cited_source
• Mapper Output: emit( (topic, source): String, 1: Integer )
• Reducer Input: ( (topic,source), [1,1,1,...] )
• Reducer Output: emit( (topic, source), citation_count )

Job 2 — Find top-10 per topic:
• Mapper Input: ( (topic,source), citation_count ) from Job 1 output
• Mapper Output: emit( topic: String, (source, count): String ) — key is just topic
• Reducer Input: ( topic, List[(source,count)] )
• Reducer Logic: sort all (source,count) pairs by count descending, take top 10
• Reducer Output: emit( topic, top_10_sources_list )

Design considerations [mark-winning points]:
• Job chaining: output HDFS path of Job 1 = input HDFS path of Job 2
• Combiner in Job 1: local partial sum reduces shuffle volume (important at 10M articles/day scale)
• Partitioner: ensure all records for the same topic go to the same reducer in Job 2

📋 2023 Exam — Q2b: Hadoop Overhead Profiling (8 marks)

8 marks ▼
A Hadoop job processing the news aggregator data takes 45 minutes. The engineering team wants to profile and reduce this time. Describe the main sources of overhead in a Hadoop MapReduce job and suggest how each could be measured and reduced.
Model Answer — 5 overhead sources:

1. Job Setup (JVM launch, task scheduling):
• Measure: time before first mapper starts vs job submission time
• Reduce: use YARN containers to pre-warm JVMs; use Uber mode for small jobs

2. HDFS Read (Map input):
• Measure: Hadoop counters "HDFS bytes read" and map input bytes
• Reduce: maximise data locality (check job logs for % local reads). Ensure HDFS block size matches typical query size.

3. Map Output Sort:
• Measure: compare "map output bytes" to "map output materialized bytes"
• Reduce: use Combiner to reduce output volume before sort; increase io.sort.mb

4. Network Shuffle (Copy phase):
• Measure: reduce input bytes vs map output bytes; check counters for shuffle time
• Reduce: compress map output (mapreduce.map.output.compress=true); use Combiner

5. HDFS Write (intermediate + final):
• Measure: Hadoop counters "HDFS bytes written"
• Reduce: consider switching to Spark which avoids intermediate HDFS writes

Practice Questions

1. A satellite company processes telemetry data from 500 satellites. Each satellite sends 1GB/hour. They need to compute the average temperature reading across all satellites for each 10-minute window. Design a MapReduce job — what are the input/output types of the Mapper and Reducer?

Mapper: Input: (satelliteID_timestamp, reading_record) → Parse: extract 10min window key + temperature value → Output: emit(window_key: String, temperature: Float)

Reducer: Input: (window_key, [temp1, temp2, ..., tempN]) → Compute mean = sum/count → Output: emit(window_key, average_temperature)

Note: Reducer needs to track both sum AND count (not just sum) to compute average. A Combiner can compute local partial sums but must also emit the count for the global average to be correct.

2. Explain why Hadoop's intermediate HDFS writes are both necessary and costly. Could we remove them? What would break?

Why necessary: Intermediate writes provide fault tolerance checkpoints. If a Reduce task fails, the system re-reads Map outputs from HDFS without re-running all Mappers. Without them, any failure in the Reduce phase = restart entire job from scratch.

Why costly: Full Map output (potentially 100s of GB) written to HDFS twice (Map write + Reduce read). HDFS writes are replicated 3× by default. Dominates job time for small-output transformations.

What breaks if removed: Fault tolerance — a reducer failure requires re-running all mappers. For a job with 1000 mappers, this could be catastrophically expensive. This is exactly what Apache Spark does differently — it keeps intermediate data in memory (losing fault tolerance on node failure, which it handles differently via lineage).

3. A Hadoop cluster has 10 worker nodes, each with 2 task slots. A job has 30 Map tasks and 5 Reduce tasks. Describe the execution timeline: which tasks run in parallel and what determines the total job time?

Map phase: 20 Map tasks run in parallel (20 slots across 10 nodes). The 30 map tasks run in 2 waves: first 20 start together, then the remaining 10 start as slots free up. Total map time ≈ 2 × T_map_per_task (assuming equal load).

Barrier: Reduce phase cannot start until ALL 30 Map tasks complete (or at least begin copying in some configurations).

Reduce phase: 5 reducers use 5 slots. Since 20 slots available and only 5 reducers, they all run simultaneously. But reducers first copy Map outputs (shuffle), then sort, then reduce.

Total job time ≈ T_setup + T_map_phase + T_shuffle + T_reduce + T_write.
The slowest mapper determines when Map phase ends (straggler problem = a key bottleneck in Hadoop).

4. Compare Hadoop's approach to handling "Master Failure" in V1 vs V3. Why is this an important improvement?

V1: Single JobTracker. If it dies, the entire cluster stops — no recovery. All running jobs are lost. Must restart the master manually and re-submit jobs. Single point of failure.

V3 (via YARN): ResourceManager (V2 equivalent of JobTracker) supports High Availability (HA) mode: active + standby ResourceManager. On failure, standby takes over automatically. Additionally, V3 adds multiple NameNode support — fixing the HDFS master SPOF too.

Importance: For production clusters running 24/7 batch jobs, master failure in V1 means all queued work is lost. At enterprise scale (hundreds of nodes, thousands of jobs/day), this is unacceptable. V3's HA support is essential for SLA compliance.
