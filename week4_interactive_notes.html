Spark Architecture

Client

Software the user runs to submit a Spark job. Instantiates the SparkContext and communicates with the Spark Master. Responsible for I/O with the user.

Driver

The program that executes the Spark job. Initialised by the Client — may run on the client machine or on a cluster node. Contains the DAGScheduler and TaskScheduler. Must stay alive until the job completes.

Spark Master

Receives work from the Client/Driver, analyses the DAG, assigns work to workers via the Cluster Manager. Routes tasks to Executors. Communicates with the Driver.

Spark Worker

Manages local execution of Transformations and Actions. Each machine in the cluster has a Worker. Workers host one or more Executors.

Executor

A JVM that executes tasks using a ThreadPool. Each job gets its own Executor (to avoid memory sharing between jobs). An Executor can run multiple tasks in parallel. Also responsible for caching datasets/results.

DAGScheduler & TaskScheduler

DAGScheduler: builds stages of tasks from the DAG, identifies dependencies, resubmits failed stages. TaskScheduler: ships tasks to Executors, monitors execution, handles stragglers via speculative execution.

Important Differences from Hadoop

No Defined Persistent Storage Layer

Spark uses temporary storage (disk) only if RAM is exhausted. Application code defines how data is loaded. Completely flexible — HDFS, NFS, S3, local files all supported.

Driver Lifetime

The Driver must remain alive until the Spark job finishes — it receives the final Action result. The Driver doesn't need to run on the Client.

Per-Job Executor Isolation

Each job gets its own Executor to avoid jobs sharing memory. An Executor can run multiple tasks in parallel within the same job. Much faster startup than Hadoop.

In-Memory Computation

RDDs are kept in memory across stages. No HDFS write/read between stages (unlike Hadoop MapReduce). Leads to ~100× speedup for iterative workloads.

Spark Execution Phases (7 High-Level Steps)

Phase 1 — Create SparkContext (SC)

Client instantiates SC, responsible for I/O with user, cluster manager, and executors. SC initialises the Driver, registers app with Cluster Manager, gets list of Executors.

Phase 2 — Create Input RDDs

Client uses SC to create input RDDs, partitioned/parallelised across cluster nodes (data scan).

Phase 3 — Apply Transformations (Lazy)

Client applies transformations — no computation occurs yet. Each transformation incrementally builds a DAG of operations. Lazy evaluation = no cluster work until Action.

Phase 4 — Trigger Action

Client calls an Action (e.g., collect()). This triggers DAG submission to the DAGScheduler within the Driver.

Phase 5 — DAGScheduler Builds Stages

DAGScheduler groups tasks by dependencies into Stages (shuffle boundaries). Submits execution plan to TaskScheduler. Resubmits failed stages if output is lost.

Phase 6 — TaskScheduler Ships Tasks

Serialises RDD lineage + transformations, ships to Executors. Monitors progress, handles stragglers (speculative execution), decides where to run based on locality.

Phase 7 — Return Result to DAGScheduler

TaskScheduler returns result to DAGScheduler as a series of events. DAGScheduler marks job complete, executors are killed and memory released.

Spark Transformations

Transformations convert one (or more) RDD into another RDD. They are lazy — no computation occurs until an Action is triggered.

Basic Transformations

FunctionTypeSignatureDescription
map(func) Narrow record1 → record2 Return a new RDD formed by passing each element through func. One-to-one mapping. Records in different partitions processed in parallel.
flatMap(func) Narrow record1 → Iterator<record2> Like map, but each input can map to 0 or more outputs. Useful for tokenisation (e.g. splitting lines into words). Output list can be empty.
mapPartitions(func) Narrow Iterator<T> → Iterator<U> Runs on each partition (block). More efficient than map when setup cost is high (e.g. DB connections). Partitions processed in parallel.
mapPartitionsWithIndex(func) Narrow (Int, Iterator<T>) → Iterator<U> Like mapPartitions but also provides the partition index. Useful when partitions represent meaningful data subsets.
filter(func) Narrow record1 → Boolean Return a new RDD with only elements where func returns true. Dropped elements do not appear in output.
sample(withReplacement, fraction, seed) Narrow Built-in Random filter — keeps a fraction of the data. With or without replacement. Reproducible with seed.

Example: map vs flatMap

# map: each line → (line, length)
rdd = sc.textFile("data.txt")
mapped = rdd.map(lambda line: (line, len(line)))

# flatMap: each line → multiple words (1-to-many)
words = rdd.flatMap(lambda line: line.split(" "))

# filter: only keep lines containing "big data"
filtered = rdd.filter(lambda line: "big data" in line.lower())

Set Transformations

union(otherDataset)

Returns a new RDD containing the union of elements in the source and the argument. Identical records appear only once (set semantics). Narrow transformation.

Form: RDD<T>, RDD<T> → RDD<T>

intersection(otherDataset)

Returns only records that are identical in both input RDDs. Wide transformation (requires shuffle to compare across partitions).

Form: RDD<T>, RDD<T> → RDD<T>

distinct([numPartitions])

Returns a new RDD containing only distinct elements. Wide transformation.

Form: RDD<T> → RDD<T> (unique elements only)

Key/Value Transformations

FunctionTypeDescription
groupByKey([numPartitions]) Wide On (K,V) pairs → (K, Iterable<V>). Groups all values with the same key. Also can re-partition. Warning: can be inefficient; prefer reduceByKey when aggregating.
reduceByKey(func, [n]) Wide On (K,V) pairs → (K,V). Aggregates values per key using a reduce function (V,V)→V. More efficient than groupByKey for aggregations (partial reduce per partition first).
aggregateByKey(zeroVal)(seqOp, combOp) Wide Like reduceByKey but output type can differ from input type. seqOp applied within each partition; combOp combines across partitions. record2 is an accumulator.
sortByKey([ascending]) Wide On (K,V) pairs → sorted by key ascending or descending. Keys must implement Ordered.

Set Key Transformations (Expensive)

join(otherDataset, [numPartitions])

On (K,V) and (K,W) → (K, (V,W)). All pairs for each key. Also: leftOuterJoin, rightOuterJoin, fullOuterJoin.

Very expensive — requires full shuffle. Use sparingly.

cogroup(otherDataset)

On (K,V) and (K,W) → (K, (Iterable<V>, Iterable<W>)). Also called groupWith. More compact than join when you need grouped lists.

cartesian(otherDataset)

Cartesian product — every element from RDD1 combined with every element from RDD2. Extremely expensive — O(n×m) output size. Avoid on large datasets.

Re-Partitioning Transformations

repartition(numPartitions)

Reshuffle data randomly to create more or fewer partitions and balance data across them. Always shuffles all data over the network. Use when you need to increase parallelism.

coalesce(numPartitions)

Decrease number of partitions (merges partitions together). More efficient than repartition for reducing partitions as it minimises shuffling. Use after filtering large datasets.

Narrow vs Wide Transformations (Exam Critical!)

Narrow Transformations
  • Each input partition contributes to at most one output partition
  • No shuffle needed — data stays on the same node
  • Can be pipelined within a single Stage
  • Examples: map, filter, flatMap, mapPartitions, union
  • Fast, minimal network I/O
Wide Transformations (Shuffle Boundary)
  • Input partitions may contribute to multiple output partitions
  • Require data shuffle across the network
  • Create a new Stage boundary in the DAG
  • Examples: reduceByKey, groupByKey, join, sortByKey, intersection, repartition
  • Expensive — minimise where possible
Key Rule: Stages in Spark are divided at wide transformation boundaries (shuffle points). Everything between two shuffles can execute in one stage without data movement.

Word Count Example with Narrow/Wide Labels

sc = SparkContext("local", "WordCount")
text   = sc.textFile("articles.txt")         # Load
words  = text.flatMap(lambda l: l.split(" "))  # NARROW: Stage 1
pairs  = words.map(lambda w: (w, 1))           # NARROW: Stage 1 (pipelined)
counts = pairs.reduceByKey(lambda a,b: a+b)   # WIDE: Stage 2 (shuffle boundary)
result = counts.collect()                     # ACTION: triggers execution

Spark Actions

Actions trigger execution of the lazy DAG. They either return data to the Driver or write to persistent storage.

Common Actions (~90% usage)

ActionReturnsWhen to Use
collect() All elements as an array After filtering/aggregating to a small subset. Caution: copies entire RDD to Driver machine. Do not use on large RDDs.
count() Long (number of elements) Trigger computation without copying data. Useful for debugging or counting records. Efficient — only a single number returns.
reduce(func) Single aggregated value Aggregate all elements into one using (V,V)→V. Function must be commutative and associative (so parallel execution is correct). Returns to Driver.

Sampling Actions

first()

Return the first element of the RDD. Equivalent to take(1). Stops computation as soon as one element is found.

take(n)

Return an array with the first n elements. Useful for previewing data. Returns data in RDD order.

takeSample(withReplacement, num, seed)

Return a random sample of num elements. Like take(n) but random. With replacement = same item may appear multiple times.

takeOrdered(n, [ordering])

Return first n elements based on natural ordering or custom comparator. More efficient than sortByKey().take(n).

countByKey()

Only on (K,V) RDDs. Returns a Map[K, Long] with count of values per key.

foreach(func)

Apply func to each element. Used for side effects (e.g. writing to database). Does not return data to Driver.

Save Actions

saveAsTextFile(path)

Write elements as text file(s) in given directory (local FS, HDFS, or any Hadoop-supported FS). Calls toString() on each element. One file per partition.

saveAsSequenceFile(path)

Write as Hadoop SequenceFile. Available on (K,V) RDDs implementing Hadoop's Writable interface. Binary, efficient format.

saveAsObjectFile(path)

Write using Java serialisation. Can be reloaded using SparkContext.objectFile(). Good for checkpointing intermediate RDDs.

Transformations vs Actions Summary: Transformations are lazy (RDD→RDD, no computation). Actions trigger execution (return data or write to storage). Every time an action is called, Spark re-executes the entire lineage unless the RDD is cached.

Spark Advantages & Disadvantages

Why Spark Overtook Hadoop (by 2017)

Speed (up to 100×)

All computation in-memory → no HDFS writes between stages. Benchmark: Spark sorted 100TB in 23 mins vs Hadoop's 72 mins (using 206 vs 2100 nodes). Sort rate: 20.7 GB/min/node vs 0.67 GB/min/node.

Wider Use-Case Coverage

Rich set of transformations handles complex pipelines needing many chained operations. No need to chain separate Hadoop MapReduce jobs with HDFS reads/writes between them.

Better Language Support

Written in Scala, with full Java support. Better secondary languages: Python (PySpark), R (SparkR), native SQL (Spark SQL). Integrates with ML frameworks (TensorFlow, PyTorch, MLflow), storage (Cassandra, Kafka, Delta Lake), BI tools (Tableau, Power BI).

DAG-Based Optimisation

Lazy evaluation allows the DAG Scheduler to optimise the entire execution plan before running. Narrow transformations are pipelined within stages to minimise I/O.

Remaining Limitations

Streaming: Not Ideal

Spark Streaming processes data in micro-batches (not true event-by-event). Higher latency than dedicated streaming systems. Apache Flink is better for true low-latency streaming and stateful processing.

Memory Requirements

In-memory computation requires more RAM. If data exceeds available memory, Spark spills to disk — performance degrades significantly. Must carefully tune executor memory.

No Built-In Storage

Unlike Hadoop (which bundled HDFS), Spark needs a separate storage layer. This is flexible but adds operational complexity.

Driver as Single Point of Failure

The Driver must stay alive for the entire job. If the Driver fails, the job fails. Spark does not natively support Driver high-availability in all deployment modes.

Batch vs. Streaming

Batch Processing
  • Works with static (bounded) data
  • Large blocks of data analysed at once
  • Multiple blocks processed concurrently, then merged
  • Cares about: completion time
  • Examples: Spark, Hadoop MapReduce, daily reports
  • OK to wait minutes/hours for result
Stream Processing
  • Works with dynamic (unbounded) data
  • Items processed individually or in tiny micro-batches
  • Pipeline of stages — multiple items in flight simultaneously
  • Cares about: processing latency per item
  • Examples: Flink, Spark Streaming, Kafka Streams
  • Must respond in milliseconds/seconds

What Makes Streaming Challenging?

Problem 1: No Discrete Equal-Size Blocks
  • Load-balancing is more difficult
  • Velocity/Input rate is variable — tied to real-world events (e.g. spike at rush hour)
  • Can't pre-compute input splits like Hadoop
Problem 2: Latency is Critical
  • A human user is waiting for the result
  • Must achieve consistent processing latencies
  • Buffering during task-to-task transfers is problematic
  • Bottlenecks / back pressure can cause failures

Worked Example: Bank Fraud Detection

Scenario: Flag customers who transfer more than £5,000 in a single day.

Batch Solution (Spark)

# Load transactions → Group by user → Sum per day → Filter > £5000
transactions = sc.textFile("transactions.txt")
kv = transactions.map(lambda t: (t.userId, t.amount))  # map to (user, amount)
sums = kv.reduceByKey(lambda a, b: a + b)              # sum per user
flagged = sums.filter(lambda kv: kv[1] > 5000)           # filter > £5000
result = flagged.collect()                              # trigger, return to driver
# Issue: Must wait until END OF DAY to run this check!

Each transaction is processed as it arrives. The map stage maintains a running counter per user (state). When the running sum exceeds £5000, the filter emits an alert. Counter resets at end of day.

Stateful Applications

Definition: A stateful application has one or more tasks with persistent state that changes over time based on input received.

In the fraud example, the map task stores a running total per user — that's state. State creates serious parallelism problems:

Problem: Inconsistent Results with Parallelism

If transactions for the same user are randomly assigned to different map instances, each instance has an incomplete running total. The filter receives wrong totals.

Solution: Route transactions by user key — all of User1's transactions go to the same map instance.

Shared State is Even Harder

When state must be shared across task instances (e.g., a global header filter), synchronisation is required. Issues: synchronisation costs latency, task failure corrupts global state, memory grows unboundedly.

Advice: Avoid state in transformations where possible!

Other Problems with State

  • Memory growth: State grows over time → tasks can exhaust memory and fail
  • Recovery cost: If a stateful task fails, all processed items must be replayed to rebuild state
  • Consistency: Distributed state requires expensive synchronisation protocols

Buffering & Back-Pressure

Each task has an input buffer and an output buffer. The task processes one item at a time.

Back-Pressure Cascade
  1. Items arrive faster than task can process → input buffer fills
  2. Input buffer full → previous task cannot empty its output buffer
  3. Previous task's output buffer full → it cannot process new items
  4. Previous task's input buffer fills
  5. Cascade propagates upstream through the entire pipeline
  6. When all buffers are full → job FAILS
Consequences & Mitigations
  • Items sit in queues → increasing latency
  • Eventually new items have nowhere to go → crash
  • Mitigations: Scale out (more task instances), reduce message size, implement backpressure-aware load shedding, use dedicated streaming frameworks (Flink handles this natively)

Past Exam Questions

2025 Exam Q1a — Spark Architecture (6 marks)

▼

Question: Describe the key components of the Apache Spark architecture, explaining the role of the Driver, Spark Master, Spark Workers, and Executors. How does this architecture differ from Hadoop MapReduce?

Model Answer

Driver: Contains DAGScheduler and TaskScheduler. Executes the Spark program, builds DAG from transformations, submits stages to TaskScheduler, receives results from Actions. Remains alive for the entire job.

Spark Master: Manages the cluster via Cluster Manager. Receives work from the Client, assigns Executors to Workers for each job.

Spark Workers: Nodes in the cluster that host Executors. Manage local execution of tasks assigned by the Master.

Executors: JVM processes on Worker nodes. Execute application code for tasks. Cache datasets in memory. Each job gets its own Executor to prevent memory sharing between jobs.

Differences from Hadoop: (1) No defined persistent storage — data stays in RAM instead of writing to HDFS between stages. (2) Driver-centric execution vs. JobTracker/TaskTracker model. (3) DAG-based scheduling vs. fixed Map→Sort→Reduce pipeline. (4) Lazy evaluation enables query optimisation before execution.

2025 Exam Q1b — 23-Step Execution (5 marks)

▼

Question: A Spark job is submitted by a client. Describe the key steps in the Spark job execution anatomy, from running the program to job completion. You do not need to list all 23 steps — focus on the key phases.

Model Answer
  1. Initialisation: Client runs Spark program → creates SparkContext → initialises Driver → Driver requests resources from Cluster Manager
  2. Executor Setup: Cluster Manager provisions Executors on Worker nodes → Executors launch JVMs → report ready to Driver
  3. DAG Building: Client creates input RDDs (data scan creates partitions) → applies Transformations lazily → DAG grows incrementally
  4. Action Triggered: Client calls Action → DAG submitted to DAGScheduler → DAGScheduler builds Stages (grouping by dependencies, splitting at shuffle boundaries)
  5. Stage Execution: DAGScheduler submits Stage 1 to TaskScheduler → TaskScheduler launches tasks on Executors → tasks execute (Read→flatMap→...) → partitions created in memory → heartbeats report completion
  6. Subsequent Stages: DAGScheduler submits Stage 2 (e.g. Collect) → output copied to Driver over network
  7. Cleanup: DAGScheduler marks job complete → kill messages sent to Executors → Executors shut down (memory released) → execute method returns in main program

2023 Exam Q2c — Spark Advantages over Hadoop (8 marks)

▼

Question: Apache Spark has largely replaced Hadoop MapReduce for batch processing workloads. Identify and explain THREE key advantages that Spark has over Hadoop MapReduce, providing concrete examples where appropriate. (8 marks)

Model Answer

1. In-Memory Processing (3 marks): Spark stores RDDs in RAM between stages; Hadoop writes intermediate results to HDFS after each MapReduce job. This eliminates expensive disk I/O during multi-stage pipelines. Example: a 5-step ML training loop would require 5 HDFS write/read cycles in Hadoop vs. staying in RAM with Spark → up to 100× faster for iterative algorithms. Benchmarks show Spark sorts 100TB in 23 mins vs. Hadoop's 72 mins.

2. Rich Programming Model / Wider Use-Case Coverage (3 marks): Hadoop supports only Map and Reduce operations. Spark provides ~20 transformations including joins, aggregations, set operations, and re-partitioning, plus Actions for collection/saving. Complex pipelines (e.g. joining two datasets, filtering, aggregating, sorting) require chained Hadoop jobs writing to HDFS between each step, whereas Spark handles it in a single DAG without disk I/O. Example: news recommendation requiring join+filter+groupBy+reduce would need 3+ Hadoop jobs vs. 1 Spark job.

3. Better Language & Ecosystem Support (2 marks): Hadoop is primarily Java. Spark supports Scala, Java, Python (PySpark), R (SparkR), and SQL (Spark SQL) natively. This means data scientists can use Python/R without writing verbose Java. Integration with ML frameworks (TensorFlow, MLflow), storage systems (Cassandra, Delta Lake), and BI tools (Tableau) makes Spark the hub of modern data pipelines.

2025 Exam Q2 — Batch vs Streaming (6 marks)

▼

Question: A social media company wants to detect trending hashtags. They are considering either a batch or a streaming approach. (a) Describe the difference between batch and streaming processing. (b) Design both a batch solution using Spark and a streaming solution, identifying the key challenges of the streaming approach. (6 marks)

Model Answer

(a) Difference: Batch processes static, bounded data in large blocks — optimises for completion time, results available after the job finishes. Streaming processes dynamic, unbounded data item-by-item as it arrives — optimises for per-item processing latency.

(b) Batch Solution (Spark):

tweets = sc.textFile("tweets_today.txt")
hashtags = tweets.flatMap(lambda t: extract_hashtags(t))
pairs = hashtags.map(lambda h: (h, 1))
counts = pairs.reduceByKey(lambda a,b: a+b)
top10 = counts.takeOrdered(10, key=lambda x: -x[1])
# Issue: results only available at end of batch window (e.g. hourly)

Streaming Solution: As each tweet arrives: extract hashtags → key by hashtag → map with stateful running counter per hashtag → filter if count exceeds threshold. Provides real-time trending detection.

Streaming Challenges: (1) Stateful computation — the running count per hashtag requires routing all occurrences of a hashtag to the same task instance (via keyBy), otherwise counts are inconsistent across instances. (2) Buffering/back-pressure — if tweet volume spikes (event at stadium), tasks cannot keep up, input buffers fill, back-pressure propagates upstream, and the pipeline may fail. (3) Variable velocity makes load balancing harder than batch.

2023 Exam Q3 — Spark Transformations Design (9 marks)

▼

Question: You are asked to process a large dataset of customer purchase records where each record contains: customerId, productId, price, timestamp. Using Spark RDD transformations and actions, write a PySpark program to: (i) find the total spend per customer, (ii) identify customers who have spent more than £500, (iii) return the top 5 customers by spend. Clearly identify which transformations are narrow/wide.

Model Answer
sc = SparkContext("local", "CustomerSpend")
records = sc.textFile("purchases.csv")

# Parse: record → (customerId, price)          [NARROW - map]
kv = records.map(lambda r: (r.split(",")[0], float(r.split(",")[2])))

# Sum spend per customer                        [WIDE - shuffle]
totals = kv.reduceByKey(lambda a, b: a + b)

# Filter customers spending > £500              [NARROW - filter]
high_spenders = totals.filter(lambda kv: kv[1] > 500)

# Top 5 by spend                               [ACTION]
top5 = high_spenders.takeOrdered(5, key=lambda x: -x[1])

print(top5)

Narrow transformations: map (Step 1), filter (Step 3) — no shuffle required, processed within partitions.

Wide transformation: reduceByKey (Step 2) — requires shuffle to bring all records for the same customerId to the same reducer partition. Creates a Stage boundary in the DAG.

Action: takeOrdered triggers execution, sorts and returns top 5 to Driver.

DAG Structure: Stage 1 (map → reduceByKey shuffle) → Stage 2 (filter → takeOrdered).

Practice Questions

Q1: Narrow vs Wide — Identify the transformation type in a given pipeline

▼

Given the following PySpark pipeline, classify each operation as narrow or wide and explain why:

rdd = sc.textFile("logs.txt")
r1 = rdd.filter(lambda l: "ERROR" in l)
r2 = r1.map(lambda l: (l.split()[2], 1))
r3 = r2.groupByKey()
r4 = r3.mapValues(sum)
r5 = r4.sortByKey()
result = r5.collect()
Answer
  • filter → Narrow: each partition independently filtered, no shuffle needed
  • map → Narrow: one-to-one transformation within each partition
  • groupByKey → Wide: groups all records with the same key — requires shuffle across partitions (Stage boundary)
  • mapValues(sum) → Narrow: applied to each (K, Iterable[V]) pair independently, no shuffle
  • sortByKey → Wide: global sort requires shuffle to order keys across all partitions (Stage boundary)
  • collect() → Action: triggers execution, returns all data to Driver

Stages: Stage 1 (filter → map → groupByKey shuffle) → Stage 2 (mapValues → sortByKey shuffle) → Stage 3 (collect)

Q2: Streaming State Problem — Why does this streaming program produce incorrect results?

▼

A student writes a streaming application to count the number of tweets containing "Scotland" across a day, using 3 parallel map instances that each maintain a local counter. At the end of the day, the student collect()s the counters and sums them. The result is always wrong. Explain why and describe the correct approach.

Answer

Problem: With 3 parallel map instances and no key-based routing, tweets are randomly distributed across instances. Each instance maintains its own counter for "Scotland" tweets it has seen. The 3 counters are independent — there is no shared state. Summing them at the end is actually correct for a stateless count!

Wait — the sum approach IS correct for a simple count. The real problem would arise if we needed per-user counts: if User1's tweets are split across multiple map instances, each instance has a partial sum for User1. Summing at the end still gives the correct total, but individual instance states are incorrect (which would break early-termination logic like "alert when User1 exceeds 100 tweets").

Correct streaming approach for per-user counts: KeyBy userId so all tweets from User1 always route to the same map instance. That instance then has the correct running total for User1 and can trigger per-user alerts in real-time.

Q3: Spark Execution — What triggers computation in this code, and when?

▼ 
rdd1 = sc.textFile("big_file.txt")    # Line A
rdd2 = rdd1.flatMap(tokenize)          # Line B
rdd3 = rdd2.map(lambda w: (w,1))       # Line C
rdd4 = rdd3.reduceByKey(lambda a,b:a+b) # Line D
rdd4.saveAsTextFile("output/")          # Line E
Answer

Lines A–D: No computation occurs. All operations are lazy. Lines A–D build the DAG incrementally in the Driver program — they define the computation plan but don't execute it.

Line E (saveAsTextFile): This is an Action. Calling it triggers the entire DAG to be submitted to the DAGScheduler. The DAGScheduler analyses the DAG, identifies the wide transformation boundary at reduceByKey, creates two stages, submits them to the TaskScheduler, which ships tasks to Executors. Data is read from disk, tokenized, mapped to pairs, shuffled for reduction, then written to the output directory.

Key point: If Line E were removed, no computation would ever occur — the program would finish instantly having built only a plan.

Q4: aggregateByKey vs reduceByKey — When would you use each?

▼
Answer

reduceByKey(func): Use when the output type is the same as the value type. Function must be (V,V) → V. e.g., summing integers: reduceByKey(lambda a,b: a+b).

aggregateByKey(zeroValue)(seqOp, combOp): Use when the output type differs from the input type (accumulator pattern). Two functions: (1) seqOp: (U, V) → U — how to fold a new record into the accumulator within a partition; (2) combOp: (U, U) → U — how to merge two accumulators across partitions.

Example — compute average per key:

# Value type: Float (individual score)
# Accumulator type: (sum, count)
zero = (0.0, 0)
seqOp = lambda acc, v: (acc[0]+v, acc[1]+1)    # add to running sum+count
combOp = lambda a1, a2: (a1[0]+a2[0], a1[1]+a2[1])  # merge two accumulators
sums = rdd.aggregateByKey(zero, seqOp, combOp)
avgs = sums.mapValues(lambda sc: sc[0]/sc[1])

This cannot be done with reduceByKey alone because the intermediate accumulator has a different type to the input value.
