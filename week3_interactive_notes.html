Hadoop Job Execution Anatomy (23 Steps)

Understanding exactly what happens between "submit job" and "job complete" is critical for exam questions on Hadoop overheads and architecture.

1
Run Job — Client executes the MapReduce program on the Client Machine (JVM)
2
Get Job ID — Client contacts JobTracker to obtain a unique Job ID
3
Copy Job Resources — Client uploads Job.jar (compiled code) to HDFS so all machines can access it
4
Submit Job — Client formally submits Job 1 to the JobTracker queue
5
Initialise Job — JobTracker sets up internal job metadata and state
6
Retrieve Input Splits — JobTracker queries NameNode to find where each input data block lives; determines data locality
7
Register Task + Heartbeat — JobTracker registers the Map task with a TaskTracker that has the data locally; receives heartbeat confirmation
8
Get Job Resources — TaskTracker downloads Job.jar from HDFS
9
Launch JVM — TaskTracker spawns a new JVM process for the Map task
10
Run Map Task — JVM loads Job.jar and runs the user's Mapper class
11
Read Data + Execute — Mapper reads its assigned split from the local DataNode; processes records
12
Intermediate Sort — Map output is sorted by key in main memory
13
Write Map Output — Sorted output written to HDFS as intermediate result
14
Report Map Done — TaskTracker notifies JobTracker that Map task is complete
15
Retrieve Map Partitions — JobTracker queries NameNode for locations of intermediate (Map) output files
16
Register Reduce Task — JobTracker assigns Reduce task to available TaskTracker
17
Get Reduce Resources — TaskTracker downloads Job.jar from HDFS (cached if same machine)
18
Launch JVM — New JVM spawned for Reduce task
19
Run Reduce Task — JVM loads reducer class
20
Copy + Execute — Reducer copies (shuffles) relevant key partitions from all Map output files via network transfer, then runs reduce function
21
Write Reduce Data — Final output written to HDFS
22
Report Reduce Done — TaskTracker notifies JobTracker
23
Report Job Complete — JobTracker notifies Client that the job is finished
Exam insight: Steps 3 (copy resources to HDFS), 6 (retrieve input splits), 13 (write intermediate), 20 (network shuffle), 21 (write final) are the major overhead sources. The exam may ask you to identify and explain them.

Input Splitting

How Splits Work

  • Data is split when written to HDFS (pre-computed)
  • Default: split each file into equal-sized parts
  • Splits ≤ one HDFS block by default (128MB in V2)
  • Splits are data-agnostic — they don't understand file format
  • More splits = more parallelism but more scheduling overhead

Memory Optimisation

  • Buffer in Main Memory: Map output is buffered in RAM before sort
  • Partitions in Main Memory: Sort + partition performed in RAM — faster than disk
  • OutputFormat used to write sorted partitions to HDFS
  • Reducer loads data via recursive merge of partitions (mix of in-memory and on-disk)

Task Assignment & Speculative Execution

Scheduler Variants

📋

FIFO

First In First Out — simple queue. Default scheduler.

⚖️

Fair

Equal resource share across all running jobs.

📊

Capacity

Pools with guaranteed capacity. Enterprise multi-tenant.

Data Locality Priority

  1. Data-local: TaskTracker on the same machine as the data block (fastest)
  2. Rack-local: Same network rack, different machine (one switch hop)
  3. Remote: Different rack (cross-switch, highest latency)

Speculative Execution

Also called backup task execution. If a Map task is running much slower than others (straggler), JobTracker can launch a duplicate task on another machine. Whichever finishes first wins — the other is killed.

Handles slow nodes without waiting for timeout. Trade-off: wastes resources on duplicate work.
How JobTracker knows slot availability: TaskTrackers send periodic heartbeat messages to the JobTracker. These heartbeats report free slots, task progress, and health status. A missing heartbeat = assumed failure.

Key optimisation: Sorting and partitioning happen in main memory (not disk) to save time. Data is only written to HDFS for persistent fault-tolerance at the Map→Reduce boundary. Reducer loading uses a recursive merge — a mix of in-memory and on-disk data.

Distributed Cache

Problem it Solves

HDFS blocks are minimum 128MB. Small files (like lookup tables, config files, model weights) waste space and overwhelm the NameNode index.

If 1 million files < 128MB each, the NameNode must track 1 million block entries → memory exhaustion.

Distributed Cache Properties

  • Read-only — cannot be modified by tasks
  • Supports: JARs, text, archives, config files
  • Copied once per job to each TaskTracker (not per task)
  • Can be private (one job) or public (all jobs)
  • JARs automatically added to task classpaths
  • Can share state across tasks (workaround)

Counters & Monitoring

Hadoop tasks can create and update numerical counters at runtime that are periodically aggregated by the JobTracker. Essential for profiling and debugging.

Built-in: HDFS

HDFS bytes read, bytes written, block reads, FileInputFormat/OutputFormat stats

Built-in: Tasks

Map/Reduce task progress, records processed, skipped bad records

User-defined

Custom metrics: error rates, matched records, business KPIs

Compression in Hadoop

Why compress? More data per HDFS block → lower storage cost and fewer I/O operations. Lower network shuffle volume. Trade-off: CPU cost for compression/decompression (usually worth it).
CodecSplittableSpeedCompression RatioBest For
SnappyYesFastestLowIntermediate data
LZOYes (with index)FastMediumMap output
LZ4YesFastMediumGeneral purpose
BZip2YesSlowHighCold archival storage
GZipNoMediumHighSingle-split files only
Splittability matters: Non-splittable codecs (GZip) mean the entire file must be one input split → only ONE mapper for that file → no parallelism. Always use splittable codecs (Snappy, LZO, BZip2) for HDFS data.

Failure Handling in Hadoop

Task Failure

Detected by TaskTracker

  • Runtime exception: child JVM reports error to TaskTracker
  • JVM crash: OS notifies TaskTracker of dead process
  • Hung task: Missing progress reports → timeout

TaskTracker informs JobTracker → task rescheduled to a different TaskTracker. Multiple attempts allowed. Jobs with too many failures are terminated, or bad records are skipped.

TaskTracker Failure

Detected by JobTracker

  • Crashed/slow: Missing heartbeats
  • Misconfigured: Multiple task failures on same machine

TaskTracker removed from "live" pool. All tasks assigned to it are rescheduled to other workers. Blacklisted trackers reconsidered after a time period.

Issues with Hadoop: Small Files

The HDFS Small Files Problem

HDFS default block size = 128MB. Each small file (even 1KB) requires its own block entry in the NameNode's in-memory index.

  • 1 million small files → 1 million NameNode index entries → NameNode RAM exhausted
  • Each small file = one Map task → massive scheduling overhead with minimal compute per task
Workarounds:
  • Merge small files before storing
  • HAR files (Hadoop Archives) — layered filesystem
  • Use HBase to store binary data in table cells instead of files
  • CombineFileInputFormat to merge small splits at job time

Issues with Hadoop: Speed & Latency

Designed for 2006-era Hardware

When Hadoop was designed, RAM cost ~$0.10/MB. Today RAM costs ~$0.000003/MB — a 33,000× reduction.

  • No in-memory caching: Every stage boundary requires HDFS write
  • Always writes to disk: Even trivial chained Map→Map→Map operations hit disk between each stage
  • JVM startup per task: Launching a JVM for each task adds hundreds of milliseconds
Modern commodity servers have 256GB–1TB RAM. Hadoop wastes this by routing data through HDFS between every task.

Issues with Hadoop: Chaining Maps & Reduces

Multi-Step Jobs Are Expensive

Most real applications require multiple Map-Reduce pairs chained together.

Example — Top-10 cited sources per topic:
Job 1: Map (extract citations) → Reduce (count per source)
Job 2: Map (reformat) → Reduce (sort, take top-10)

Each job boundary = HDFS Write + HDFS Read + New JVM setup + Network shuffle

Hadoop was not designed for easy or fast chaining — it compounds all overhead costs with each link.

Issues with Hadoop: Missing Use Cases & Ease of Use

Unsupported Workloads

  • Stateful tasks: MapReduce tasks cannot share mutable state across instances
  • Streaming: No native streaming support — data must be batched first
  • Side effects: Applications that write to databases, send alerts, etc. don't fit the Map→Reduce model cleanly
  • Iterative algorithms: ML training with 100 iterations = 100× HDFS read/write cycles

Ease of Use

  • Verbosity: Everything is hand-written Java code
  • Simple word count = ~50 lines of Java boilerplate
  • No lambda expressions or high-level API (until later)
  • Compare: Pandas/Python can do the same in 1-2 lines
Modern solutions use optimised abstractions — developers shouldn't need to write Map/Reduce boilerplate for common operations.

Apache Spark: Origins & Motivation

Birth of Spark

  • Founded as a class project at University of California, Berkeley in 2009
  • Open-sourced in 2010, just 3 years after Hadoop
  • Core motivation: "MapReduce+ in Memory"
  • Overtook Hadoop in popularity around 2017
  • Popularity plateau due to Databricks (managed Spark) absorbing demand
  • By 2009, RAM costs had fallen 20× from Hadoop design era — enough to fit large datasets in memory on commodity hardware

Resilient Distributed Datasets (RDDs)

What is an RDD?

An RDD is a fault-tolerant, partitioned collection of records stored in memory. It is the fundamental data structure of Spark.

Properties

  • Distributed: Partitions spread across cluster
  • Resilient: Can be rebuilt from lineage on failure
  • Immutable: Cannot be modified, only transformed into new RDDs
  • Lazily evaluated: Not computed until an Action is called
  • Optionally cached: Can be persisted in memory for reuse

RDD: Students

Partition 1: [Joe Blogs, John Doe]
Partition 2: [Kate Brown, Sara Williams]

RDD: CS Students (after filter)

Partition 1: [Joe Blogs]
Partition 2: []
Fault tolerance without HDFS writes: Instead of checkpointing to disk, Spark tracks the lineage of each RDD — the sequence of transformations used to create it. On failure, it replays just that partition's lineage to regenerate the lost data.

// Spark word count in Python (PySpark) — compare to 50+ lines of Hadoop Java!
from pyspark import SparkContext

sc = SparkContext("local", "WordCount")
text_rdd = sc.textFile("news_articles.txt")          # Load → RDD
words = text_rdd.flatMap(lambda line: line.split(" "))  # Transformation
pairs = words.map(lambda w: (w, 1))                      # Transformation
counts = pairs.reduceByKey(lambda a, b: a + b)            # Transformation
result = counts.collect()                                  # Action → triggers execution

Key difference from Hadoop: In Spark you can chain Map→Map→Map→Map→Reduce with no disk writes between them. Spark won't even start computing until collect() is called — it builds the full computation plan (DAG) first, then executes optimally.

DAGs & Lazy Execution

Directed Acyclic Graph (DAG)

When a Spark job is submitted, all transformations are compiled into a DAG — a directed graph of tasks with dependencies, with no cycles.

Read Data
Stage 1
→
flatMap P1
flatMap P2
Stage 2 (parallel)
→
reduce()
Stage 3

Stages

The Spark scheduler divides the DAG into Stages:

  • Stage = group of tasks that can run in parallel
  • Stage boundary = when data needs to be shuffled across partitions (e.g. reduceByKey)
  • One stage must complete before the next begins (barrier)

Lazy Execution

Spark does not execute transformations when they are defined. It only executes when an Action is called.

  • Allows the scheduler to optimise the full plan before running
  • Eliminates unnecessary computations (only executes what's needed)
  • If no action on an RDD branch — that branch is never computed

Past Exam Questions

📋 2023 Exam — Q2b: Hadoop Overhead Profiling (8 marks)

8 marks ▼
A news aggregator uses Hadoop to process 10 million articles daily. Their MapReduce job takes 45 minutes. The engineering team wants to profile the overheads and reduce total runtime. Describe the main overhead sources in Hadoop MapReduce and how each can be measured and reduced.
5 overhead sources with measurement and mitigation:

1. Job Setup (JVM launch, task scheduling):
Measure: Time between job submission and first mapper start (in JobTracker UI or job history)
Reduce: Use YARN Uber mode for small jobs; pre-warm JVM pools; increase reuse between tasks

2. HDFS Read (Map input):
Measure: Hadoop counter "HDFS_BYTES_READ" / ratio of data-local vs remote reads (JobTracker task logs)
Reduce: Ensure data locality — check % local reads. Compress input data (use splittable Snappy/BZip2 to maintain parallelism)

3. Map Output Sort (intermediate sort):
Measure: Compare "MAP_OUTPUT_BYTES" to "MAP_OUTPUT_MATERIALIZED_BYTES"; sort time in task logs
Reduce: Use Combiner to reduce map output size before sort; increase io.sort.mb config; reduce number of output partitions

4. Network Shuffle (Copy phase):
Measure: "REDUCE_SHUFFLE_BYTES" counter; network utilisation metrics
Reduce: Compress map output (mapreduce.map.output.compress=true); use Combiner to reduce shuffle volume; collocate reducers near map output where possible

5. HDFS Write (final output + intermediate):
Measure: "HDFS_BYTES_WRITTEN" counter; DataNode write throughput
Reduce: Compress output; consider whether intermediate HDFS writes can be eliminated by switching to Spark

📋 2023 Exam — Q2c: Spark Advantages over Hadoop (8 marks)

8 marks ▼
The news aggregator team is considering migrating from Hadoop to Apache Spark. Discuss the advantages Spark would offer for their use case, including how Spark addresses Hadoop's limitations for iterative batch processing and ad-hoc analytics.
Key advantages (award 2 marks per well-explained point):

1. In-Memory Processing (eliminates intermediate disk I/O):
Spark stores intermediate RDDs in RAM. For the news aggregator's multi-step pipeline (count citations → rank top-10), Spark avoids 2× HDFS write + 2× HDFS read between Job 1 and Job 2. With 10M articles, this could eliminate tens of GB of disk I/O per run.

2. RDD Caching for Iterative Workloads:
If the same source RDD (e.g., all 10M articles) is needed by multiple analytics queries, .persist() keeps it in memory. Subsequent queries skip data loading entirely — critical for ad-hoc analytics and A/B query development.

3. Flexible Execution via DAGs:
Spark's DAG scheduler allows arbitrary transformation chains (Map→Map→Filter→GroupBy→Sort→Take) without the Hadoop enforced Map→Reduce→Map→Reduce structure. Eliminates unnecessary Reduce phases for filtering-only workloads.

4. Lazy Execution Optimisation:
Spark defers computation until an Action is called, allowing the scheduler to optimise the full pipeline (e.g. push-down filters, eliminate dead code paths). Hadoop always executes the full specified pipeline.

5. Richer API:
PySpark / Spark SQL allows analysts to query 10M articles with SQL or Python, reducing development time. Hadoop requires full Java MapReduce code for every operation.

📋 2025 Exam — Q2: Hadoop Job Execution Steps (part of Q2)

~4 marks ▼
Describe what happens between the point at which a client submits a Hadoop MapReduce job and the point at which a Map task begins executing on a worker node.
Key steps in order (2 marks for correct order, 2 marks for detail):

1. Client contacts JobTracker to get a Job ID
2. Client uploads Job.jar (compiled MapReduce code) to HDFS
3. Client submits the job to the JobTracker
4. JobTracker initialises the job and queries the NameNode for input split locations
5. JobTracker uses data locality information to assign the Map task to a TaskTracker that has the data locally
6. TaskTracker receives the task assignment via heartbeat
7. TaskTracker downloads Job.jar from HDFS
8. TaskTracker spawns a new JVM process
9. JVM loads Job.jar and begins executing the Map task by reading its assigned data split from the local DataNode

Practice Questions

1. A company has 500 million small log files (average 2KB each) stored in HDFS. Explain what problem arises and describe two concrete solutions.

Problem: HDFS block size = 128MB (default). Each 2KB file gets its own block entry in the NameNode's in-memory index. 500 million files = 500 million NameNode index entries. The NameNode JVM heap (typically 256MB-1GB) runs out of memory. Additionally, each file = one Map task → 500 million Map task launches = unsustainable scheduling overhead.

Solutions:
1. Merge files: Pre-process to combine many small log files into large files (e.g., daily archives). Use CombineFileInputFormat to merge small splits at job time.
2. Hadoop Archives (HAR): Pack many small files into a HAR file — provides a single HDFS block entry for multiple files. Cost: slower random access (must read HAR index first).
3. (Bonus) Store log data in HBase tables instead of files — HBase uses LSM trees which handle small random writes efficiently.

2. Explain the difference between Spark Transformations and Actions. Give one example of each and explain why this distinction matters for performance.

Transformation: Converts one RDD into another RDD. Lazy — defined but not executed until an Action is called. Example: filter(lambda x: x.contains("crypto")) on a text RDD returns a new filtered RDD, but no computation happens.

Action: Triggers actual execution and returns a result or writes to storage. Example: count() counts records in an RDD and returns an integer to the driver.

Why it matters: Lazy evaluation allows Spark to build a complete execution plan (DAG) before running anything. This enables:
- Whole-pipeline optimisation (e.g., push filters earlier to reduce data volume)
- Elimination of unnecessary computation branches (only executes what's needed for the action)
- Combining multiple transformations into a single stage without intermediate materialisation

3. What is a DAG in the context of Apache Spark, and how does it differ from Hadoop's job structure? What are "stages" within a DAG?

DAG (Directed Acyclic Graph): When a Spark job is submitted, all transformations are compiled into a directed graph of tasks with dependencies. Directed = tasks have a direction (A produces B). Acyclic = no circular dependencies. Represents the order in which tasks must execute.

Difference from Hadoop: Hadoop jobs have a fixed, static structure (always Map → Sort → Write → Copy → Reduce → Write). Spark's DAG is dynamic — determined by the transformations the developer chains together. A Spark job could be Map→Map→Filter→GroupBy→Sort→Collect with no enforced structure.

Stages: The Spark scheduler partitions the DAG into stages. Tasks within a stage can run in parallel on different partitions. A stage boundary occurs when data needs to be shuffled (e.g., at a reduceByKey or join). Stage N cannot begin until Stage N-1 is complete. Example: Stage 1 = read + filter (narrow transformations), Stage 2 = reduceByKey (shuffle boundary), Stage 3 = collect (action).

4. A team is choosing between Hadoop and Spark for two different workloads: (A) a one-time 10TB historical data ETL job, (B) a daily ML training pipeline with 50 iterations on a 100GB dataset. Which would you recommend for each, and why?

Workload A (one-time 10TB ETL): Hadoop or Spark both acceptable, slight edge to Spark
For a one-time sequential scan, Hadoop's disk-based approach works fine. However, Spark is still faster (2-3×) even for single-pass ETL due to lower task setup overhead and in-memory intermediate writes. If the cluster has sufficient RAM for the output, Spark is preferred. If RAM is limited, Hadoop's disk-based approach is more memory-efficient.

Workload B (50-iteration ML training on 100GB): Strongly recommend Spark
Iterative algorithms are where Spark's advantage is most dramatic. With Hadoop, each iteration reads the full 100GB from HDFS, processes it, writes intermediates back to HDFS, then starts again. 50 iterations = 50 full dataset reads + 50 writes = 5TB of I/O.

With Spark: Load the 100GB once into memory with .persist(). Iterations 2-50 read from in-memory RDD, not disk. Benchmark: Hadoop = 127s/iteration, Spark iteration 2+ = 6s/iteration (21× faster). Total: Hadoop ~6350s vs Spark ~380s.
