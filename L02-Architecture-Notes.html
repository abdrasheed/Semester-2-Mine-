Part 1: Text Processing

Why Process Text?

IR models use statistical properties of text ("bag of words"). We need to convert raw text into a normalised set of index terms. Three main steps: Tokenisation → Stopword Removal → Stemming.

Step 1: Tokenisation (Lexical Analysis)

Converts a stream of characters into a stream of words (tokens). Not as simple as splitting on spaces!

Issues to handle:

  • Numbers: 1999 vs 510B.C.
  • Hyphens: state-of-the-art vs B-49
  • Punctuation: 510B.C. vs list.id
  • Case: Bank vs bank
  • Multi-language: Arabic, Chinese, Cyrillic

Small decisions matter:

Tokenisation choices have major impact on retrieval effectiveness for some queries. E.g. treating "C.A.T." as one token vs three affects retrieval for abbreviation queries.

Step 2: Stopword Removal

Words too frequent in a collection are poor discriminators — called stopwords.

  • Examples: the, am, and, of, in, to
  • Reduces index size considerably
  • Strategies: list lookup, frequency analysis (remove terms in >80% of docs)

⚠️ Care needed!

Some phrases lose meaning: "to be or not to be" — all words are stopwords! Modern IR often retains stopwords in the index but ignores them at query processing time.

Step 3: Stemming (Conflation)

Reduces word variants to a single root form. E.g. connect is the stem for connected, connecting, connections.

Benefits:

  • 5–10% improvement for English
  • Up to 50% improvement in Arabic
  • Reduces index size 10–50%
  • User doesn't need to submit variants

Problems:

  • GRAVITY (place) ≠ GRAVITATION → GRAVITY
  • Overstemming: "universe" → "univers"
  • Can collapse distinct meanings

Example: Porter Stemmer Rules

  • Rule: (.*)SSES → \1SS — e.g., possesses → possess
  • Rule: (.*[AEIOU].*)ED → \1 — e.g., shared → shar
  • Rule: (.*[AEIOU].*)ING → \1 — e.g., running → run

Text Processing Pipeline Example

Python: Text Processing Pipeline

import re
from nltk.corpus import stopwords
from nltk.stem import PorterStemmer

def process_text(text):
    # Step 1: Tokenise (lowercase, split on non-alphanumeric)
    tokens = re.findall(r'[a-zA-Z0-9]+', text.lower())
    
    # Step 2: Remove stopwords
    stop = set(stopwords.words('english'))
    tokens = [t for t in tokens if t not in stop]
    
    # Step 3: Stem
    stemmer = PorterStemmer()
    tokens = [stemmer.stem(t) for t in tokens]
    
    return tokens

text = "Twinkle, twinkle, little bat. How I wonder what you're at!"
print(process_text(text))
# Output: ['twinkl', 'twinkl', 'littl', 'bat', 'wonder']

Part 2: Indexing — The Inverted Index

Why an Inverted Index?

Without an index: to answer a query, we scan every document — infeasible for billions of pages. With an inverted index: we jump directly to the posting list for each query term, then intersect/score. Response time: milliseconds.

Inverted Index Structure

Inverted Index Summary

An index contains three sub-structures:

Lexicon

All unique terms and their statistics (df, cf). Stored in sorted order for fast lookup.

Inverted Index

Term → posting list. Each posting has (docID, tf, positions). The core retrieval structure.

Document Index

All documents and their statistics (length, URL, PageRank, etc.).

Python: Building an Inverted Index

from collections import defaultdict

def build_index(docs):
    # docs: {docid: text}
    index = defaultdict(lambda: defaultdict(int))
    
    for docid, text in docs.items():
        tokens = process_text(text)  # from earlier
        for token in tokens:
            index[token][docid] += 1  # tf
    
    return dict(index)

docs = {1: "now is the time for all good men",
        2: "it was a dark and stormy night in the country"}

idx = build_index(docs)
print("time:", idx['time'])    # {1: 1}
print("dark:", idx['dark'])    # {2: 1}
print("country:", idx['countri']) # {2: 1} (stemmed)

Index Construction Algorithms

The Challenge

For web-scale collections (billions of documents), the inverted index is too large to build in RAM. Two classic algorithms solve this: BSBI (Block Sort-Based Indexing) and SPIMI (Single-Pass In-Memory Indexing).

BSBI — Block Sort-Based Indexing

Processes documents in fixed-size blocks that fit in RAM, sorts each block, then merges. Requires a global term dictionary.

BSBI Algorithm
BSBI-Index-Construction():
  while (collection not exhausted):
    block ← ParseNextBlock()          // Read a block of docs
    BSBI-Invert(block)                 // Create (termID, docID) pairs
    SortAndWrite(block, disk)          // Sort pairs, write to disk
  MergeBlocks(all blocks on disk)      // Merge sorted runs → final index

Steps in Detail

  1. Accumulate (termID, docID) pairs in memory
  2. When block full: sort by termID, then docID
  3. Write sorted block to disk as a "run"
  4. Repeat for all blocks
  5. Merge all sorted runs into final inverted index

Limitation of BSBI

Requires a global term dictionary mapping terms to integer termIDs. This dictionary must fit in RAM — problematic for very large collections. SPIMI avoids this.

SPIMI — Single-Pass In-Memory Indexing

Avoids the need for a global term dictionary. Instead, builds partial inverted indexes directly in memory and writes them to disk when memory is full. Faster and more memory-efficient than BSBI.

SPIMI Algorithm
SPIMI-Invert(token_stream):
  output_file = newFile()
  dictionary = newHashMap()
  while (memory not full):
    token = next(token_stream)         // (term, docID) pair
    if term not in dictionary:
      dictionary[term] = newPostingList()
    posting_list = dictionary[term]
    if posting_list is full:
      posting_list = doublePostingList(posting_list)
    posting_list.append(docID)
  sorted_terms = SortTerms(dictionary)
  WriteBlockToDisk(sorted_terms, dictionary, output_file)
  return output_file

Key SPIMI Advantages

  • No global term dictionary needed — terms added as encountered
  • Posting lists grow dynamically (doubled when full)
  • Single pass through document collection
  • Handles any vocabulary size
  • Faster: no sorting of (termID, docID) pairs — sort only terms
BSBI vs SPIMI Comparison
FeatureBSBISPIMI
Term dictGlobal (in RAM)Local per block
SortingSort all (termID,docID) pairsOnly sort terms
SpeedSlowerFaster
MemoryNeeds dict in RAMMore flexible

Distributed Indexing (MapReduce)

At web scale (billions of docs), even SPIMI is too slow for a single machine. Google uses MapReduce-style distributed indexing:

  • Map phase: Each machine processes a shard of documents → emits (term, docID) pairs
  • Reduce phase: Group by term → merge posting lists → write to distributed index
  • Enables indexing of the full web in hours using thousands of machines

Index Compression

Why Compress?

The inverted index for the web can be hundreds of GB. Compression reduces: (1) disk footprint, (2) I/O time (read compressed data faster than uncompressed), (3) can fit more in RAM. Decompression is fast enough to be done on-the-fly during retrieval.

Step 1: Gap Encoding (d-gaps)

Instead of storing raw docIDs, store the difference (gap) between consecutive docIDs in a posting list. Since docIDs are sorted, gaps are always positive. Small gaps = fewer bits needed.

Example: Gap Encoding

Raw posting list for term "the": [1, 5, 12, 25, 200, 201]

After gap encoding: [1, 4, 7, 13, 175, 1]

For frequent terms like "the", gaps are small → very compressible. For rare terms, gaps are large but there are few entries anyway → still efficient overall.

Step 2: Variable-Byte (VB) Encoding

Encode each gap as a variable number of bytes. Small gaps use 1 byte; larger gaps use 2, 3, or 4 bytes. The most significant bit of each byte signals whether more bytes follow.

Variable-Byte Encoding Format
Each byte: [continuation_bit | 7 bits of data]
  - continuation_bit = 1: more bytes to follow
  - continuation_bit = 0: this is the last byte

Example: gap = 5 (binary: 101)
  → One byte: [0|000 0101] = 0x05

Example: gap = 214 (binary: 1101 0110)
  → Two bytes: [1|000 0001] [0|101 0110] = 0x81 0x56

Numbers 0-127: 1 byte; 128-16383: 2 bytes; etc.

VB Encoding Example

Gaps: [5, 128, 2]

  • Gap 5: 00000101 (1 byte)
  • Gap 128: 10000001 00000000 (2 bytes)
  • Gap 2: 00000010 (1 byte)

Total: 4 bytes vs 3×4=12 bytes uncompressed

Other Compression Schemes

  • Unary coding: encode n as n ones followed by a zero. Simple but only good for very small gaps.
  • Gamma coding: Elias gamma — more complex, better compression for skewed distributions.
  • PForDelta: used in modern search engines (Elasticsearch, Lucene) — pack groups of 128 gaps.
Worked Compression Example

Posting list for "cat": docIDs = [3, 7, 11, 15, 20]

Step 1 — Gaps: [3, 4, 4, 4, 5]

Step 2 — VB encode each (all <128, so 1 byte each): [03, 04, 04, 04, 05]

Compressed size: 5 bytes vs 5×4=20 bytes uncompressed = 75% reduction

Skip Pointers

Why Skip Pointers?

When computing AND (intersection) of two posting lists, we must merge them. For lists of length \(m\) and \(n\), naive merge takes \(O(m+n)\). Skip pointers allow us to jump ahead in a list, skipping large portions that can't possibly intersect. This speeds up AND queries significantly when lists are long and the intersection is small.

Skip Pointer Structure

At regular intervals in the posting list, add a "skip" pointer that jumps ahead by \(\sqrt{L}\) entries (where L is the list length). Each entry that has a skip also stores the docID at the skip destination.

Example: AND intersection with skips

List A: [2, 4, 8, 41→, 48, 64, 128] (skip from 8 to 41)

List B: [1, 2, 3, 8, 11, 17, 21, 50, 64]

Merging at docID 8: both lists have 8 → add to result. Now advance A. A's skip points to 41; B's current is 11. Since 11 < 41, we can't use the skip yet. Advance B normally... when B reaches 50, A's current is 41 — use A's normal advance to 48, then 64. B also has 64 → add to result.

Result: [2, 8, 64] — with skips, we avoided inspecting A's entries 4, 48 (jumped from 8 to 41).

Optimal Skip Interval

For a posting list of length \(L\), place a skip every \(\sqrt{L}\) entries. This gives \(\sqrt{L}\) skip pointers, each spanning \(\sqrt{L}\) entries. Empirically the best trade-off between skip overhead and skip savings.

Skip Pointers and Compression

Skip pointers are harder to use with compressed posting lists since we can't easily random-access mid-list. Modern systems (e.g., using PForDelta in blocks) add skips at block boundaries, giving block-level skipping.

The Boolean Retrieval Model

Boolean Queries

The simplest retrieval model. Documents are retrieved if they satisfy a Boolean expression over query terms. No ranking — output is a set.

AND

Document must contain ALL terms. "cat AND dog" → only docs with both. Tends to give too few results.

OR

Document must contain ANY term. "cat OR dog" → docs with either. Tends to give too many results (information overload).

NOT

Document must NOT contain the term. "cat NOT dog" → docs with cat but without dog. Rarely used alone.

AND Intersection Algorithm

To compute "term1 AND term2": retrieve both posting lists (sorted by docID), then merge them like merge sort — only output docIDs that appear in both.

Posting List Intersection (AND)
Intersect(P1, P2):
  result = []
  p1, p2 = pointers to start of P1, P2
  while p1 ≠ END and p2 ≠ END:
    if P1[p1].docID == P2[p2].docID:
      result.append(P1[p1].docID)
      advance p1; advance p2
    elif P1[p1].docID < P2[p2].docID:
      advance p1
    else:
      advance p2
  return result
  // Time complexity: O(|P1| + |P2|)
Worked AND Intersection Example

P("time") = [1, 4, 7, 11, 21, 31, 41]
P("dark") = [2, 4, 11, 16, 21, 35, 41, 50]
Query: "time AND dark"

Merge: 1<2→adv p1 | 4=4→output 4, adv both | 7<11→adv p1 | 11=11→output 11, adv both | 21=21→output 21, adv both | 31<35→adv p1 | 41=41→output 41, adv both

Result: [4, 11, 21, 41] — inspected 15 entries total (7+8), returned 4.

Query Optimisation: Shortest List First

For multi-term AND queries, process terms in order of increasing posting list length (shortest first). This minimises the number of docIDs compared at each step.

Example: 3-term AND Query

Query: "cat AND dog AND zoo"

  • P("zoo"): length 50 (rare term)
  • P("cat"): length 1,200
  • P("dog"): length 3,500

Optimal order: intersect(zoo, cat) → get ~50 result → intersect that with dog. Much faster than starting with "dog".

Problems with Pure Boolean Retrieval

  • Null output: too many ANDs → zero results
  • Information overload: too many ORs → thousands of unranked results
  • No ranking: all matching documents treated equally
  • Exact term matching: misses synonyms and near-matches
  • Solution: Best-match (ranked) retrieval

Zone Indexes & Weighted Zone Scoring

What are Zones?

Documents have structure: title, abstract, body, author, URL. A zone is a named field of a document. Zone indexes extend the inverted index to record which zone each term occurrence is in.

Zone Index (Fielded Index)

Each posting entry records not just (docID, tf) but also the zone in which the term appears: e.g., (docID=5, zone=TITLE, tf=1). Posting list format: term → [(docID, zone, tf), ...]

Weighted Zone Scoring

Assign different weights to different zones — a match in the title is more indicative of relevance than a match in the body. The overall relevance score is a weighted sum over zones.

Weighted Zone Score
\[ \text{Score}(d, q) = \sum_{z \in \text{zones}} w_z \cdot \text{match}(q, d, z) \]

where \(w_z\) is the weight of zone \(z\) (learnt from training data or set manually), and \(\text{match}(q, d, z)\) is 1 if the query term appears in zone \(z\) of document \(d\), else 0. Weights must sum to 1: \(\sum_z w_z = 1\).

Worked Example: Weighted Zone Scoring

Query: "information retrieval". Document d has: title="Information Retrieval Systems", body="...learning information...

Zone weights: title=0.6, body=0.4.

match("information", d, title)=1, match("retrieval", d, title)=1, match("information", d, body)=1, match("retrieval", d, body)=0.

Per-term scores: "information": 0.6×1 + 0.4×1 = 1.0; "retrieval": 0.6×1 + 0.4×0 = 0.6.

Final score = (1.0 + 0.6) / 2 = 0.8

Typical Zone Weights

  • Title: 0.4–0.6 (high — title summarises content)
  • Abstract / Description: 0.2–0.3
  • Body: 0.1–0.2 (low — less discriminative)
  • Anchor text: 0.3–0.5 (very informative on the web)
  • URL: 0.1–0.2

Weights are often learnt from click-through data using machine learning.

Learning Zone Weights (Preview)

Given training examples (query, doc, relevant/not), learn weights \(w_z\) that minimise classification error. This is the simplest form of Learning to Rank — treating retrieval as a binary classification problem. Covered in detail in L08.

Dynamic Indexing

The Problem: The Web Changes

Documents are added, deleted, and modified constantly. Rebuilding the full index from scratch every time is too slow. Dynamic indexing strategies maintain the index incrementally.

Main Index + Auxiliary Index

Keep a large main index on disk. New documents go into a small auxiliary index in RAM. At query time, search both and merge results. Periodically merge auxiliary into main index.

Invalidation Lists (Deletions)

When a document is deleted or updated, add it to an invalidation list. At retrieval time, filter out invalidated docIDs from results. Actual removal happens during next index merge.

Logarithmic Merge Strategy

Maintain a series of indexes of exponentially growing sizes: \(I_0, I_1, I_2, \ldots\) where \(|I_k| = 2^k \cdot Z_0\). When \(I_0\) is full, merge with \(I_1\); if \(I_1\) overflows, merge with \(I_2\), etc. Amortised merge cost is \(O(\log^2 T)\) per document where \(T\) is total docs. Used in Lucene's segment-based architecture.

Logarithmic Merge Example

Z₀ = 2 documents per level. After 8 documents added:

  • I₀: [d7, d8] (newest 2)
  • I₁: [d5, d6] (merged from I₀ overflow)
  • I₂: [d1, d2, d3, d4] (merged I₀+I₁ overflow)

Query searches all three levels and merges results. This avoids rebuilding one large index.

Part 3: Retrieval & Best-Match Algorithm

Boolean Retrieval vs Best-Match

Boolean (AND):

  • All query terms must match
  • All terms treated equally (binary)
  • Returns a set (unordered)
  • E.g. "time AND dark" → Doc 2 only

Best-Match (Ranked):

  • More matching terms = higher score
  • Terms weighted by importance (TF-IDF)
  • Returns ranked list
  • More flexible, better user experience
Best-Match Retrieval Algorithm (Co-ordinated Search)
For each document I, Score(I) = 0
For each query term t_k:
    Search the lexicon for t_k
    Pull out the posting list P(t_k)
    For each document J in P(t_k):
        Score(J) = Score(J) + weight(t_k, J)
Return documents sorted by Score descending
🔶 Practice Example

Given index: run → [Doc1(tf=3), Doc2(tf=1)], shoe → [Doc1(tf=2), Doc3(tf=5)]. Query: "run shoe" (binary weights). Compute Score for Doc1, Doc2, Doc3.

✅ Solved Example

Start: Score[1]=Score[2]=Score[3]=0
Process "run": Doc1 → Score[1]+=1=1; Doc2 → Score[2]+=1=1
Process "shoe": Doc1 → Score[1]+=1=2; Doc3 → Score[3]+=1=1
Final ranking: Doc1=2, Doc2=1, Doc3=1 → Doc1 is most relevant!

Relevance Estimation

The process of computing a numeric relevance score for each document. Requires:

  • Term Weighting — assigns numerical values to index terms (e.g., TF-IDF)
  • Similarity Coefficient — combines weights to compute overall similarity (e.g., Cosine, Dice)

More detail on weighting models in L03 and L07!

Summary

Text Processing

Tokenisation + Stopword Removal + Stemming → normalised {docID, term, frequency} triples.

Inverted Index

Term → [docID, tf] mapping enabling O(1) term lookup. Consists of Lexicon, Inverted Index, Document Index.

Index Construction

BSBI: sort (termID,docID) pairs per block, merge. SPIMI: build partial indexes per block without global dictionary — faster and more scalable. Distributed indexing (MapReduce) for web scale.

Index Compression

Gap encoding (d-gaps) + Variable-Byte encoding reduces index size dramatically. Skip pointers (every √L entries) speed up AND intersection. Both save I/O and RAM.

Boolean Model

AND/OR/NOT over posting lists. AND intersection: O(|P1|+|P2|) two-pointer merge. Optimise: process shortest list first. Problems: null output (AND) and information overload (OR).

Zone Indexes & Dynamic Indexing

Zone indexes record per-field occurrences; weighted zone scoring weights title matches more than body matches. Dynamic indexing uses auxiliary index + invalidation list for real-time updates.

Retrieval

Best-match: score each document by summing term weights for matching query terms. Return ranked list.

Key Trade-off

The inverted index dramatically speeds up retrieval at the cost of storage and preprocessing time. Offline indexing; online retrieval.

Short Answer Questions
Q1. Describe the three steps of text processing and explain the purpose of each.
(1) Tokenisation: converts raw text to a stream of words, handling punctuation, hyphens, numbers, case. Creates candidate index terms. (2) Stopword Removal: removes high-frequency, low-discriminative words (the, and, of) to reduce index size and improve retrieval speed. (3) Stemming: reduces morphological variants to a common root (running → run) so query terms match document terms even if inflected differently.
Q2. What is a posting list and what information does it contain?
A posting list is an entry in the inverted index for a specific term. It contains: (1) the document IDs of all documents containing the term; (2) the term frequency (tf) in each document; (3) optionally, positions of occurrences for phrase/proximity queries. The list is typically sorted by docID for efficient intersection operations.
Q3. Explain why Boolean AND retrieval can suffer from "null output" or "information overload".
Null output: with many query terms connected by AND, only documents containing ALL terms are returned. Rare combinations return nothing. Information overload: with OR, any document matching any term is returned, potentially thousands of unranked results. Best-match retrieval avoids both by returning ranked results with partial matches.
Q4. How are inverted files created? Describe the main steps.
(1) Parse all documents, extract tokens, assign docIDs. (2) Create (term, docID, tf) triples. (3) Sort triples alphabetically by term (then by docID). (4) Merge triples for the same term into posting lists. (5) Compress posting lists for storage efficiency. (6) Store sorted lexicon for fast binary search. This is done offline before any queries are processed.
Q5. What is the difference between BSBI and SPIMI index construction algorithms?
Both process large collections in memory-sized blocks and merge on disk. BSBI creates (termID, docID) pairs, sorts them, and writes sorted runs to disk — requires a global term dictionary in RAM. SPIMI builds partial inverted indexes directly without a global dictionary: for each token it appends the docID to the term's posting list, growing the list dynamically. When memory is full, it sorts terms and writes the block. SPIMI is faster (only sort terms, not all pairs) and handles larger vocabularies.
Q6. Explain skip pointers. When do they provide the greatest benefit?
Skip pointers are extra forward pointers placed every √L positions in a posting list of length L. During AND intersection, if the skip destination is still less than the current position in the other list, we can jump ahead without inspecting each intermediate entry. Greatest benefit: when posting lists are long and the intersection is small (many entries can be skipped). Least benefit: when the intersection is large relative to list size — few skips are possible because lists advance together. Also, skips are harder to use with heavily compressed lists.
Q7. What is dynamic indexing and why is it needed?
Dynamic indexing allows an IR system to handle documents that are added, updated, or deleted without rebuilding the entire index from scratch. The approach: maintain a large main index on disk and a small auxiliary index in RAM for new documents. At query time, search both and merge results. Deletions are tracked via an invalidation list and filtered at query time. Periodically the auxiliary index is merged into the main index. This is essential for web search where millions of pages change daily. Lucene uses a logarithmic merge strategy (segment-based) for efficient incremental updates.

Q3. Describe the BSBI and SPIMI algorithms for large-scale index construction. What problem does each solve, and what is the key advantage of SPIMI over BSBI?
Problem [1 mark]: Web-scale collections are too large to build an inverted index entirely in RAM. Both algorithms process the collection in blocks, writing partial indexes to disk and merging.

BSBI [3 marks]: Block Sort-Based Indexing. (1) Parse document block → create (termID, docID) pairs. (2) Sort pairs by termID, then docID. (3) Write sorted block to disk as a "run". (4) Repeat. (5) Merge all sorted runs into final index. Requires a global term→termID dictionary in RAM — problematic for very large vocabularies.

SPIMI [3 marks]: Single-Pass In-Memory Indexing. Processes the token stream one pass. For each (term, docID): if term not in local dictionary, create new posting list; else append docID. When memory full, sort terms and write block to disk. No global dictionary needed — terms mapped locally per block.

SPIMI advantage [1 mark]: No global term dictionary required. Posting lists grow dynamically. Faster because only terms (not (termID,docID) pairs) need sorting. More memory efficient — can handle arbitrarily large vocabularies.
H[6 marks]
Q4. Explain gap encoding and variable-byte encoding as methods of index compression. Given the posting list for term "run" = [3, 7, 11, 200, 201, 350], show the gap-encoded sequence and describe how variable-byte encoding would store gap 197.
Gap encoding [2 marks]: Instead of storing raw docIDs, store the difference between consecutive docIDs (d-gaps). Since posting lists are sorted by docID, gaps are always positive. Small gaps (common for frequent terms) require fewer bits. The posting list [3, 7, 11, 200, 201, 350] becomes gaps: [3, 4, 4, 189, 1, 149].

Variable-byte encoding [2 marks]: Each integer is encoded using a variable number of bytes. The most significant bit of each byte is a continuation flag (1=more bytes follow, 0=last byte). The remaining 7 bits of each byte carry data. Numbers 0–127 need 1 byte; 128–16383 need 2 bytes, etc.

Encoding gap 197 [2 marks]: 197 in binary = 11000101. Since 197 > 127, needs 2 bytes. Low 7 bits = 1000101 = 69. High bits = 1 = 0000001. Encode as: byte1 = [1|0000001] = 0x81 (continuation), byte2 = [0|1000101] = 0x45 (final). So gap 197 = bytes [0x81, 0x45].

Q5. Describe the Boolean AND intersection algorithm for two posting lists. Given P("computer") = [1, 3, 5, 8, 11, 17] and P("science") = [2, 3, 7, 8, 11, 14, 21], trace through the intersection algorithm step by step and give the result. Then explain the query optimisation strategy for multi-term AND queries.
Algorithm [2 marks]: Two pointers p1, p2 start at beginning. While both lists unexhausted: if P1[p1]==P2[p2], output docID and advance both; if P1[p1]<P2[p2], advance p1; else advance p2. Time: O(|P1|+|P2|).

Trace [4 marks]:
p1=1, p2=2: 1<2 → advance p1
p1=3, p2=2: 3>2 → advance p2
p1=3, p2=3: 3=3 → output 3, advance both
p1=5, p2=7: 5<7 → advance p1
p1=8, p2=7: 8>7 → advance p2
p1=8, p2=8: 8=8 → output 8, advance both
p1=11, p2=11: 11=11 → output 11, advance both
p1=17, p2=14: 17>14 → advance p2
p1=17, p2=21: 17<21 → advance p1 → p1=END
Result: [3, 8, 11]

Query optimisation [2 marks]: For multi-term AND queries with k terms, process posting lists in order of increasing length (shortest first). After intersecting the two shortest lists, the intermediate result is at most as large as the shorter list. This intermediate result is then intersected with the next shortest list. Processing shortest-first minimises the total number of comparisons at each step.
H[6 marks]
Q6. Explain zone indexes and weighted zone scoring. Given zone weights w(title)=0.6, w(body)=0.4, and two documents: Doc1 has query term in title and body; Doc2 has query term in body only. Compute the weighted zone score for each document and rank them.
Zone indexes [2 marks]: Extend the inverted index to record which zone (field) of a document each term occurrence is in. A zone is a named region of a document (title, abstract, body, anchor text, URL). Posting list entries include zone information: (docID, zone, tf). This allows the retrieval system to weight matches differently by zone.

Weighted zone scoring [2 marks]: Score(d,q) = Σ_z w_z × match(q,d,z), where w_z is the weight of zone z (Σw_z=1) and match=1 if the query term appears in zone z of document d.

Computation [2 marks]:
Doc1: match(title)=1, match(body)=1 → Score = 0.6×1 + 0.4×1 = 1.0
Doc2: match(title)=0, match(body)=1 → Score = 0.6×0 + 0.4×1 = 0.4
Ranking: Doc1 (1.0) > Doc2 (0.4). Title match is much more valuable, correctly reflecting that title terms are stronger indicators of document content.

Additional True / False Questions
7. BSBI requires a global term dictionary that maps terms to integer IDs.
TRUE — BSBI works with termIDs, so a global term→termID dictionary must be maintained in RAM.
8. Gap encoding is effective because posting lists are sorted in ascending docID order.
TRUE — Sorted order ensures all gaps are positive and typically small for frequent terms.
9. Boolean OR retrieval returns a ranked list of documents.
FALSE — Boolean retrieval (AND/OR/NOT) returns an unordered set. No ranking is produced.
10. Zone weights must sum to 1 in weighted zone scoring.
TRUE — Zone weights are typically normalised to sum to 1, making the score a convex combination of zone matches.
11. In dynamic indexing, deleted documents are immediately removed from the main index.
FALSE — Deletions are recorded in an invalidation list and filtered at query time; actual removal happens during index merge.
12. Skip pointers work best when the intersection of two posting lists is large relative to list sizes.
FALSE — Skip pointers are most beneficial when the intersection is small (many entries can be skipped). If intersection is large, few skips are possible.
Flashcards
Tokenisation
Converting a character stream to a stream of word tokens. Must handle punctuation, hyphens, numbers, case, multi-language.
Stopword
A very frequent word with low discriminative value for retrieval. E.g. "the", "and", "of". Typically removed at indexing or query time.
Stemming
Reducing word variants to a common root form. E.g. connect(ed/ing/ions) → connect. Porter Stemmer is the classic algorithm.
Inverted Index
Core IR data structure: maps each term to a posting list of documents containing it. Enables fast lookup by term.
Posting List
For a given term: list of (docID, tf, [positions]) pairs. Sorted by docID for efficient intersection.
Lexicon
Dictionary of all unique index terms with statistics (df, cf). Sorted alphabetically for O(log n) lookup.
Best-Match Retrieval
Ranks documents by sum of term weights for matching query terms. More matches = higher rank. Returns ranked list, not binary set.
Term Frequency (tf)
Number of times a term appears in a specific document. High tf suggests the document is "about" that term.
BSBI
Block Sort-Based Indexing: processes docs in fixed blocks, creates (termID,docID) pairs, sorts each block, writes to disk, then merges all blocks. Needs global term dictionary in RAM.
SPIMI
Single-Pass In-Memory Indexing: builds partial inverted indexes directly per block. No global term dictionary needed. Faster than BSBI. Handles arbitrarily large vocabularies.
Gap Encoding (d-gaps)
Store differences between consecutive docIDs instead of raw docIDs. Since lists are sorted, gaps are positive and small for frequent terms → highly compressible.
Variable-Byte Encoding
Encode integers using variable number of bytes. MSB is a continuation flag (1=more follows). Numbers <128: 1 byte; 128–16383: 2 bytes. Widely used in Lucene/Elasticsearch.
Skip Pointers
Extra pointers in posting lists placed every √L entries. Allow AND intersection to jump ahead in a list, skipping entries that can't possibly be in the intersection.
Boolean AND
Intersection of posting lists: output only docIDs in BOTH lists. O(|P1|+|P2|) via two-pointer merge. Returns unranked set. Optimise: process shortest list first.
Zone Index
Extended inverted index that records which document field (zone) each term appears in. Enables weighted zone scoring where title matches outweigh body matches.
Weighted Zone Scoring
Score(d,q) = Σ_z w_z × match(q,d,z). Zone weights (Σ=1) reflect importance of each field. Title weight typically highest. Weights can be learnt from training data.
Dynamic Indexing
Main index on disk + small auxiliary index in RAM. New docs added to auxiliary. Deletions tracked via invalidation list. Auxiliary periodically merged into main index.
Null Output Problem
In Boolean AND: too many query terms → no document contains all of them → empty result set. Best-match retrieval solves this by returning partial matches ranked by score.
