⚙️ Week 4a: The Visualisation Pipeline

Based on Card, Mackinlay & Shneiderman (1999). The pipeline describes how raw data becomes an interactive visual representation.

🔄 The Pipeline Stages

Raw Data
→
Data Tables
Transform
→
Visual Structures
Encode
→
Views
Display
↺
Interaction

Transform Stage

Raw data → data tables. Filtering, aggregation, derivation of new values. Example: computing % male from raw male/female counts; binning finish times into 10-minute intervals.

Encode Stage

Data tables → visual structures. Mapping attributes to visual channels. Must be both expressive (encodes all and only the data) and effective (uses best channels for the data type).

Display Stage

Visual structures → views. Rendering to screen. Resolution, colour gamut, display size all constrain what is possible.

Interaction Stage

User manipulates the view, which feeds back into earlier pipeline stages. Key interaction types:

  • Select → change data subset displayed
  • Query → filter or highlight
  • Reconfigure → change encoding
  • Focus+Context → distortion/overview
  • Details on demand → progressive disclosure

🖱️ Interaction Techniques

Focus + Context

Shows detail (focus) while preserving overview (context). Examples:

  • Fisheye distortion: magnifies focal area, compresses periphery
  • Perspective Wall: for large linear data (chronological/alphabetical)
  • Hyperbolic trees: for large hierarchies
  • Overview+Detail: separate overview panel alongside detail view
Exam Definition: Focus+context is NOT the same as a zoomed view. A zoomed view loses context entirely. Focus+context retains the full data while magnifying a region — e.g., fisheye distortion of a map.

Visual Feedback Timing (Responsiveness)

For large datasets: use frontbuffer for selection highlight; show progress bars for long operations; use background threads.

🔍 Week 4b: Data Selection

Selection Methods

Direct Selection ▼

Click on individual items. Simple but limited to visible, single objects. Enhanced by bubble/area cursor which selects the closest object to cursor (not just directly under it).

Brushing & Linking ▼

Select (brush) items in one view → linked view shows same items highlighted. Selection propagates across all linked views simultaneously. Essential for SPLOM analysis.

From: Becker & Cleveland, "Brushing Scatterplots", 1987.

Dynamic Queries ▼

Sliders, checkboxes, range selectors define a query. The view updates in real-time (<0.1s). No typing required. Users explore the data space visually.

Advantage over SQL: no need to know what to look for in advance. Users see the effect of their query instantly — supports discovery tasks.

Example: Attribute Explorer (Spence & Tweedie, 1994); FSMVis demo.

Generalised Selection ▼

Selection uses the semantic model of the data (hierarchy, spatial relationships, categories) rather than just pixel coordinates.

Example — Cars dataset: Rather than clicking individual car dots, you select "all cars manufactured in 1978-1982 with >6 cylinders". The semantic model (car attributes) defines the selection.

Advantage: Can select groups that share a property but are not spatially adjacent in the view. Enables selection at different levels of abstraction.

Query Representation

Tuple-based selection

Store selected items by their data values (a list of item IDs/tuples). Simple and direct. Limited to the items currently visible.

Query-based selection

Store the selection as a query (e.g., "members > 100 AND fees < 30"). More powerful — the query can be applied to new data, used in linked views, and supports generalised selection across hierarchies.

Query-based = declarative query (what, not how). This is the basis of dynamic queries and generalised selection.

Dynamic Queries vs SQL

from vega_datasets import data as vd

cars = vd.cars()

# Create an interval selection (brush)
brush = alt.selection_interval()

# View 1: Scatter (horsepower vs mpg) — brush selects here
scatter = alt.Chart(cars).mark_point(filled=True).encode(
    x=alt.X('Horsepower:Q'),
    y=alt.Y('Miles_per_Gallon:Q'),
    color=alt.condition(brush,
                        alt.Color('Origin:N',
                                  scale=alt.Scale(scheme='category10')),
                        alt.value('lightgray')),  # grey = not selected
    opacity=alt.condition(brush, alt.value(0.9), alt.value(0.2)),
    tooltip=['Name:N', 'Horsepower:Q', 'Miles_per_Gallon:Q']
).add_params(brush).properties(width=350, height=280,
    title='Brush to select cars')

# View 2: Bar chart — linked, shows only selected cars' origin counts
bars = alt.Chart(cars).mark_bar().encode(
    y=alt.Y('Origin:N'),
    x=alt.X('count():Q', title='Number of Selected Cars'),
    color=alt.Color('Origin:N', scale=alt.Scale(scheme='category10'))
).transform_filter(brush).properties(width=350, height=280,
    title='Origin of selected cars')

# Combine side by side
(scatter | bars).properties(title='Brushing & Linking Demo').show()

Question 7 — Generalised Selection (from 2025 paper)

Imagine a dataset of cars' current locations and speeds in some urban area, as tracked by a sensor network. Demonstrate the generalised selection interaction technique using this dataset. Explain what semantic model of the data you would use, and how you would apply generalised selection to it, to improve interaction and analysis when compared to normal direct selection of data objects.

Semantic model: The cars dataset has attributes including location (position), speed (quantitative), car type (categorical: taxi, private, lorry), and heading/direction (quantitative, cyclic). Spatially, the city can be modelled as zones (residential, commercial, motorway corridors). Temporally, rush hours vs. off-peak times form semantic groups.

Normal direct selection (the problem): Clicking on individual car dots on a map selects exactly one car at one moment. With thousands of cars moving, this is: (1) slow — only one car per click; (2) imprecise — difficult to click tiny moving dots; (3) temporally limited — the selection is a snapshot, not a pattern.

Generalised selection using the semantic model:

1. Zone-based selection: Draw a region on the map → select all cars currently within that geographic zone. This is generalised because it uses the spatial semantic structure (zones), not pixel proximity. One gesture selects hundreds of cars.

2. Speed-class selection: Define a speed band (e.g., <10 mph = congested). Selecting "all congested cars" via a slider highlights all matching cars across the entire map — regardless of where they are. This uses the attribute semantic model (speed as a meaningful class, not just a number).

3. Type-based hierarchical selection: Select "all lorries" using the vehicle type hierarchy (vehicles → lorries). This propagates the selection up/down the hierarchy — selecting a type selects all instances.

Improvement over direct selection: Generalised selection allows a single user gesture to select a semantically meaningful group (all cars in zone A travelling over 40 mph), which direct clicking cannot achieve. The declarative query representation means the selection can be applied to linked views (e.g., a time-series chart showing selected cars' speed history) without re-selection.

Question 8 — Dynamic Queries

Your local health service wishes to offer patients access to a database with, for each patient, a medical record with attributes such as medical conditions, prescriptions, hospital visits, and measurements (e.g., heart rate) recorded over time. The service currently has a simple web app offering SQL queries. You are asked to present an alternative design based on dynamic queries. Outline such a design, and present arguments for it compared to the SQL app.

Dynamic Query Design:

The interface would consist of a main display panel (showing a scatterplot, timeline, or map of patient data) with dynamic query controls around it:

  • Age slider (range: 0-100): Double-ended slider → instantly filters to patients in selected age range
  • Condition checkboxes: Tick "diabetes", "hypertension" etc. → immediately shows only matching patients
  • Heart rate range slider: Filters by average/max heart rate value
  • Time range selector: Date picker or timeline brush → shows patients with visits in selected period
  • Prescription dropdown: Multi-select list → filters by prescribed medications

All controls update the display in <0.1 seconds. Selected patients are highlighted; unselected patients fade to grey (not removed). Patient count for current selection is shown prominently.

Arguments for dynamic queries over SQL:

1. No expertise required: Patients or non-technical clinicians cannot write SQL. Dynamic queries require only slider manipulation and checkbox selection.

2. Supports discovery: With SQL, you must know what you're looking for before writing the query. Dynamic queries allow exploration — moving the age slider reveals the distribution of conditions across ages without any predetermined hypothesis.

3. Instant feedback: SQL queries take time to write, execute, and return results. Dynamic queries update at 0.1s — the "as-you-move-it" feedback allows rapid iteration and exploration.

4. Visual overview preserved: SQL shows only query results (a list). Dynamic queries show all patients at all times — selected ones highlighted. This maintains context (how many patients NOT matching the query) which SQL cannot provide.

5. Error prevention: SQL queries can have syntax errors, logical errors, or return empty results without explanation. Dynamic queries cannot have syntax errors; a result of 0 is immediately visible because all dots disappear.

🔢 Week 4b: Multidimensional Visualisation

When the number of dimensions exceeds 3, spatial position alone cannot encode all variables. Multiple strategies exist.

🌀 Dimensional Reduction — Core Concept

Problem: Data has d dimensions (e.g., d=100). We want to show it in 2D while preserving relationships.

Dimensional Reduction: Find a mapping f: ℝᵈ → ℝ² such that similar objects in high-D space remain close in 2D, and dissimilar objects remain far.

\[ \text{Ideal: } \forall i,j: \; dist_{2D}(i,j) \approx dist_{highD}(i,j) \]

This is a 2D layout that retains as much high-dimensional structure as possible.

Methods: Spring models, PCA (matrix methods), t-SNE, UMAP.

⚙️ Spring Models (Force-Directed Layout)

Concept

Simulate springs between every pair of objects. The ideal relaxed length of each spring ∝ high-dimensional distance between those objects.

  • Similar objects (close in high-D) → short spring → pull together
  • Dissimilar objects (far in high-D) → long spring → push apart
  • System reaches equilibrium when spring forces balance

Algorithm (Simplified)

initialise 2D positions randomly
for each iteration:
  for each object i:
    totalForce = [0, 0]
    for each other object j:
      totalForce += force(i, j)
    velocity(i) += ts * totalForce
    position(i) += ts * velocity(i)

Similarity Metric

For quantitative columns: normalise each column to [0,1], then: \[ s = \sum_c |M_{ic} - M_{jc}| \] For categorical columns: multiply s by 1.25 for each mismatch. Finally: \( s = s / D \) (D = number of dimensions)

Complexity Analysis

Naïve spring model:

\[ \text{Per iteration: } O(N^2) \text{ force calculations} \] \[ \text{Overall (≈N iterations): } O(N^3) \]

This limits naïve spring models to N ≈ 10,000–50,000 objects.

Barnes-Hut approximation:

\[ \text{Per iteration: } O(N \log N) \] Uses a spatial tree: nearby objects → exact forces; distant cells → one approximate force from centre of mass.

Chalmers' 1996 sampling method:

\[ \text{Per iteration: } O(N) \] Each object maintains a neighbour set + random sample. Forces calculated only from these, not all N objects.

Exam Calculation Example

Q: First, lay out 5000 objects (50 dims). Then lay out 10000 objects (same 50 dims). How much longer per iteration?

Naïve: O(N²). Ratio = (10000)²/(5000)² = 4× longer.

Answer: 4 times longer per iteration.

Question 9 — Dimensional Reduction (from 2025 paper)

Imagine a dataset with a significant number of objects (e.g., 1,000,000) and a high number of dimensions (e.g., 100). You have one visualisation of a dimensional reduction of the data made using a spring model. You also have several other chart types (bar charts, scatterplots, selectable lists). Describe, in general terms, how and why you would link multiple views of the data.

Why link multiple views:

The spring model 2D layout shows the overall clustering structure of all 100 dimensions combined — it reveals global patterns and groupings. However, it does not show which individual dimensions drive the clustering, nor does it allow inspection of specific attribute values. The bar charts and scatterplots can show individual dimensions precisely, but they cannot show the 100-dimensional structure. Linking combines both capabilities: global structure from the spring model, detail from the individual-dimension views.

How to link the views:

1. Shared data representation: All views must reference the same underlying dataset. Each object has an ID that is shared across all views. When an object is selected in one view, its ID is used to highlight it in all other views.

2. Brushing & Linking: User draws a rectangle over a cluster in the spring model layout → all objects in that spatial region are selected → the bar charts update to show the distribution of each dimension for only the selected objects. This reveals what attributes characterise the cluster.

3. Selectable list: The selectable list shows individual objects. Selecting an object in the list → highlights the corresponding dot in the spring model (locate interaction: target known, position unknown).

4. Cross-filtering: Applying a filter in a bar chart (e.g., select objects with dimension 1 > 0.7) highlights only those objects in the spring model. This links dimensional filters to the spatial layout.

With 1,000,000 objects: Full highlighting of all 1M objects is computationally expensive. Use aggregation in linked views (e.g., histograms of selected objects rather than individual dots in a linked scatterplot). For the spring model, use sampling or clustering to display a representative subset, linking back to the full dataset for detail-on-demand.

🌳 Tree Visualisation Methods

Node-Link Trees (Reingold-Tilford) ▼

Hierarchical layout: parent above/left of children. Compact but without overlap. Rectilinear and radial variants. Good for topology and path tracing. Scalable to 1K-10K nodes with labels.

Treemap ▼

Area containment marks. Hierarchical structure shown by nested rectangles. Leaf node area encodes a quantitative attribute (e.g., file size). Scalable to 1M leaf nodes. Excellent for attribute queries at leaves. Poor for topology/path tasks. Area perception (n=0.7) is a weakness.

Sunburst / Icicle Plot ▼

Implicit tree layout: parent-child shown through position only (not containment or connection). Sunburst = radial; Icicle = rectilinear. Shows inner nodes AND leaves (unlike treemap which only shows leaves visually). Good balance of space efficiency and topology visibility.

Arc Diagrams / Circular Layouts

Nodes arranged around a circle or along a line. Arcs show connections. Node ordering is crucial — barycentric ordering minimises edge crossings, revealing structure.

Hybrid: NodeTrix

Combines node-link (for sparse parts of network) with adjacency matrix (for dense clusters). Best of both: topology navigation with scalable dense cluster representation.

Question 10

A company wants to visualise its employee hierarchy (5,000 employees, 8 levels of management) and also its internal communication network (who emails whom, with frequency data). Compare and contrast three different visualisation techniques for this data. For each technique, describe how it works, what tasks it supports well, what tasks it performs poorly on, and what scalability characteristics it has. Conclude with a recommendation for this specific use case.

Technique 1 — Node-Link Diagram: Nodes = employees, edges = communication links, line thickness = email frequency. Layout algorithm (e.g., Reingold-Tilford for tree hierarchy, force-directed for communication network). Good for: topology understanding (who reports to whom), path tracing (can this message reach the CEO through 3 hops?), intuitive understanding. Poor for: scalability — 5,000 nodes creates dense hairball; dense email networks become unreadable. Scalability: typically <1,000 nodes readable without interaction; 5,000 requires significant aggregation or clustering.

Technique 2 — Adjacency Matrix: Rows and columns = employees (5,000 × 5,000 matrix); cells = email frequency (colour value encoding). After reordering by department, clusters appear as dark squares. Good for: dense networks, scalability (1K+ nodes, millions of edges), finding densely connected groups, attribute-based queries. Good for: attribute distribution across hierarchy (which department communicates most?), scalability to leaves. Poor for: showing cross-hierarchy communication links (the email network), path tracing, topology. Area perception (n=0.7) is a weakness for precise email-count comparison.

Question 10b — Tree Layouts

A university wants to visualise its academic structure: 5 faculties → 40 departments → 800 research groups → 12,000 researchers. The university also wants to show two attributes for each researcher: number of publications (quantitative) and primary research theme (one of 12 categories). (i) Describe three different tree layout techniques and evaluate each against this use case. (ii) Which technique would you recommend, and why? (iii) How would you encode the two researcher attributes in your chosen layout?

(i) Three tree layout techniques:

Node-Link Tree (Reingold-Tilford): Nodes as circles/icons, edges as lines, layout algorithm ensures no overlaps. Clearly shows hierarchy depth (5 levels) and parent-child relationships. Good for path tracing (can this researcher reach the Dean in 4 steps?), topology understanding. Poor for scalability — 12,000 leaf nodes creates an enormous diagram; at any useful zoom level, researcher-level detail is invisible. Leaf area is wasted as whitespace.

Treemap: Recursive subdivision of a rectangle; leaf area = attribute value. 12,000 researchers displayed in a bounded space — excellent scalability. This overrides the equal-area-per-researcher convention, making the most prolific researchers visually prominent. Research theme (categorical, 12 categories): encode as hue (12 distinct hues — at the limit of categorical colour discrimination; use ColorBrewer qualitative palette). Within each research group, the dominant colour shows the dominant theme. Note: area encodes publications (n=0.7, some underestimation) — consider adding a tooltip with exact count for precision. Hue distinguishes theme identity (expressively correct for categorical data).

Question 10c — Adjacency Matrix: Node Ordering

The adjacency matrix is a powerful alternative to node-link diagrams for dense networks. (i) Describe how an adjacency matrix works and how it encodes edge presence, direction, and weight. (ii) Explain why node ordering is critical to the effectiveness of an adjacency matrix, using a concrete example. (iii) Describe two different ordering strategies and explain what structural patterns each one reveals. (iv) State two tasks that adjacency matrices perform better than node-link diagrams, and two tasks they perform worse on.

(i) How adjacency matrix works: An N×N matrix where rows and columns represent nodes. A cell at (i,j) is filled (or coloured) if an edge exists between node i and node j. Edge presence: filled vs. empty cell. Direction: a directed graph has an asymmetric matrix — cell (i,j) ≠ cell (j,i); e.g., row = sender, column = receiver. Edge weight: encode weight as colour value (darker = stronger connection) or cell size. The main diagonal represents self-loops (usually empty).

(ii) Why node ordering is critical: Example — a social network of 100 people from 4 departments. With random ordering, the matrix looks like noise: scattered dark cells with no apparent structure. After reordering nodes by department (all dept A together, then dept B, etc.), clusters emerge as dark 4×4 squares along the diagonal — each square = dense within-department communication. Without reordering, this structure is invisible. The same data, entirely different visual structure depending on ordering.

(iii) Two ordering strategies:

Attribute-based ordering: Sort nodes by a node attribute (e.g., department, geographic region, or quantitative centrality score). Reveals attribute-correlated clusters — do nodes with similar attributes connect to each other? The dark squares along the diagonal reveal community structure. Best for: "do people in the same department communicate more?"

Algorithmic ordering (e.g., spectral reordering or seriation): Apply an algorithm (e.g., Cuthill-McKee, spectral layout) to reorder nodes so that connected nodes are as close as possible on both axes. Reveals the network's natural block structure or gradient structure, independent of external attributes. Often produces a banded pattern along the diagonal — strongly connected subgraphs appear as boxes. Best for: discovering unknown community structure without prior attribute knowledge.

(iv) Comparison:

Adjacency matrix better: (1) Scalability — 1,000-node networks are readable as a matrix; the same as a node-link hairball is unreadable. (2) Finding dense subgraphs — dark squares along the diagonal immediately visible; in node-link this requires manual cluster identification. (3) Large, dense networks with many crossing edges.

Node-link better: (1) Path tracing — "find all paths from A to B in 3 hops" is intuitive by following edges; impossible to do visually in a matrix. (2) Topological intuition — non-experts understand node-link diagrams without training; matrices require learning the encoding. Also: trees and sparse networks look clean as node-link; a sparse matrix is mostly empty and wastes space.

🪟 Multiple Coordinated Views

Multiple views of the same dataset, each showing different aspects, coordinated through shared selection/highlighting.

Why Use Multiple Views?

  • No single vis shows all aspects of complex data
  • Different encodings reveal different patterns
  • Linking allows cross-dimension analysis

To link views, they must share a common data element. If two views share no data items, linking may not be meaningful. Shared database with consistent IDs enables linking.

Question 11b — Focus+Context and Interaction Techniques

An analyst is exploring a large dataset of 10,000 academic papers. She wants to identify papers relevant to her current research topic while maintaining awareness of the broader literature landscape. (i) Explain the focus+context interaction paradigm and contrast it with overview+detail as a separate strategy. (ii) Describe two specific focus+context techniques and explain the trade-offs of each in the context of this use case. (iii) How does "details on demand" complement either approach? Use the Schneiderman mantra to structure your answer.

(i) Focus+Context vs Overview+Detail:

Focus+Context: The focus area (detail) and the context (overview) are shown simultaneously in the same view — the context surrounds the focus. Objects of interest are shown at full resolution; peripheral objects are distorted/compressed but still visible. Benefit: spatial continuity — the user always knows where the focus is within the broader space without switching views. No "view switching" cost.

Overview+Detail: Two separate views — one showing the full dataset at low resolution (overview), one showing a selected region at high resolution (detail). The user navigates by selecting in the overview. Benefit: both views can be optimised independently — the overview is not distorted. Cost: spatial discontinuity — the user must mentally map between the two views. Requires screen real estate for two panels.

Key distinction: Focus+context maintains spatial context within a single view through distortion; overview+detail separates context and detail into distinct panels.

(ii) Two focus+context techniques:

Fisheye View (Furnas, 1986): Items near the focus are magnified; items further away are compressed (geometrically distorted). The degree of interest (DOI) function determines the magnification factor: items close to the focus get high DOI → enlarged; distant items get low DOI → compressed. For 10,000 papers on a 2D canvas: the analyst's current paper is shown at full size; 20 nearest neighbours at medium size; the remaining ~9,980 papers are compressed into the periphery. Advantage: everything is visible simultaneously. Disadvantage: geometric distortion makes it hard to read peripheral paper titles; users may find the distortion disorienting.

Perspective Wall: Uses 3D perspective to create a "wall" effect — the focus area occupies the flat front face; context recedes into two side "wings" using perspective foreshortening. For the paper corpus: a timeline of papers could use a perspective wall — current year's papers at full resolution in the centre; earlier years compressed by perspective into the sides. Advantage: natural "zoom" metaphor, less jarring than fisheye. Disadvantage: the 3D perspective wastes space (wings show much less data per pixel); the distortion is linear and less flexible than fisheye.

(iii) Details on Demand + Schneiderman Mantra:

Schneiderman's mantra: "Overview first, zoom and filter, then details on demand." Applied here: (1) Overview: the full 10,000-paper space is shown — perhaps as a scatter plot of papers by topic (t-SNE/UMAP layout). (2) Zoom and filter: the analyst uses fisheye to zoom into the cluster of relevant papers, or applies a dynamic query to filter to papers published after 2020 on her topic. (3) Details on demand: hovering over a paper shows its abstract and citation count in a tooltip — without cluttering the main view. Details on demand complements focus+context by ensuring that detailed information (full title, authors, abstract) does not need to be shown for all 10,000 papers at once — only the ones the analyst explicitly requests.

Question 12b — Design Space and Design Decisions

A research team is designing a visualisation of climate change data: they have 3 datasets (temperature, CO₂, sea level), 4 colour maps, 3 chart types, and 2 interaction techniques to choose between. (i) Calculate the size of the design space for this project. If they add one more colour map, by what factor does the space grow? (ii) Describe Munzner's "nested model" of visualisation design and explain why it matters for structuring design decisions. (iii) A colleague suggests the team should try all designs in the space before choosing. Critique this suggestion and propose a better strategy.

(i) Design space calculation:

Design space size = 3 datasets × 4 colour maps × 3 chart types × 2 interaction techniques = 72 designs.

Adding one more colour map (4→5): new space = 3 × 5 × 3 × 2 = 90 designs.

Growth factor = 90/72 = 5/4 = 1.25×. The space grows by 25%, not by 5× — only the colour map dimension changes. This illustrates how the design space is multiplicative: a small addition to one dimension has proportionally small impact when other dimensions are unchanged.

(ii) Munzner's Nested Model of Visualisation Design:

The nested model has four layers, each dependent on the one above:

Level 1 — Domain characterisation: Understand the problem domain and users. What data do climate scientists analyse? What questions do they ask? Errors here (wrong domain model) invalidate everything below.

Level 2 — Data/task abstraction: Translate domain problems into IV terms: what data types, what tasks (e.g., "compare CO₂ trend to temperature trend" = compare two quantitative attributes over time). Errors: using the wrong abstraction (treating ordinal as categorical).

Level 3 — Encoding/interaction design: Choose visual encoding (marks, channels) and interaction techniques. Errors: violating expressiveness (using hue for quantitative data) or effectiveness (weak channel for important attribute).

Level 4 — Algorithm design: Efficient implementation. Errors here (slow rendering) don't change the visual encoding — but affect usability.

Why it matters: errors cascade downward. If the domain model is wrong (Level 1), even a perfect encoding (Level 3) solves the wrong problem. Evaluate at each level separately — formative evaluation should check the domain model first, encoding design second.

(iii) Critique and better strategy:

Trying all 72 designs is impractical: even 72 designs × 30 minutes of testing per design = 36 person-hours, likely with different orderings for each participant. Statistical testing of 72 designs requires extremely large sample sizes (multiple comparisons problem — familywise error rate explodes).

Better strategy: Use the nested model to prune the space. (a) At Level 2, the task "compare trends over time" eliminates chart types that don't support temporal encoding — a pie chart is eliminated. (b) At Level 3, the expressiveness principle eliminates colour maps that use hue for quantitative temperature data — sequential value-based maps remain. (c) Prune to ~4-6 viable designs, then test these with think-aloud (formative) to identify the 1-2 best candidates, followed by a controlled experiment (summative) with those 2 candidates to determine the best with statistical rigour.

⚗️ Experiment Design: Variables

A well-designed experiment controls what changes and what stays the same:

Variable TypeDefinitionExample (chart comparison study)

Why Confounding Factors Are Dangerous

A confounding factor changes during your experiment and may also affect the dependent variable. You cannot then be sure whether the change in your results was caused by your independent variable or by the confounding factor.

Example: You run chart comparison tasks in the morning (chart A) and afternoon (chart B). It turns out participants are more tired in the afternoon. Their reduced accuracy on chart B might be due to fatigue (confounding) rather than chart B being worse. The experiment is now invalid for its intended purpose.

Fix: Counterbalancing — randomise the order of conditions across participants, so fatigue is a random variable, not a confound.

Pilot Testing

Always run a pilot study with 1-2 participants before the main experiment. Check: task phrasing is unambiguous, training is adequate, session duration is correct, data collected makes sense. "Create dummy data to see if it makes any sense."

📑 Qualitative Data Analysis: Thematic / Grounded Theory

Used for interview transcripts, open-ended questionnaires, think-aloud protocols. Method: inductive coding (grounded theory — no preconceived theories, let themes emerge from data).

Three Coding Stages

Stage 1: Open Coding ▼

Identify distinct pieces of information in raw transcripts. Assign an open code to each. Use in-vivo coding: use the participant's own words as the code label. Size/scope of pieces is determined by the coder's interpretive process.

Example codes from a vis evaluation: "too cluttered [001]", "bright colours [002]", "busy-ness [004]", "lively [005]".

Stage 2: Axial Coding ▼

Organise open codes into sets of concepts and categories. Think about relationships between codes. Categories don't all need to be at the same specificity level. Be driven by what's in the data, not by pre-existing theory or notions of symmetry.

E.g., codes 004 (busy) + 005 (lively) → category 006 (lively positive): users who find density engaging.

Stage 3: Selective Coding ▼

Combine concepts and categories into a larger concept framework. Re-code original transcripts using the new framework. This becomes the basis of your qualitative findings.

Reporting Qualitative Results

  1. Set out the coding framework
  2. One report section per major theme
  3. Use participant quotes as evidence
  4. Note frequency/context of each theme
  5. Discuss overall/higher-level findings
  6. Contextualise with related work
  7. Discuss design implications
Quant ≠ Better than Qual: Quantitative analysis is NOT inherently more rigorous than qualitative. It's common in qual to have multiple independent coders compare results (inter-rater reliability). This level of rigour is rarely applied to quant. Each can be done well or badly. Ideal: use quant to learn what users do, qual to learn why.

A researcher wants to determine which of three chart types (A: line chart, B: bar chart, C: scatter plot) is most accurate for reading quantitative values from a running club dataset. Independent variable: Chart type. Conditions: A=line chart, B=bar chart, C=scatter plot. This is what we deliberately change.

Dependent variable: Accuracy in reading quantitative values (% of answers correct, or mean absolute error between read value and true value). This is what we measure.

Control variables: The dataset presented (same running club data for all participants); the specific tasks/questions asked; the colours used in each chart; the screen used; the ordering of questions within each chart. These must be kept constant so they cannot affect accuracy.

Random variables: Participant age, gender, prior experience with charts, running knowledge, screen brightness. We allow these to vary randomly (counterbalanced across conditions); they should average out across participants.

(ii) Confounding factor example: If all participants do chart A first, then B, then C, fatigue or learning effects are confounded with chart type. Participants become more experienced with the dataset by chart C, which may improve accuracy independently of the chart type. This means we cannot tell if higher accuracy on chart C is due to chart C being better, or due to learning — the experiment is invalid for comparing charts. Fix: counterbalance the order of chart conditions across participants (randomise which chart each participant sees first).

(iii) Participants: For a summative experiment with statistical comparison, recruit ≥30 participants (commonly cited minimum for statistical validity). More precisely, run a power analysis: with a medium effect size (d=0.5), α=0.05, and 80% power, you need approximately 34 participants per condition (or ~34 total for a within-subjects design). Data collection: automatic collection (the system records the participant's answer and the time taken for each task) — objective, quantitative, and continuous.

Use ANOVA or t-tests to compare mean accuracy across conditions, with statistical significance testing (p < 0.05). However, supplementing with qualitative data (brief exit interview) helps explain why one chart was more accurate — e.g., participants may report that bar charts are clearer because of the zero-baseline anchor.

📏 Week 8: Rules of Thumb

Based on Tamara Munzner's Visualization Analysis & Design. Guidelines (not absolute rules) for good IV design.

🚫 Rule 1: No Unjustified 3D

Why 3D is problematic for abstract data

We "see" in 2.05D, not 3D. Thousands of points are acquired on the image plane via rapid eye movements; depth information requires slow head/body motion (one point per ray).

Problems with 3D:

  • Occlusion: objects block each other; interaction needed to resolve (costly)
  • Perspective distortion: object size and angle varies with depth; interferes with ALL size encodings; "power of the plane" is lost
  • Tilted text: legibility far worse when tilted from image plane
  • Depth position is a LOW-ranked channel (n=0.67 in Stevens' law)

When 3D IS justified

  • True 3D spatial data (e.g., medical imaging, molecular structure, fluid simulation)
  • Task is shape perception of 3D spatial objects
  • Constrained navigation with carefully designed viewpoints (e.g., NYT economic growth curve)

No unjustified 2D?

Even 2D spatial layout isn't always justified! If reading text is central to the task, a network layout (2D) has lower information density and harder label lookup than a simple list. Use 2D spatial layout only when topology/structure is important.

📋 All Rules of Thumb Summary

No Unjustified 2D ▼

Even 2D spatial layout (network node-link, map) is not always justified. If the primary task is reading text labels or looking up individual items, a simple sorted list has higher information density and faster lookup than a 2D network layout.

When 2D IS justified: When spatial structure or topology is meaningful — network diagrams (topology), maps (geography), scatterplots (correlation). When spatial position encodes data (e.g., SPLOM), 2D is always justified.

Exam point: A node-link diagram of 10 friends where the task is "find Alice's phone number" — a list is faster. A node-link diagram where the task is "find who connects Alice to Bob in 2 hops" — 2D is justified.

Eyes Beat Memory ▼

It is easy to compare side-by-side views (move eyes). Harder to compare a new item against memory of what you saw before.

Implications for animation: Animation = good for choreographed storytelling, transitions between 2 states. Poor for many states with changes everywhere → use small multiples instead (show time with space, not time with time).

Resolution Beats Immersion ▼

Pixels are the scarcest resource. Immersion (VR, AR) not helpful for abstract data — no need for sense of presence or stereoscopic 3D. Desktop is better for integration with other work. Both first-wave VR (1980-90s) and second-wave AR/MR appear to be poor for abstract data visualisation.

Overview First, Zoom & Filter, Details on Demand ▼

Shneiderman's influential slogan (1996). Pattern of tasks to design for:

• Overview ≅ identify: show most/all data; find interesting large-scale aggregates

• Zoom & Filter ≅ compare: closer views, selection, filtering

• Details ≅ summarise: individual data items within features

Responsiveness is Required ▼

Three response-time categories: 0.1s (perceptual), 1s (immediate), 10s (brief task). For large datasets: frontbuffer for selection highlight; progress bars; background threads; guaranteed frame rate.

Function First, Form Next ▼

Dangerous to start with aesthetics — usually impossible to add function retroactively. Start with functionality. Improve aesthetics as refinement. Aesthetics matter as "another level of function" — culture, Gestalt principles, visual hierarchy.

Basic design principles (Robin Williams, Non-Designer's Design Book):

  • Proximity: group related items; avoid equal whitespace for unrelated
  • Alignment: find strong line, stick to it; avoid auto-centering
  • Repetition: unify by pushing existing consistencies
  • Contrast: if not identical, make very different; avoid "not quite the same"
Labelling Best Practices ▼

Make visualisations self-documenting: meaningful titles, axis labels, legends. Axes need min/max tick marks. Everything plotted needs a legend. Use reasonable numerical format (avoid scientific notation). Don't label axes with arbitrary identifiers.

📐 Week 8b: Design Examples — Tufte & Classic IV Critiques

Based on Edward Tufte's foundational IV books and landmark historical examples. These concepts are directly examinable.

🧮 Tufte's Lie Factor

\[ \text{Lie Factor} = \frac{\text{size of effect shown in visualisation}}{\text{size of effect in the data}} \]

A lie factor of 1.0 = perfectly honest. >1 = effect exaggerated. <1 = effect understated. Tufte (1983) considers anything outside [0.95, 1.05] problematic.

Classic Example (Tufte 1983, p.57)

A chart showing fuel economy standards from 1978–1985. The data showed an increase from 18 mpg to 27.5 mpg = 53% increase.

The line drawn on the chart grew from 0.6 inches to 5.3 inches = 783% increase in line length.

\[ \text{Lie Factor} = \frac{783\%}{53\%} = 14.8 \]

The visualisation made the fuel economy improvement look nearly 15× more dramatic than it actually was.

Common Lie Factor Sources

  • Truncated y-axis: bar chart not starting at zero; a 5% difference looks like 50%
  • Non-linear scale misread: logarithmic axes not clearly labelled
  • 3D perspective distortion: far objects appear smaller → bars look different sizes when they're the same
  • Rubber-band scale: uneven spacing on the x-axis (e.g., intervals of 8,3,4,8,2,2 years displayed as equally spaced)
  • Inconsistent time windows: comparing tuition over 35 years vs. ranking over 11 years on the same chart

🗑️ Chart Junk (Tufte, 1983)

Definition

"Stuff that obscures the real information in the interests of prettiness." The unnecessary use of data-ink — ink that does not represent data variation.

Data-ink ratio (Tufte): the proportion of a chart's ink devoted to actual data. Maximise data-ink ratio. Remove anything that doesn't carry information: excessive gridlines, decorative backgrounds, 3D effects on 2D data, drop shadows, unnecessary borders.

Moiré Effect

Dense repeated patterns (e.g., cross-hatching in bar charts) interact with the physiological tremor of the eye to produce an apparent vibration effect. Distracting, reduces readability. Use solid fills or white space instead.

Useful Junk? (Bateman et al., 2010)

Bateman et al. CHI 2010 challenged Tufte — found that "chartoons" (embellished charts) were better remembered over a longer period than clean charts, though not more accurately read immediately. Key point: chart junk may have value for long-term memorability in journalism/storytelling, but not for analytical precision.

Design principle: For analytical IV tools (where precision matters), minimise chart junk. For public communication/storytelling (where engagement and recall matter), some embellishment can be justified.

🔢 Anscombe's Quartet — Why Visualisation is Essential

Anscombe (1973) constructed four datasets with near-identical summary statistics but completely different distributions. A powerful argument for always visualising data before drawing conclusions.

The Four Datasets (I, II, III, IV)

All four have (to 2-3 decimal places):

📜 Historical IV Examples

Florence Nightingale's Coxcomb (1858)

Polar area diagram showing causes of soldier deaths in the Crimean War. The large blue wedges (preventable disease) vastly dwarfed the red wedges (battle wounds), making the case visually compelling to Parliament that sanitation reform was needed.

Why it matters: First major example of data visualisation used to drive policy change. The coxcomb made the comparative cause-of-death data impossible to ignore — where tables of numbers had failed to motivate action, the visualisation succeeded.

John Snow's Cholera Map (1855)

Dot map of cholera deaths in London, with pump locations marked. The spatial cluster of deaths around the Broad Street water pump provided visual evidence of waterborne transmission — at a time when miasma theory (bad air) was the accepted explanation.

Why it matters: Demonstrates how spatial visualisation (geographic clustering) can reveal a causal mechanism invisible in tabular data. The map is one of the first instances of visualisation used for epidemiological investigation. Adding Voronoi polygons around each pump (retrospective overlay) shows that most deaths fall within the Broad Street pump's area.

Question 14b — Lie Factor & Anscombe

(i) Define Tufte's Lie Factor and explain its significance in information visualisation design. Calculate the lie factor for a chart that shows a data increase of 25% using a visual element that grows by 200%. (ii) Describe Anscombe's Quartet and explain what it demonstrates about the relationship between statistical summaries and data visualisation. (iii) Identify two specific design choices that introduce lie factor distortion in practice, and propose corrected alternatives for each.

(i) Lie Factor:

Tufte (1983): Lie Factor = (size of effect shown in visualisation) / (size of effect in data). A value of 1.0 is perfectly honest; values significantly above 1 exaggerate the effect; values below 1 understate it. Significance: viewers interpret visual magnitudes as proportional to data magnitudes — a chart with a large lie factor misleads viewers into drawing incorrect conclusions about the scale of a change or difference, even when the numbers are printed correctly.

Calculation: Data effect = 25%. Visual effect = 200%. Lie Factor = 200/25 = 8.0. The chart makes the change look 8× more dramatic than the data supports.

(ii) Anscombe's Quartet:

Four datasets constructed with near-identical summary statistics (mean, variance, correlation, and linear regression line all match to 2-3 decimal places) but completely different scatter plot appearances: one linear, one parabolic, one linear with an outlier, one vertical cluster. Demonstrates that summary statistics (mean, correlation, R²) are insufficient to characterise the true structure of a dataset — two analysts relying only on statistics could draw identical conclusions from completely different underlying data. Visualisation of the raw data is essential before analysis; statistical summaries can mask non-linearity, outliers, and degenerate distributions entirely. Extended by Matejka & Fitzmaurice (CHI 2017) who showed you can produce a dataset whose statistics match Anscombe's while the scatterplot looks like a dinosaur.

(iii) Two design choices and corrections:

1. Truncated y-axis in bar charts: Starting a bar chart y-axis at 95 instead of 0 makes a 2% difference (95→97) look like a 100% difference visually (bar doubles in height). Lie factor = visual doubling / 2% ≈ very large. Correction: always start bar chart y-axes at zero; use line charts if showing trends where small differences matter and zero is not meaningful.

2. 3D perspective on 2D charts: A 3D bar chart creates perspective distortion — bars at the back appear shorter than bars of the same height at the front. A bar representing 50 at the back looks like it's ~40 due to foreshortening. Lie factor varies by bar position. Correction: use 2D bar charts; there is no justification for 3D when the data is abstract (no unjustified 3D rule).

🧠 Week 9: Cognitive Amplification & Knowledge Crystallization

⚡ Cognitive Amplification

Core Concept

Information visualisation as a cognitive tool — extends human cognitive ability beyond what unaided memory and reasoning can achieve. The visualisation acts as external memory and a reasoning aid.

External Cognition

Using the world as external memory (Kirsh & Maglio, 1994). Instead of computing internally, offload computation to the visual representation:

  • Rotate Tetris blocks externally rather than mentally
  • Use a scatterplot to "see" correlations rather than compute them
  • Group items visually rather than remembering groupings

Analytic Discourse

Complex analytical reasoning supported by visualisation. Users build hypotheses, test them visually, accumulate insights, and communicate findings — all mediated through interactive visual displays.

Sensemaking

The iterative process of collecting data, encoding it into visual form, extracting insights, and refining the visualisation in light of those insights. Pirolli & Card's sensemaking loop: forage for information → schematise → build mental model → tell a story.

💎 Knowledge Crystallization

The process by which insights from data analysis become structured, communicable knowledge. Key stages:

  1. Data collection and filtering — identify relevant data sources
  2. Schema building — organise data into meaningful categories
  3. Hypothesis generation — form initial explanations
  4. Evidence gathering — test hypotheses with data
  5. Presentation — communicate findings to others

Design Implications

IV systems should support the full sensemaking/knowledge crystallization loop — not just the "display" stage. This means supporting:

  • Annotations and note-taking within the visualisation
  • Bookmarking/recording significant views
  • Sharing and presenting findings
  • Iterative refinement of views
  • Integration with external tools

Question 15

The concept of "external cognition" suggests that information visualisation tools act as cognitive amplifiers, extending human reasoning beyond what unaided memory allows. Using two specific examples from data analysis tasks, demonstrate how a well-designed interactive visualisation supports external cognition. For each example, describe (i) what cognitive task the user faces without visualisation; (ii) how the visualisation externalises that task; and (iii) what perceptual or interaction mechanism makes this effective. Conclude with a discussion of the design implications for IV systems.

Example 1 — Correlation detection in multidimensional data:

(i) Without visualisation: an analyst with a 100-column spreadsheet must compute correlations between all pairs of variables mathematically, holding each result in working memory while comparing to others. This exceeds working memory capacity (Miller's 7±2 chunks) for even moderate dimensionality.

(ii) A scatterplot matrix (SPLOM) externalises this: each cell shows the bivariate scatter of two dimensions. Correlation is visible as a diagonal cluster of dots — a pre-attentive Level 1 feature — no calculation needed. With 10 dimensions (45 plots), the analyst can visually scan for correlations in seconds rather than computing 45 Pearson coefficients.

(iii) The mechanism is Stevens' Law (position on common scale, n≈1) and pre-attentive processing: correlated data produces diagonal patterns that pop out from random scatter. Brushing and linking further externalises the task: select an outlier in one plot → all other plots highlight it, showing which other dimensions this outlier is anomalous in. The external representation does the multi-dimensional tracking that internal memory cannot.

Example 2 — Temporal pattern recognition in time series:

(i) Without visualisation: a researcher checking whether electricity consumption follows weekly patterns across a year must mentally compare 52 weeks of hourly data — impossible to hold in memory.

(ii) A calendar heatmap (van Wijk & van Selow, 1999) externalises weekly patterns: each day is a cell coloured by consumption. The visual pattern (dark Mondays, light Saturdays) is immediately apparent. The human visual system's pattern recognition (Level 2, Gestalt: similarity and continuity) detects the recurring structure without any calculation.

(iii) Linking the heatmap to a superimposed time-series line chart (showing average day profiles for selected clusters) allows the analyst to both identify which weeks are anomalous (heatmap) and understand what makes them anomalous (line chart profile). External memory via the linked view replaces the need to remember the Monday profile while inspecting the Saturday profile.

Design implications: IV systems should maximise the use of pre-attentive and Gestalt features to externalise pattern detection (Level 1 and 2 processing). Interaction should support the sensemaking loop by allowing annotation, bookmarking, and linking between views. "Eyes beat memory" principle: design for side-by-side comparison, not sequential viewing. Responsiveness (<0.1s) ensures the visual system and the external representation are synchronised — any lag breaks the externalisation effect.

Question 15b — Pirolli & Card Sensemaking Loop

Pirolli and Card's sensemaking model describes how analysts move between "foraging" for information and "making sense" of it. (i) Describe the two main loops in the model and explain what happens at each stage. (ii) Identify three specific features of an interactive visualisation that would support the foraging loop and explain how each reduces cognitive cost. (iii) Explain how the "representational bottleneck" described by the model relates to the design of IV systems — and describe one concrete design choice that specifically addresses this bottleneck.

(i) The two main loops:

Foraging Loop (bottom/left): The analyst searches for and filters relevant information. Stages: search for sources → read/filter content → extract relevant snippets to a "schema" (organised collection). The cognitive cost is managing the query process — knowing what to search for, finding it, and deciding what's relevant. This loop is about information acquisition.

Sensemaking Loop (top/right): The analyst organises extracted information into a frame (mental model, hypothesis, explanation). Stages: place items into a schema → build a hypothesis → verify hypothesis against data → create a product (report, decision, insight). The cognitive cost is holding the current state of the hypothesis in working memory while examining new evidence. Failures here mean the analyst must "restart" their mental model.

The two loops interact: foraging provides raw material to sensemaking; sensemaking generates new queries for the foraging loop. A good IV system accelerates both.

(ii) Three features supporting the foraging loop:

1. Dynamic Queries (interactive filters): Allows the analyst to narrow the information space instantly (<0.1s response). Instead of formulating a SQL query (requires expertise, breaks the foraging flow), the analyst moves a slider to filter by year or magnitude. Reduces the cognitive cost of "knowing what to search for" — the analyst can explore incrementally. Supports discovery of unexpected patterns.

2. Details on Demand (hover tooltips): Instead of clicking through to each item individually, hovering reveals key attributes. Reduces the cost of "reading/filtering content" — the analyst can scan many items rapidly without committing to navigation. Keeps the overview visible while accessing item-level detail.

3. Search-and-highlight: Typing a query term highlights matching items in all linked views simultaneously. Reduces the cost of locating relevant items in a large space — the analyst does not need to remember or re-identify items across views. The visual system handles tracking (pre-attentive colour pop-out).

(iii) Representational Bottleneck:

The representational bottleneck is the limit on how much of their current "working schema" an analyst can hold in their head simultaneously. As the analyst forages more information, their mental schema grows beyond working memory capacity — they forget early findings, lose context, make contradictory hypotheses.

IV as an external cognitive store directly addresses this bottleneck: the visualisation itself becomes the externalised schema. The analyst does not need to remember which clusters exist in the data — they are persistently displayed. Concrete design choice: persistent annotation/bookmarking — the analyst can pin notes ("this cluster appears in 2008 only") directly to the visualisation. These notes persist across sessions, offloading the schema maintenance from working memory to the display. The bottleneck is widened because the representational capacity is now limited by the screen, not by the 7±2 working memory chunks.

Stevens' Power Law: S = k·Iⁿ. When n=1, perception is accurate. n<1 = underestimation; n>1 = overestimation. IV designers should choose channels where n≈1 for quantitative data, or use channels whose n-value is well-understood so corrections can be applied. The most important implication: position (n≈1) is the most reliable channel for quantitative encoding; area (n=0.7) and brightness (n=0.5) cause systematic perceptual error.

Strength: scalable to 200 countries × 20 years in a single compact view. Weakness: sector dimension not encoded — need separate heat maps per sector or interaction.

Encoding 2 — Bubble chart (country × year matrix, bubble size=unemployment): Size/area encodes unemployment. n=0.7 — systematic underestimation. Encoding 3 — Line chart (year on x, unemployment on y, one line per country, colour=sector): Position on common scale (y-axis) encodes unemployment — n≈1.0, accurate. Mock Q3

Explain the key differences between t-SNE, UMAP, and spring model approaches to dimensional reduction in information visualisation. In your answer, include: the core algorithmic concept for each; their relative strengths and weaknesses for preserving local vs. global structure; their computational complexity; and a scenario where you would choose each approach over the others.

Spring Models (force-directed):

Core concept: simulate springs between all pairs of objects. Ideal spring length ∝ high-D distance (similarity metric). System iterates until forces reach equilibrium. Local structure: good (similar objects pulled together). Global structure: good — both neighbours and non-neighbours are accounted for, unlike t-SNE. Complexity: O(N³) naïve; O(N log N) with Barnes-Hut; O(N) with Chalmers' sampling. Scales to millions with fast variants.

Scenario for spring models: A dataset of N=500,000 genomic sequences with both local similarity (subspecies clustering) and global taxonomy relationships important. Need to show both fine-grained clusters AND the relative distances between clusters. Spring model (with Chalmers-style sampling) scales to this size and preserves both local and global structure.

t-SNE (Stochastic Neighbour Embedding):

Core concept: use KL-divergence to match the probability distribution of neighbours in 2D to the distribution in high-D space. High penalty for neighbours that are far in layout; low penalty for non-neighbours that are close. Excels at local structure; poor global structure. Risk: creates clearly separated clusters even where none exist in the data — scientists may be misled into interpreting artificial clusters as real. Complexity: O(N²) or O(N log N) with approximations; typically limited to N < 50,000.

Scenario for t-SNE: Exploring a dataset of N=5,000 cell images in a biology lab where the primary goal is identifying distinct cell types (clusters). Global relationships between cell types are not important for this task. t-SNE's clear cluster separation aids cell-type identification. N is small enough for t-SNE to run efficiently.

UMAP (Uniform Manifold Approximation and Projection):

Core concept: build a topological representation (manifold) of the high-D data, then find a 2D embedding that preserves the manifold structure. Uses random projection trees and nearest-neighbour descent for fast neighbour finding, then stochastic gradient descent. Balances local and global structure better than t-SNE. Scales better: estimated O(d·N^1.14). Scales to millions.

Scenario for UMAP: A dataset of N=1,000,000 customer purchase records where both cluster identification (which customer segments exist?) and inter-cluster relationships (how similar are luxury buyers to budget buyers?) matter. UMAP scales to 1M objects and preserves both local clusters and their relative global positions — the right balance for this use case.

4. Area channel (choropleth) bias: Large-area countries (Russia, Canada, Australia) visually dominate regardless of their actual sales figures. Small high-sales countries (e.g., Singapore, Belgium) are barely visible. Area of the country is an irrelevant variable that strongly influences the viewer's impression.

Overview first, zoom and filter, details on demand (Shneiderman, 1996):

A sequential task pattern: (1) Overview — show all/most of the data to identify patterns and interesting aggregates (Query → Identify); (2) Zoom and filter — use interaction to focus on these aggregates (Query → Compare); (3) Details — inspect individual items within them (Query → Summarise). Example — Medical records: Overview: a timeline showing all 1,000 patients' hospital visits as dots (overview of the full dataset). Filter: use a slider to filter to patients aged 60-70 with hypertension. Zoom: enlarge the filtered subset to see individual visit patterns. Details: click one patient → popup shows full medical record.

Focus and Context:

Shows detail AND overview simultaneously in the same view. The focused area is magnified; the surrounding context is compressed but remains visible. The user never loses sight of where the focused area sits within the whole. Techniques: fisheye distortion, perspective wall, hyperbolic trees.

Example — Map navigation: A fisheye distortion of a city map magnifies the area around the user's current location (focus) while showing surrounding city regions at compressed scale (context). The user can plan a route from their location to a distant area without losing spatial context.

Design considerations:

Overview+zoom: requires clear interaction controls for filtering; transitions between overview and detail must be smooth; breadcrumb navigation helps users understand where they are in the hierarchy. Works best when the overview and detail are qualitatively different (e.g., aggregate vs. individual level).

Focus+context: requires careful distortion design to prevent perceptual confusion at the distortion boundary; the compression function must preserve enough context to be useful; labels in context area must remain legible despite compression. Works best for continuous spatial data (maps, large documents) where context is spatially meaningful.

When to prefer each: Overview+zoom for hierarchical data with clear abstraction levels; when the overview and detail views are categorically different. Focus+context for spatially continuous data where location within the whole is constantly relevant; when users need to navigate large homogeneous datasets while retaining positional awareness.

Describe the Gestalt laws of visual perception and explain how each one can be used as a design principle in information visualisation. For at least four Gestalt laws, give a specific visualisation example showing both correct application and a common violation of each law.

Proximity:

Law: elements that are physically close are perceptually grouped. Design principle: place related chart elements (e.g., a chart and its legend) close together; avoid equal whitespace between unrelated elements.

Correct: legend placed directly adjacent to its chart, no whitespace between them. Violation: legend placed on the opposite side of the screen from its chart with equal whitespace — viewer groups the legend with nearby text rather than its chart.

Similarity:

Law: similar elements tend to be grouped. Design principle: use the same colour to encode the same category across all views in a multi-view system.

Correct: in a SPLOM, all dots representing "category A" are consistently blue in every scatterplot. Violation: same categories coloured differently in different views — the user cannot trace the same item across views perceptually, defeating brushing and linking.

Connectedness:

Law: elements connected by lines are grouped. Design principle: draw edges/links to show relationships in network diagrams; use line charts to imply continuity in time series.

Correct: a network diagram with visible edges clearly shows which nodes are related. Violation: placing related data items close to each other without a connecting line (relying on proximity alone) — viewers may group them with other nearby unrelated items instead.

Common Fate:

Law: elements that move together are grouped. Design principle: animate only related elements simultaneously; use coordinated motion to show group membership.

Correct: when a user selects a cluster in a spring model, all selected dots gently pulse together → the viewer perceives them as a group. Violation: animating ALL elements simultaneously (e.g., 30-year animated bar chart where every bar moves at every frame) — no selective grouping possible from motion, just visual noise.

Closure:

Law: contours with gaps are perceptually closed. Design principle: enclose related data within a region (box, colour background) to signal grouping without explicit borders.

Correct: a dashed rectangle around a group of bars in a bar chart signals they represent the same time period. Violation: using equally-spaced columns in a dashboard with no enclosing regions — viewer sees an undifferentiated grid rather than logical groupings of related charts.

(ii) Animated bar chart racing — PARTIALLY recommended (with caveats):

Animation is suitable for the "literal" end of the literal→abstract axis (showing time with time). For storytelling about how GDP evolved, the animation can be effective — each frame shows one year's ranking, and the motion draws attention to fast-rising/falling countries. However, "eyes beat memory" warns against using animation for complex multi-object comparison: viewers cannot compare, say, 1985 to 2015 without remembering the 1985 state. If the task is comparison across many years, small multiples would be superior. Recommendation: use animation for storytelling/presentation (one audience viewing, no need for precise comparison); add a scrubber slider so users can pause and compare any two years directly. [4 marks]

(iii) VR for molecular simulation — RECOMMENDED:

This is one of the justified uses of 3D. The data IS 3D spatial (atomic positions in 3D Euclidean space). The task IS shape perception of 3D spatial objects (how does the protein fold?). Interactive 3D navigation (rotation, zoom) allows synthesis across multiple viewpoints — standard 2D projections lose depth information critical to understanding molecular geometry. "Resolution beats immersion" warns against VR for abstract data, but molecular simulation is genuinely 3D spatial — the exception, not the rule. Caveats: ensure high resolution (pixel density in the VR headset), support navigation interaction with clear viewpoint cues, and consider stereoscopic rendering quality. [4 marks]

(iv) Aesthetics before encoding — NOT recommended:

Violates "function first, form next". Starting with colour themes and typography before deciding what data to encode creates a design prison: the chosen aesthetic will constrain what encodings are possible. For example, if a corporate blue colour theme is chosen first, it may be impossible to later use blue for a meaningful categorical distinction in the data. "Usually impossible to add function retroactively" — the aesthetic decisions will have created commitments (layout, typefaces, colour palette) that limit the expressive range of the encoding. Correct approach: encode data first using optimal channels (position, then size, then colour), verify the design is expressive and effective, THEN bring in a graphic designer to refine the aesthetics within the constraints of the encoding. [3 marks]
